# Форма плана реализации

Объём реализации и рабочая спецификация определяются в диалоге. Процесс плана, DOCS и delivery задан Workflow Core; SPEC ниже — форма требований. Запиши только данные задачи, служебные поля создаёт Kit.

```json
{
  "id":"prototype-001",
  "spec":"docs/planning/prototype.md",
  "objective":"Пользователь получает работающий результат",
  "stack":"Node.js",
  "checks":[{"id":"test","executable":"node","args":["--test"],"kind":"test"}],
  "tasks":[{"id":"T001","title":"Реализовать основной сценарий","files":["src/main.mjs","tests/main.test.mjs"],"checks":["test"],"acceptance":["Сценарий и обработка ошибок работают"]}]
}
```

Сохрани JSON в `.harness/runtime/plan.json`, вызови `./scripts/workflow plan:create --input .harness/runtime/plan.json`. Подставь существующий стек и реальные проверки; Node не обязателен. spec — существующий документ требований. Небольшой самостоятельный результат может составлять одну микрозадачу.

files — предполагаемые пути; acceptance, why, commit, dependencies уточняются при необходимости. checks — ID проверок конфигурации. Для delivery используется verification_kind package или installed и проверка того же kind с evidence; форму показывает task:start --help. Контекст задачи выбирается через context_pack в plan:apply; не копируй шаблоны в проект.

Для нового плана с настройками выполнения передай вместе `parallel_allowed` (boolean), `max_workers` (целое ≥ 1), `execution_strategy` (`sequential`/`parallel`) и непустую `execution_reason`. Это снимок новой основной сессии, не текущих Settings. Отсутствие всех четырёх полей сохраняет legacy-последовательность. OFF или лимит 1 допускают только sequential; ON не обязывает выбирать parallel. Зависимости нового плана должны стоять раньше задачи.

У задачи `parallel_safe` — boolean, по умолчанию false при нормализации нового плана. false означает исключительное выполнение: в parallel-плане задачу также получает отдельный исполнитель. true требует конкретных путей записи; glob/неизвестная область запрещены. Пересечение областей допустимо в плане, но исключает совместную выдачу. Общая спецификация в documentation_paths тоже считается областью записи; read-only контекст задаётся через context_pack, а не предполагается по имени файла.

Review получает нормализованные поля и включает их в digest согласованной пары. Служебный commit_ref не заполняй: DONE родительской задачи parallel-плана требует роли integration с operation_id и source_commit. Собственный SHA интеграции восстанавливается из Git. Коммит локального задания не подтверждает родительское DONE; операции назначения и слияния реализуются отдельно от этой формы.

После публикации parallel-плана завершите ответ и передайте выполнение Web Pilot. Основной чат не вызывает task:start и commit его задач в main. Все задачи, включая основу и исключительные, выполняются в назначениях. Единственное управление запуском для пользователя — AutoPlan конкретного проекта: ON запускает готовые назначения, OFF оставляет план ожидающим. После завершения плана AutoPlan выключается; новый план начинает с OFF. Агент переключателем не управляет.
