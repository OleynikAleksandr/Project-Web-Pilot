# Назначения и интеграции

Workflow Kit 1.7.2 поддерживает подчинённые задания parallel-плана в Git worktree и проверяемое принятие результатов непосредственно в main. Один checkout — один current plan и один пишущий агент. Сессия планом не владеет; приложение координирует чаты, Kit проверяет Git и состояние.

Код: `src/lib/plan.mjs` (схема), `task-assignment.mjs` (выдача/подготовка/проверка источника), `task-integration.mjs` (merge и восстановление), `task-handoff.mjs` (передача прежнего старта main), `validate.mjs`, `transaction.mjs`, `actions.mjs`, `recovery.mjs`. Команды доступны через штатный launcher.

## План

Опциональный полный набор `parallel_allowed:boolean`, `max_workers:positive safe integer`, `execution_strategy:sequential|parallel`, `execution_reason:string` сохраняет разрешение и решение. Parallel требует ON и max_workers>1. В Web Pilot `execution_origin_session_id` обозначает сессию происхождения снимка, отдельно от адресата Review.

Каждая задача нового плана имеет parallel_safe, dependencies, functional_paths, documentation_paths, acceptance_criteria и verification_ids. Зависимости ссылаются назад в топологическом порядке, без циклов/самоссылок/неизвестных ID. parallel_safe=true требует конкретных проверяемых путей без glob; пересечение областей допустимо в плане, но исключает одновременную выдачу. false означает исключительную задачу. Legacy без полей не преобразуется в parallel.

## Назначение

- `assignment:create --input <JSON> --expected-revision <revision>`: id, task_id, абсолютный worktree и base_commit текущего main. Ветка создаётся как workflow/<id>.
- `assignment:status --id <id>` — проверенное состояние; в дочернем worktree ID берётся из локального назначения.
- `assignment:setup --id <id> --npm-ci` — явная подготовка Node-окружения worktree.

Перед выдачей нужны активный parallel-план без основной текущей задачи, чистый main без Git-операции/транзакции, актуальная revision и HEAD, готовые интегрированные зависимости, допустимые области и лимит. Реальные Git-пути, свободная ветка и каталог проверяются; worktree находится вне основного checkout, symlink не допускаются. Чужие пути не используются.

Родительские записи лежат в собственном git-dir/workflow-kit/assignments/<id>.json; дочерняя — в собственном git-dir/workflow-kit/assignment.json. Они связывают parent scope/task/root, ID, worktree, branch, base_commit и external_dependencies. Повтор create того же ID сверяет неизменность входов и продолжает прежнюю выдачу; второй ID для уже назначенной задачи запрещён.

В дочернем worktree один локальный план scope assignment-<id>, одна неизменная задача, dependencies=[] и проверенное внешнее происхождение зависимостей из базы. Подготовка создаёт отдельный commit. Разрешены task:start → работа → commit --task с назначенными проверками; новый план, Review, расширение задания, доставка и вложенные назначения запрещены.

Node-проверки требуют собственного окружения. При отсутствии подготовки статус NEEDS_SETUP и task:start не допускается. Setup выполняет npm ci по lockfile и штатные pre-скрипты; подтверждение сохраняется для конкретного дерева. node_modules main не копируются и не связываются symlink. Windows запускает npm через Node/npm-cli.js. Игнорируемые ресурсы создаются штатной подготовкой.

Статусы различают NEEDS_SETUP, READY, RUNNING, READY_FOR_INTEGRATION и подтверждённое INTEGRATED. Локальное DONE — только готовность источника к интеграции; общий план им не закрывается. Источник должен содержать ровно подготовку и один однородительский implementation-коммит с правильным scope/task/контрактом, допустимыми файлами, проверками и чистым рабочим деревом.

## Основной чат и восстановление прежнего старта

`task:start` в основном parallel-плане возвращает `PARALLEL_MAIN_READ_ONLY` до записи плана и файлов задачи. Все задачи, включая общую основу и исключительный участок, выполняются через назначения. Агент основного чата публикует план и заканчивает ход; выдачей управляет приложение при AutoPlan проекта ON. У sequential и дочернего назначения прежний цикл task:start/commit сохраняется.

`assignment:handoff --input <JSON> --expected-revision <revision>` принимает те же id/task_id/worktree/base_commit, что создание назначения. Это узкое восстановление ошибочного старта основного чата в Kit 1.7.0: допустимо только точное изменение task:start и принадлежащие ему обычные файлы в объявленной области. Чужие/staged правки, несовпадение HEAD, плана или снимка файлов отклоняются без очистки.

До первой записи содержимое и режимы файлов сохраняются в git-dir/workflow-kit/task-handoff.json. Затем main восстанавливается к опубликованной основе, создаётся одно назначение, туда переносятся файлы и квитанция их принадлежности задаче. Если реальный install --update уже зафиксировал прежний task:start, Kit создаёт отдельный plan-adjustment с TODO без перемотки Git. Коммит задачи и проверенная интеграция по-прежнему обязательны.

Повтор использует тот же ID и сохранённый вход. Журнал распознаёт свои частично выполненные операции, сверяет каждый файл и не перезаписывает новые внешние изменения. Незавершённая передача блокирует остальные записи (`HANDOFF_PENDING`); завершённая не создаёт второй worktree. Нового Send команда не выполняет.

## Интеграция

- `integration:start --input <JSON>`: {id, source_commit}, точный проверенный источник назначения.
- `integration:status`: ID операции, задача, источник, стадия, конфликты/провал проверки.
- `integration:continue --id integration-<assignment-id>`: продолжение той же операции после исправления или прерывания.

Main должен быть чистым и свободным. Журнал integration.json в собственном git-dir блокирует остальные записи Kit. Стадии включают PREPARED, MERGING, RESOLVING, CONFLICT, CHECKING, CHECKS_FAILED и UNKNOWN.

Git готовит merge --no-commit --no-ff. Только локальный дочерний план заменяется кандидатом общего плана, сформированным Kit из текущего main. Служебная конфигурация и runtime исполнителя не импортируются. Исходные файлы нельзя автоматически разрешать через ours/theirs. После проверки области и штатных checks/hooks объединённого кандидата создаётся двухродительский commit: прежний main и точный source.

Конфликт или провал проверки оставляет родительскую задачу PENDING и незавершённое слияние. Исправляющий агент работает в main в пределах операции, разрешает конфликт, явно добавляет исправленные конфликтные файлы в index и вызывает continue. Kit снова проверяет кандидат. Чужие изменения не прячутся и не удаляются; они блокируют продолжение.

Trailers интеграции содержат отдельную роль integration, ID операции и source SHA. План хранит идентичность принятия, а собственный integration SHA восстанавливается из истории: самохеш в создаваемый commit не записывается. DONE требует подтверждённой пары родителей и успешных проверок. HISTORY_NOT_LINEAR для обычных implementation-коммитов не отключается.

Повтор сверяет журнал/HEAD/родителей и завершает финализацию уже созданного коммита, не создавая второй merge. Историческое доказательство использует контракт задачи из первого родителя интеграции, поэтому последующее закрепление или удаление рабочего документа в DOCS его не отменяет. Неизвестный исход требует сверки, не нового merge. Автоматического reset --hard, удаления worktree/веток и переписывания main нет.

## Планирование и завершение

Размер задач определяется завершённым результатом, смысловыми зависимостями, общими контрактами, пересечением записи, контекстом, риском, проверками и ценой координации. Нет нормы строк/файлов/числа задач или обязательного benchmark. Разные файлы не доказывают независимость; основу и итог выделяют, когда этого требуют зависимости.

Перед последним DONE Web Pilot передаёт одно сохраняемое финальное поручение основной сессии; она завершает оставшиеся integration:start/continue, проверяет общий main и отвечает пользователю. Kit сохраняет прежние Git/checks-инварианты. READY_FOR_ACCEPTANCE не архивирует план; предпросмотр не останавливается. Протокол отправки принадлежит [приложению](../../../../docs/modules/parallel-execution.md).

## Проверки

Установщик 1.7.2 поддерживает 1.7.1 и прежний upgradeFrom. До записи отказывает при assignment.json, незавершённой integration.json или ещё не INTEGRATED родительском назначении. Исходник — packages/workflow-kit; установленную копию меняет только install --update, сохраняя current plan. check-previous-upgrade-fixture строит самосогласованный runtime с версией 1.7.1, выполняет реальный installer update до 1.7.2 и повтор без нового коммита; это синтетическая предыдущая копия, не неизменяемый релиз из Git.

Fixtures проверяют настоящие Git worktree, собственную npm-зависимость, NEEDS_SETUP, конфликты/ошибки checks, чужие изменения, последовательные merge, базу зависимой задачи, повтор и исторические доказательства. `check-parallel-execution-fixture.mjs` включён в npm run check. Upgrade-тесты начинают задачу на неизменяемом выпущенном runtime 1.6.4 из Git, обновляют, завершают и начинают следующую; сохраняются проверки 1.5.6 и Review 1.6.3. Отдельный тест обновляет неизменяемый runtime 1.7.0 из v0.6.105 с активной основной задачей, передаёт её файлы и завершает проверенную интеграцию. check-task-handoff-fixture проверяет прерывания, повторы и сохранение чужих правок. Native Windows и живой ChatGPT этими fixtures не приняты.
