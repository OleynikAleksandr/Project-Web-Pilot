## Работа над прототипом и Git

Выполняй поставленную задачу за минимально необходимое количество шагов, сохраняя качество результата, необходимые проверки и понятные сообщения о ходе работы.

Для создания и доработки программного продукта по умолчанию готовь быстрый работающий прототип. Подготовка к эксплуатации и распространению начинается по явному поручению пользователя. Выполни все заказанные функции; не добавляй инфраструктуру и возможности на будущее. Для других типов работы выбирай столь же прямой путь к проверяемому результату.

Из запроса определи результат, основной пользовательский сценарий, способ запуска и достаточную проверку. Ясное поручение уже разрешает работу: запиши короткий контракт и план без повторного согласования. Обратимые решения принимай самостоятельно с учётом существующего проекта. Уточняй только то, без чего нельзя корректно продолжить. Не переизобретай архитектуру и не навязывай стек.

Для выдаваемого артефакта определи конечный путь и проверь конкретное назначение до сборки, включая символические ссылки; ошибка чтения не означает свободный путь; перед записью повторно проверь свежую доступность назначения. Сначала обеспечь основной сценарий целиком, затем заверши запрошенный объём. Продумай проверку до первой сборки и проверяй через тот интерфейс, которым пользуется пользователь. Проверяй выдаваемую копию; внутренний вызов функции не подтверждает кнопку, Enter или внешний API. Не подменяй требуемую интеграцию имитацией. Перед завершением сопоставь критерии результата с фактически выполненными проверками; недостающую существенную проверку выполни либо явно укажи ограничение. Подтверждай только фактически проверенные свойства.

Для локального прототипа не выбирай пользовательские сертификаты, не запускай подпись для распространения, нотарификацию, публикацию и настройку выпуска. Отключи автоматический выбор сертификата в сборщике. Выполни необходимую для запрошенного запуска упаковку; платформенную техническую подпись без сертификата применяй только если она нужна для запуска.

Build/package/sign/notarize/release/publish разрешены только внутри активной микрозадачи, где соответствующее действие прямо названо. Не запускай их как вспомогательный шаг code/test/DOCS-задачи. Перед любой сборкой или GitHub publish актуализируй и зафиксируй относящиеся к результату документы; push при незавершённой DOCS текущего плана отклоняет pre-push hook, не обходи его --no-verify. Если plan предусматривает delivery, DOCS должна быть завершена до явного delivery-хвоста; если явной delivery-задачи нет, сборка и публикация запрещены.

Используй уже доставленный контекст и сводку проекта. Недостающие независимые сведения о структуре, окружении и назначениях собирай одним обращением; различай среду клиента и среду сборки проекта. Объединяй независимые чтения и предсказуемые последовательности; при ошибке останавливай зависимые действия. Не повторяй успешные проверки без изменения относящихся к ним условий. Если commit запускает нужную проверку, отдельный предварительный запуск обычно не нужен. Например, объедини независимые чтения в один запрос, а согласованную цепочку установки зависимостей и сборки — в одну команду с остановкой при ошибке. Создание папки не требует отдельного обмена перед записью файла. Ожидай тот же процесс, не запускай его заново. Сохраняй содержательные промежуточные сообщения.

Если выдаёшь пакет или архив, определи необходимый для его использования состав и проверь фактическое содержимое. Рабочие инструкции, служебное состояние и материалы разработки включай только если они нужны получателю; .gitignore не задаёт состав пакета.

План соразмерен работе: небольшому прототипу достаточно одной задачи реализации с проверкой и финальной DOCS. Отдельные задачи нужны для самостоятельных результатов, не для каждой команды. Документы кратко сохраняют результат, запуск, проверку и ограничения; подробности не дублируй. Архитектурное усложнение должно решать текущую задачу.

**Git и завершение микрозадачи**

- До правок учти staged, unstaged и untracked из recovery; обнови status/diff, если состояние изменилось. Существовавшие изменения не присваивай задаче и не удаляй. Перед реализацией начни task:start.
- До первой сборки, генерации или установки зависимостей определи фактические выходные каталоги. Обнови .gitignore для воспроизводимых артефактов, кэшей, временных файлов и локального состояния. Сохраняй исходники, необходимые ресурсы и lock-файлы. Не исключай каталоги только по названию и сохраняй пользовательские правила.
- .gitignore не действует на уже отслеживаемые файлы. Если они должны выйти из Git, отдельно проверь состав и сохраняй рабочие копии; не применяй массовое удаление из index или очистку проекта ради проверки.
- Перед commit проверь фактические status/diff, включая содержимое новых файлов. Не используй git add . вслепую. Дополнительные исходники допускаются без task:update; артефакты и посторонние правки автоматически включаться не должны. При неоднозначном составе передай commit --files с относящимися к задаче путями.
- Каждую микрозадачу заверши отдельным commit через Workflow Kit с необходимыми проверками. Не обходи hooks, не создавай пустые исходники или бессмысленные правки документации. Задача завершена только после подтверждённого Git-коммита.
- При отказе исправь конкретную причину и повтори commit. После прерывания сначала проверь, создан ли коммит; не повторяй выполненную работу. repair нужен лишь для незавершённой транзакции, которую нельзя завершить обычным повтором.

Начинай task:start до изменения .gitignore: иначе собственная ранняя правка будет считаться существовавшей до задачи. Если это уже произошло, проверь авторство и до commit явно включи нужный файл через --files вместе с остальными файлами задачи. После commit проверь excluded_changes и status; перед финальной DOCS не оставляй незамеченных собственных правок. Для изменения только правил .gitignore достаточно проверки изменения и контрольных примеров git check-ignore; полный прогон приложения повторяй лишь при связанных изменениях. Явно назначенные проверки остаются обязательными.

При первом осмотре объединяй независимые сведения о доступных инструментах, версиях и будущих путях результата с чтением нужных файлов. Не выделяй заранее известную независимую подготовку в отдельный обмен с моделью. Содержимое крупных рабочих изменений в recovery может быть представлено ссылкой CHANGE_CONTENT_ON_DEMAND: перед зависимым действием прочитай соответствующий файл или diff. Ссылка и контрольная сумма не заменяют проверку содержимого.
