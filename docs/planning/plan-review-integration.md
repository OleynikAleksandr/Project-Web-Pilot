# Ревью плана: интеграция, очистка и приёмка

Вторая обязательная часть [спецификации Review](plan-review.md).

## Продолжение после паузы

Обычный путь — агент сам ведёт все раунды в одном ходе. Если он завершил ход раньше, Web Pilot по файловому событию и состоянию страницы может отправить узкое продолжение именно review-цикла с путём и поколением результата. Это разрешённое расширение автоматических сообщений, независимое от AutoPlan и работающее при NONE. В сообщении — указание прочитать состояние и продолжить предусмотренный шаг, без содержимого документов и без разрешения кода.

При NEEDS_USER допустимо одно продолжение основного агента, чтобы он озвучил ошибку/спор и задал вопрос, если не сделал этого в текущем ходе. После этого ожидать пользователя. Машинно различать «нужно сообщить проблему» и «вопрос уже передан», не читать семантику ответа ChatGPT для разрешения следующего раунда.

Повторно использовать проверки Composer/AutoPlan: выбран правильный checkout и разговор, страница готова, нет busy/пользовательского draft/ручной остановки, пауза не использована, запись sending перед Send и sent после. Review и AutoPlan используют общую защиту от двух сообщений на одной паузе, а не только composer.inFlight. На паузе после публикации возможен только переход к AutoPlan; старое событие review уже погашено. UNKNOWN не отправляется повторно автоматически.

Наблюдать явный state-файл существующим ProjectInputWatch; одного добавления пути в PlanMonitor недостаточно — нужен потребитель событий review. Не вводить постоянный функциональный polling. Ограниченные ожидания команды и watchdog допустимы. После restart перечитать сохранённое состояние; не повторять неизвестный запуск или Send. При потерянной exec session, зависшем RUNNING и невозможности подтвердить результат — видимая ошибка и решение пользователя. Не обещать, что процесс обязательно переживает перезапуск исполнителя.

Смена проекта не направляет результат чужому разговору. До возврата корректного получателя доставка ждёт. Продолжение другим чатом допустимо после чтения состояния того же checkout и явного подхвата пользователем; отдельного плана у чата не появляется.

## Публикация и взаимодействие с Kit

review:publish вызывает штатный путь создания scope с текущими проверками; не заменяет конфигурацию checks пустым или неполным списком. Предпочтительная основа — createScope с полной формой и expectedRevision. Планировочные документы включены одновременно в documentation_paths и required context_pack. Большая спецификация делится на части с обязательным включением каждой части.

Проверить разрешение ревью, SHA актуальной пары, вердикт/явное решение пользователя, NONE и базовый HEAD/revision внутри штатной блокировки Kit непосредственно перед созданием scope. Обязательная проверка должна действовать и при прямых plan:create/scope:create, чтобы случайный другой путь не обошёл включённый Review. plan:create не должен успеть изменить checks до отказа REVIEW_REQUIRED. Поведение carryover определить явно: существующее прямое пользовательское поручение переноса не превращается автоматически в новое ревью первой версии.

Если документы, HEAD или revision изменились после согласования, результат STALE: пересобрать входы и пересмотреть существенные изменения, не публиковать старый вердикт. Копировать только одобренные документы, не захватывать чужие изменения документации. Служебные значения Kit отличаются лишь по известным правилам. После коммита проверить итоговые blobs/задачи; при неопределённом исходе сначала штатный status/repair, а не повтор публикации.

Это защита от ошибок обычного workflow, не криптографическая граница против агента с полным файловым доступом. Не строить подписи, инфраструктуру доверия или отдельного арбитра. Нужны проверка связности результата и запрет случайной публикации при споре.

После подтверждённой публикации и проверки результата ставится PUBLISHED и разрешается обычное продолжение AutoPlan. До этого review имеет приоритет и не даёт AutoPlan начать уже видимый промежуточный ACTIVE при незавершённой публикации. При AutoPlan OFF никаких сообщений для исполнения задач не отправлять. При ON не спрашивать дополнительное разрешение пользователя. Review никогда сам не меняет кнопку автовыполнения.

## Очистка

Триггер — успешный переход первой задачи опубликованного scope в IN_PROGRESS через task:start; не публикация, не включение AutoPlan заранее, не начало подготовки плана. Очистка выполняется и при ручном запуске без открытого Web Pilot, поэтому привязать её к Kit, а не только к UI-наблюдателю.

После подтверждённого перехода удалять ровно зарегистрированную папку данного run: все черновики, позиции, запросы, ответы и журналы. Состояние очистки хранить вне удаляемого каталога минимально: scope/run и факт/ошибка очистки; без копий ревью и накопления истории. Убрать ссылки на удаляемые файлы из required recovery; опубликованная спецификация остаётся доступной.

Проверять принадлежность каталога checkout, run-id и отсутствие выхода через symlink. Не удалять .harness/runtime целиком, соседние циклы, прежние эксперименты или глобальную историю Claude. Не очищать RUNNING/NEEDS_USER. Повтор task:start и восстановление после crash выполняют очистку идемпотентно. Ошибка удаления видима и допускает безопасный повтор; не выдавать ложный «всё удалено» и не откатывать начавшуюся задачу ради уборки.

## Проверки и доставка

Автоматические проверки в рамках реализации, без ещё одной обязательной серии исследовательских раундов:
- Kit fixtures: обе формы создания плана; существующие checks; согласованная пара; существенный спор; ошибка/невалидный ответ; изменение SHA/HEAD/revision; повтор публикации и восстановление; чужие dirty документы не попали в коммит; OFF совместим с прежним Kit.
- Runner: новая сессия + resume, success/error/timeout/неизвестный исход, полный ответ в файле, предел раундов. Подмена CLI доказывает контракт, не живую модель.
- UI/Composer fixtures: четыре комбинации кнопок; зелёное/aria состояние; NONE/ACTIVE; restart; duplicate events; draft/Stop/busy; правильный получатель; единственная отправка на паузе; NEEDS_USER ждёт пользователя.
- Очистка: первый task:start вручную и AutoPlan, повтор/crash/ошибка, не затронуты спецификация, соседний каталог и symlink-цель; спор сохранил материалы.
- Проверить единые инструкции всех слоёв и packaged runtime, актуальность recovery/help, лимиты UTF-8. До DOCS — unit-all, electron-smoke, kit-check, codex-tools-live; executor-channel при изменении MCP-контракта.

Живая приёмка пользователем после установки: новый временный проект в Web Pilot, пара документов, реальные раунды Claude, появление ACTIVE, запуск по двум кнопкам/вручную и очистка. Отдельно ошибка авторизации и существенный спор с вопросом пользователю. Начать с macOS; native Windows и чистую ОС не объявлять проверенными по Mac fixtures или кросс-сборке.

План включает подготовку версии 0.6.102, DOCS, одну парную сборку и установку готового macOS приложения без пересборки. Перед delivery сверить, что версия не занята другим выпуском. Evidence конфигурации обновлять управляемо. Публикация GitHub в этот план не включена и выполняется по отдельному поручению. DOCS переносит действующий контракт в docs/modules/plan-review.md и связанные модули, после чего временная спецификация удаляется по правилам Kit с точной Git-ссылкой в recovery.
