[Черновик to-do-плана](parallel-execution-plan-draft.md).

## 1. Результат

В Project Web Pilot пользователь обсуждает задачу с основным агентом. Агент составляет спецификацию и план, при Review ON согласует их с существующим рецензентом. Когда параллельность разрешена и полезна, отдельные чат-сессии выполняют микрозадачи в отдельных Git worktree. Web Pilot управляет сессиями и очередями; Kit хранит проверяемое состояние и выполняет Git-операции. Готовые результаты сливаются непосредственно в main по одному.

Первая версия: Chat/Work и MCP, без SDK, модельных API, промежуточной ветки, службы/БД и ревью кода. Review документов сохраняется.

## 2. Решения пользователя и Settings

- В Settings — блок «Параллельное выполнение», переключатель «Разрешить параллельное выполнение» и, при ON, максимум одновременно работающих исполнителей. Предлагаемые начальные значения: OFF и 2.
- Настройки считываются один раз при создании пользователем новой основной сессии для нового обсуждения. Изменения Settings не влияют на уже созданную сессию, её план и исполнителей. Изменения лимита на ходу нет.
- Разрешение не обязывает распараллеливать. Планировщик и рецензент оценивают зависимости, пересечения изменений и практическую пользу.
- Если пользы нет, весь план выполняет основной агент обычным способом, без дополнительных чатов и worktree.
- Если выбран параллельный способ, основной агент ведёт планирование, а все обычные задачи, включая последовательные участки, выполняют назначенные чат-агенты.
- Общий план — в основном checkout, а не у сессии. Один checkout/worktree — один current plan и один пишущий агент.
- Слияния — непосредственно в main, по одному; main нельзя параллельно изменять во время интеграции.
- Зависимые задачи стартуют от main с уже проверенными результатами предшественников.
- Сессии исполнителей видны в сайдбаре; клик открывает соответствующий чат, остальные продолжают работать.
- Возможность параллельной работы ChatGPT подтверждена опытом пользователя; отдельного предварительного эксперимента нет.
- Финальная приёмка и закрытие плана — по поручению пользователя. Выпуск только через явно порученные delivery-задачи.
- Сегодняшняя архитектура должна допускать будущий detach **только чат-сессий** в отдельные окна того же Web Pilot. Сам detach сейчас не реализуется.

Лимит — положительное целое; неверный ввод отклоняется. При 1 исполнение последовательное.

Снимок настроек сохраняется в основной сессии; исполнители наследуют его. Перезапуск, просмотр сохранённого чата и автоматическое создание исполнителя не считывают Settings заново. В новом плане фиксируются разрешение, лимит, выбранный способ и причина.

Новая сессия при существующем ACTIVE-плане продолжает этот же план с его параметрами, не перенастраивает его и не создаёт второй. Её новый снимок применяется лишь к следующему новому плану. Legacy-сессии и планы без параметров остаются последовательными.

## 3. Разметка и выбор способа выполнения

Предлагаемые поля схемы; имена уточняются при реализации:

| Уровень | Поле | Значение |
| --- | --- | --- |
| План | parallel_allowed, max_workers | Снимок настроек |
| План | execution_strategy, execution_reason | sequential/parallel и обоснование |
| Задача | dependencies | ID задач, интеграция которых нужна до старта |
| Задача | parallel_safe | Допустимо ли одновременное выполнение |
| Задача | functional_paths, documentation_paths | Разрешённые области изменений |
| Задача | acceptance_criteria, verification_ids | Результат и его проверки |

Волны не хранятся: готовность вычисляется из зависимостей. Циклы, неизвестные зависимости и самозависимости запрещены. Топологический порядок/ссылки назад требуются только для новых планов с полями параллельности; legacy не меняются.

parallel_safe=false означает исключительную задачу: она ждёт интеграции ранее выданных заданий и не допускает соседних запусков. Это не назначение планировщику.

Пересечение областей не делает план ошибочным: такие задачи выдаются по очереди. Неизвестная область при parallel_safe=true — ошибка разметки.

Одновременно выдаются только готовые задачи со свободными местами и непересекающимися проверяемыми областями изменений. При неизвестной области задача последовательная. Семантические зависимости общих контрактов оцениваются при планировании: разные файлы сами по себе не доказывают независимость.

Агент объясняет выбор способа и лимита. При Review OFF решение принимает планировщик.

## 4. Роли и одно назначение

Планировщик ведёт документы; рецензент проверяет план; Web Pilot управляет сессиями и очередями; Kit проверяет состояние/Git; исполнитель делает одну задачу. Основная сессия может получить отдельное поручение на исправление интеграции.

Назначение содержит parent scope/task, уникальный ID попытки, абсолютный worktree, ветку, base SHA main, критерии, границы и документы. Kit проверяет реальные Git-пути и назначение до правок. Выбранная строка сайдбара не определяет cwd. Это проверка адресации, не файловая песочница MCP.

Recovery — штатными вложениями: 28000 байт на документ/часть, 180000 байт и 7 частей на пакет. Не через MCP.

Исполнитель вызывает task:start, работает, завершает через commit --task с проверками и заканчивает ответ. До коммита возможны несколько ходов одной задачи; продолжение не создаёт нового исполнителя. После коммита он не берёт следующую задачу.

Исполнитель не расширяет объём, не редактирует общий план, не запускает вложенных агентов, новый пользовательский план или отдельный Review локального задания. Изменение требований возвращается планировщику.

## 5. Общий план и локальные задания

Техническое предложение для Kit:

1. В main — один общий current plan.
2. В worktree — локальный current plan одной выданной задачи, связанный с parent scope/task и base SHA. Это подчинённое задание, не самостоятельный пользовательский план.
3. Зависимости локального задания подтверждаются интеграциями родительского плана, присутствующими в base SHA.
4. Подготовка задания и коммит исполнителя имеют отдельную идентичность scope/role: нельзя получить два implementation-коммита одной родительской задачи.
5. Локальное DONE означает «готово к интеграции». Родительское DONE возможно только после проверенного слияния.
6. Дочерний .harness/plans/todo-plan.md не переносится поверх общего. Кандидат основного плана формирует Kit из актуального main. Конфигурация/установленные служебные файлы также не заменяются неявно.
7. Операции выдачи, принятия результата и интеграции становятся управляемыми командами Kit. Их CLI-имена пока не определены; обычный git merge не является готовой поддержкой этого контракта.

Фазы и назначения — в локальном runtime-журнале без копии плана. Итоги проверяются по Kit/Git. Частичное создание восстанавливается по ID без дубликатов.

Документы в main правятся через Kit между интеграциями; незакоммиченное не прячется/удаляется ради merge.

## 6. Worktree и интеграция в main

Worktree создаются в управляемом каталоге вне основного checkout. Проверяются realpath, принадлежность Git, занятые пути, symlink и уникальность ветки. Чужие папки и изменения не трогаются. Автоудаление веток/worktree не входит в первую версию.

Перед выдачей задания проверяется окружение для его verification_ids. Для Node-проекта без зависимостей допускается явный штатный шаг npm ci по package-lock.json в этом worktree; при невозможности — NEEDS_SETUP без запуска агента. Не создавать symlink и не копировать node_modules из main. Аналогично проверять нужные игнорируемые генерируемые ресурсы, создаваемые штатными pre-скриптами.

Хранилище Git общее, рабочие файлы/index отдельные. Lock и transaction исполнителя используют git-dir его worktree; очередь main отдельная и единственная. Hooks не должны перенастраивать соседние деревья. Используются существующие Git/Node обеих ОС.

Порядок интеграции:

1. Проверить назначение, точный source SHA, происхождение от базы, допустимые файлы, отсутствие посторонних коммитов и успешные проверки.
2. Поставить готовый результат в очередь. Предложение: время готовности, при равенстве — порядок плана; не ждать более раннюю неготовую независимую задачу.
3. Заблокировать записи в main; проверить HEAD, чистоту staged/unstaged/untracked, отсутствие другой Git-операции/транзакции.
4. Подготовить управляемый merge без финального коммита. Служебный план исполнителя заменить кандидатом общего плана по явному правилу Kit. Исходники не разрешать произвольным ours/theirs.
5. Проверить фактический diff и выполнить назначенные проверки объединённого кандидата.
6. Только при успехе создать интеграционный merge-коммит и подтвердить DONE родительской задачи. Повтор операции не создаёт второго коммита.
7. Сохранить доказательства, освободить main и запустить готовые зависимые задачи от нового HEAD.

Дочерний implementation-коммит остаётся однородительским; интеграция получает отдельную роль и проверку двух родителей. Нельзя просто отключить существующий HISTORY_NOT_LINEAR, hooks или проверку происхождения зависимостей.

Source SHA известен заранее и записывается в состояние. Integration SHA восстанавливается по уникальным trailers операции; записать собственный хеш внутрь самого коммита невозможно. В проекции доступны оба SHA.

При конфликте/провале проверок main занят незавершённой интеграцией, задача не DONE, следующего merge нет. В панели плана появляется «Передать исправление основному агенту». По нажатию Web Pilot доставляет основной сессии планировщика одно поручение с ID интеграции, main cwd, конфликтами/проверками и командами Kit. На время исправления эта сессия исполняет роль агента исправления; остальные записи main заблокированы. После исправления Kit повторяет проверки и завершает ту же интеграцию одним merge-коммитом. UNKNOWN доставки не повторяется автоматически. Расширение требований возвращается пользователю/планировщику.

После сбоя сначала сверяются HEAD, журнал, планы, сессии. Неизвестный исход останавливает интеграцию, не запускает её повторно. Отмена затрагивает лишь собственную операцию с сохранением работы; автоматических reset --hard, массовой очистки и переписывания main нет. Независимые уже запущенные исполнители могут завершить свои ветки.

## 7. Запуск и AutoPlan

Разрешение в Settings само ничего не запускает. Нужны разрешённое выполнение и опубликованный план; Review ON остаётся gate. Перед любым запуском приложение сверяет parallel_allowed/max_workers с сохранённым снимком основной сессии происхождения плана. Связь — метаданные происхождения, не owner_session_id и не владение планом; выбранный чат для сравнения не используется. Несовпадение или неизвестный снимок блокирует запуск с видимой причиной. Старый ACTIVE продолжает собственный подтверждённый снимок.

В панели плана кнопка «Выполнить доступные задачи» выдаёт одну доступную группу через узкий IPC с assertLocalSender-подобной проверкой; повторный клик не дублирует назначения. AutoPlan ON разрешает последующие автоматические назначения и продолжения. OFF прекращает новые автоматические отправки/запуски; уже начатые команды и безопасное завершение Git-транзакции не прерываются. Ручное продолжение проходит те же проверки.

Существующая кнопка AutoPlan независима от фиксированного снимка разрешения параллельности. Её состояние не передаётся агенту текстом и агент ею не управляет. После подтверждённого коммита продолжения исполнителю прекращаются; интеграция ждёт конца его ответа и отсутствия активной команды.

Лимит учитывает занятые назначения, включая ожидание пользователя/восстановления. Готовый и остановившийся исполнитель освобождает место; исключительная задача ждёт также интеграции ранее выданного. Неизвестный исход не освобождает слот для дубликата того же задания.

## 8. Живые сессии и возможность будущего detach

Каждая активная сессия имеет собственные WebContentsView, PageState, Composer, доставку, таймер и восстановление. Используется штатный общий профиль входа ChatGPT. Переключение отображения не загружает другой URL поверх работающего чата.

**Сессия существует независимо от окна-представления.** Её жизненным циклом и выполнением владеет контроллер сессии на уровне приложения; основное окно лишь показывает выбранную страницу. Идентификаторы, cwd, наблюдатели и очередь не зависят от выбранной/активной BaseWindow.

Сегодня нужны реестр живых сессий и показ/скрытие; универсальная система окон не нужна.

Будущий detach перемещает ту же сессию в другое окно без нового чата/Send/агента и потери таймера/подписки. Страница показана в одном месте. Закрытие представления не равно завершению сессии.

В текущем объёме **нет** кнопок detach/attach, дополнительных окон сессий, сохранения их геометрии и автоматизации окон. Достаточно не связывать контроллер с главным окном и проверить, что скрытие/смена места представления не уничтожает сессию. Политика будущего закрытия detached-окон определяется в отдельной задаче.

События: session/worktree/task и проверенный WebContents/mainFrame. Узкие IPC, защита renderer и контракт Web Pilot Sidebar сохраняются.

Наблюдение событийное, без polling в простое. Смена выбора не уничтожает webContents. Завершённые страницы можно освобождать, облачные чаты сохраняются.

## 9. Сайдбар и время

Под проектом — основная сессия и группа «Исполнители». Это связь для отображения/доставки, не владение планом. Исполнители не становятся отдельными проектами списка.

Строка содержит ID/название задачи, отметку «Отдельный worktree», состояние и время. Цвет дополнительный. Клик открывает реальный чат; можно читать сообщения и доступные tool calls, ответить на вопрос. Существующая настройка скрытия вызовов сохраняется; собственную копию полного лога беседы не создаём.

Состояния: ожидает зависимостей; в очереди; запускается; работает; ожидает ответа/восстановления; готово к слиянию; интегрируется; требует вмешательства; завершено.

Idle сам по себе не означает вопрос пользователя. Для «ожидает ответа» нужен явный статус Kit или подтверждённый UI-сигнал; иначе «Пауза, состояние уточняется». Модельный классификатор текста не вводится.

Наблюдаемое время работы и ожидание различаются. Переключение/перезапуск не обнуляют накопленное время. За закрытое приложение активность не выдумывается: неизвестный интервал так и обозначается.

## 10. Восстановление

Сохраняются sending до Send, sent после, UNKNOWN без автоматического повторного Send; защита черновика/ручного Stop и отбрасывание поздних событий чужой навигации. У каждой сессии свои ключи.

Проверено по src/conversation-recovery.mjs: распознанная ошибка связи допускает одну безопасную перезагрузку того же чата через 3 секунды, без повторного задания/генерации. Обнаруженный HTTP 429 задаёт паузу 60–300 секунд, затем ручной повтор. Механизм применяется отдельно к сессиям без бесконечного retry.

Заблокированный OpenAI до выполнения tool call агент повторяет один раз без изменения. Неизвестный исход команды требует проверки результата. Долгие команды — exec session/write_stdin, без &/nohup.

После restart сверяются снимки/назначения/Git/Kit и подключаются существующие чаты без дубликатов. Ошибка блокирует исполнителя и зависимые задачи.

Сбои разбираются по фактам; в диагностике ID/фазы/время/ошибки/SHA, без секретов и текста беседы.

## 11. Приёмка

Критерии T010/T011 черновика покрывают Settings, два независимых исполнителя, зависимую/исключительную задачи, последовательный merge, реальные зависимости окружения и путь «конфликт → исправление → проверки → DONE». Автотесты используют временные Git-репозитории и Electron TEST FIXTURE; живой ChatGPT, native Windows и чистая установка проверяются пользователем. Detach не реализуется.
