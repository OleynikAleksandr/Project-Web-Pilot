## 1. Кнопки и индикация Review
Обе независимые кнопки имеют одинаковое зелёное оформление при aria-pressed=true и обычное при false в светлой и тёмной темах. Названия действий явно говорят «Включить…»/«Выключить…», состояние доступно экранному диктору. Переключение сохраняет существующие IPC-проверки и источники настроек; перезапуск восстанавливает оба состояния.

Слева от текста Review компактный декоративный индикатор. RUNNING показывает спиннер выполнения Claude; PUBLISHING — публикации. PREPARED и AUTHOR_PENDING сами по себе не доказывают работу: без подтверждённой активности статический знак ожидания. AGREED/PUBLISHED — статический успех. NEEDS_USER, STALE, ошибка чтения/уборки/доставки — статическое внимание. IDLE/CANCELLED без ошибки не анимируются; при OFF не показывать фиктивную активность. При prefers-reduced-motion анимация отключена, текст сохраняет смысл. Текст статуса остаётся role=status, декоративный знак aria-hidden. Общий редизайн не требуется.

## 2. Восстановление текущей страницы
Живость RUNNING проверяется при refresh через штатный reviewStatus; отсутствующий/потерянный runner даёт статическое внимание. Пока RUNNING, допустим ограниченный watchdog до дедлайна запуска, чтобы при гибели процесса без файлового события спиннер не оставался бесконечным. Вне RUNNING опросов нет. Проверить потерю runner, restart и прекращение watchdog. src/main.mjs передаёт состояние ошибки доставки/паузы для правильного статического индикатора.

STALL_WARNING и отсутствие видимых изменений не являются ошибкой связи и не открывают блок восстановления. Работающий Review продолжает показывать собственный актуальный статус. Обнаруженный connectionError сохраняет существующий безопасный путь восстановления.
Кнопка: «Перезагрузить страницу чата». Причина в тексте — обнаруженная ошибка страницы/соединения, не предположение по времени. Пояснение: перезагружается текущая страница, новый чат не создаётся, сообщение повторно не отправляется.
Сохранить защиту draft, неопределённого Send, неподтверждённого URL, смены проекта/чата, manual Stop и rate limit/cooldown. Не вводить автоматических повторных отправок. Проверить отсутствие нового чата и send в обработчике reload.

## 3. Получатель автоматического продолжения
У одного checkout по-прежнему один current plan. Session ID — адресат доставки, не владелец плана и не выбор плана.
Проследить полный путь startup Session ID → обычная подготовка scope/review → state.json → ReviewContinuation. Использовать явный ID из входа/метаданных подготовляемого плана с проверкой совпадения, не угадывать по выбранному сейчас чату, времени или последней сессии. Полная стандартная форма и recovery/help должны делать передачу однозначной; противоречивые ID отклонять до запуска. Вне Web Pilot допустим явно описанный ручной режим без автоматической доставки.
Продолжение текущего run сохраняет получателя; смена получателя требует явного подхвата пользователем. Не назначать чужой чат при переключении панели. Старые данные без ID не переписывать догадками.
Другой ID продолжающегося run без явного recipient_change_note с решением пользователя отклоняется с REVIEW_RECIPIENT. Этот узкий вход сохраняет поручение пользователя о подхвате; агент не придумывает его. Проверить отказ обычной замены и успешный явный подхват вместе с защитой от отправки прежнему/чужому адресату.
Точный вход: recipient_session_id верхнего уровня либо явно заданный scope.session_id; при наличии обоих они должны совпадать. Новый цикл без ID отклоняется. Вне Web Pilot нужен явный recipient_mode: manual без ID. Следующие раунды наследуют адресата; смена в том числе из старого null требует recipient_change_note. State хранит текущего адресата и последнее разрешение подхвата, без создания отдельного плана для чата. Перед самой отправкой повторно сверяются сохранённые run, generation, получатель и выбранный checkout/чат.
Проверить паузу между раундами, restart с сохранённым state/checkpoint, draft/Stop/UNKNOWN, дубли событий и выбор другого чата/checkout. Обычная подготовка и реальный обработчик продолжения проверяются вместе на временном проекте.

## 4. Позиция автора после каждого отзыва
После чтения полного успешного отзыва сохранять краткую содержательную позицию отдельным файлом данного run: номер раунда, что принято/отклонено и почему, оставшиеся разногласия, нужные исполнителю решения и где они отражены в спецификации/критериях. Это относится и к окончательному approved.
Предусмотреть штатную команду Kit для сохранения позиции без создания нового раунда, привязанную к текущему отзыву и хешам проверенной пары. Publication при ON не пропускает отсутствующую/устаревшую позицию либо существенное авторское разногласие. OFF сохраняет обычный порядок публикации. Не добавлять инфраструктуру подписей или арбитража.
Если документы не менялись и существенного спора нет, сохранить позицию и публиковать с имеющимся одобрением. При содержательном изменении проверенных документов прежнее согласие недостаточно: подготовить актуальную пару и новое ревью. Не считать позицию автора согласием рецензента на изменённые документы.
Существенные результаты обсуждения переносятся в публикуемые документы до окончательного согласования. Одной ссылки на удаляемый runtime недостаточно. Обновить инструкции CLI, recovery и автоматического продолжения. Проверить полный путь prepare/run/позиция/publish/task:start; fake CLI обозначать явно.
Исключение по явному решению пользователя: после NEEDS_USER команда review:resolve --action publish с записанным note разрешает публикацию без согласия рецензента или при сохранённом существенном споре. Это разрешение публикации, а не утверждение о снятии спора. Если на текущую пару есть успешный отзыв, содержательная позиция на него остаётся обязательной. Если успешного отзыва на текущую пару нет из-за ошибки Claude, позиция не требуется; сохранённое решение пользователя описывает основание публикации. Актуальность входов и SHA проверяется в обоих случаях. Тесты: ошибка без отзыва → resolve publish → публикация; успешный отзыв и спор в позиции → отказ без решения → публикация после решения; отсутствующая позиция при успешном отзыве всё ещё блокирует публикацию.
Ошибка Claude и неразрешённый существенный спор требуют вопроса пользователю. Очистка по фактическому первому task:start удаляет только связанный run, сохраняя опубликованные документы и посторонние папки.

## Пользовательская приёмка после выпуска
Пользователь сам полностью закрывает и запускает установленное приложение.
1. Переключить обе кнопки во всех четырёх сочетаниях, проверить зелёный ON и восстановление после перезапуска.
2. На новом временном проекте включить Review и выключить автовыполнение: при реальном Claude видны текст и спиннер; длительное ожидание не выдаёт ошибку связи; после согласования статический успех.
3. Прервать ход между раундами безопасным завершением ответа (не кнопкой Stop), проверить продолжение в правильном чате и после перезапуска; другой чат не получает сообщение. Manual Stop остаётся запретом автопродолжения.
4. Проверить позицию окончательного раунда и сохранённые решения в опубликованной спецификации; после первой задачи удалён только свой runtime.
5. При реально обнаруженной ошибке страницы проверить название и пояснение reload; черновик и неопределённая отправка защищены, новый чат и повторное сообщение не возникают.
