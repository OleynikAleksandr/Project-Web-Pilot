## Результат

Режим «Автовыполнение» принадлежит только клиенту Project Web Pilot. Агент не включает его, не выключает его и не сообщает Web Pilot, можно ли продолжать, специальными строками в ответе.

Единственное автоматическое сообщение, которое Web Pilot вправе отправлять в ChatGPT от имени пользователя, — точное слово:

`Продолжай`

Переключатель можно включить или выключить в любой момент. Сам переключатель не отправляет агенту стартовую инструкцию и не меняет его prompt. Если режим включён, Web Pilot событийно ждёт паузу в выбранном разговоре. При подходящей паузе и незавершённом current plan он отправляет ровно одно `Продолжай`. Если режим включили уже во время существующей паузы, эта пауза сразу должна привести к одному `Продолжай`.

Нормальная работа агента не зависит от положения переключателя: одна микрозадача, проверка, Workflow Kit commit, короткий отчёт и завершение ответа. Это общее правило сессии/Workflow Kit, а не временная AutoPlan-инструкция.

## Подтверждённый дефект 0.6.76

Живая сессия проекта `/Users/oleksandroliinyk/VSCODE/01TestAuto` 02.10.2026 воспроизвела архитектурную ошибку.

Факты:

- `autoPlanEnabled=true`;
- Workflow Kit корректно создал scope `auto-execution-test-001`;
- T001 завершена и подтверждена commit `ee6a98c`;
- после T001 план ACTIVE, следующая задача T002;
- AutoPlan не отправил `Продолжай`.

Диагностика показывает два связанных дефекта текущей state machine:

1. После появления нового ACTIVE-плана AutoPlan восстановился поверх уже идущего обычного ответа агента, который не получал AutoPlan-инструкцию. Ответ завершился без footer-сигнала и был ошибочно трактован как `NO_CHECKPOINT`.
2. `NO_CHECKPOINT` создаёт липкую паузу без `resumeOnMessage`: переключатель остаётся визуально включённым, но `run` уничтожается. Следующее ручное сообщение пользователя не оживляет цикл. Позднее окончание T001 было корректно видно странице, но AutoPlan уже не наблюдал turn.

Причина — неверное владение автоматизацией: клиент зависел от текстовых footer-сигналов агента (`Готов продолжать.`, `Нужен ваш ответ.`, `План завершён.`) и от отдельной стартовой AutoPlan-инструкции.

## Новый контракт

### 1. Агент не управляет AutoPlan

Удалить из AutoPlan весь управляющий текст для агента:

- не отправлять `AUTO_PLAN_INSTRUCTION` при включении режима;
- не требовать footer `Готов продолжать.`;
- не трактовать `Нужен ваш ответ.` как управляющий сигнал;
- не трактовать `План завершён.` как управляющий сигнал;
- AutoPlan не должен читать смысл текста ответа для решения о продолжении.

Если footer-парсер больше нигде не нужен, удалить `turnSignal` из observer/page-state/diagnostics и соответствующие тесты как устаревший протокол.

### 2. Обычное правило работы агента независимо от AutoPlan

Стартовый контекст обычной Web Pilot session должен один раз закреплять общее правило:

- за один ответ выполнять не более одной микрозадачи;
- перед реализацией использовать `task:start`;
- завершать микрозадачу проверкой и `commit --task`;
- после commit кратко отчитаться и закончить ответ;
- если микрозадача ещё не закончена, допустимо завершить ответ на безопасной контрольной точке; следующее `Продолжай` продолжает фактическую текущую работу.

В этом тексте не должно быть слов о положении AutoPlan, footer-сигналах или обязанности агента решать, будет ли следующий turn.

### 3. Единственный источник решения — клиент + Workflow Kit + состояние страницы

Web Pilot событийно выполняет reconcile при:

- включении/выключении переключателя;
- изменении выбранного проекта/сессии;
- загрузке/reload документа ChatGPT;
- изменении `busy`/готовности composer;
- ручной отправке пользователя;
- семантическом изменении current plan от PlanMonitor.

Автоматическое `Продолжай` допустимо, только если одновременно:

- AutoPlan включён;
- выбранный разговор совпадает с выбранной сессией;
- страница доступна, editor готов, нет connection error;
- ChatGPT сейчас не busy;
- пользовательский draft не должен быть затёрт;
- current plan подтверждён: нет незавершённой Workflow Kit transaction и чтение плана стабильно;
- scope ACTIVE;
- в плане есть незавершённая работа.

Факт footer-текста агента не входит в условия.

### 4. Что считается паузой

Для AutoPlan пауза — это доступное idle-состояние выбранного разговора при незавершённом ACTIVE-плане.

Пауза может возникнуть:

- после окончания ответа агента;
- после ручного Stop;
- после reload/повторного открытия разговора;
- уже существовать в момент включения кнопки;
- возникнуть потому, что AutoPlan был ON ещё до появления current plan, а план стал ACTIVE после обычного ответа агента.

Если AutoPlan ON и пауза подходит под условия выше, отправляется ровно одно `Продолжай`.

Нормальная граница — завершённая микрозадача с DONE+commit. Но AutoPlan не обязан требовать новый DONE, чтобы продолжить незавершённую микрозадачу: если агент остановился на безопасной точке, `Продолжай` продолжает ту же фактическую работу.

### 5. Семантика переключателя

- OFF: Web Pilot ничего автоматически не отправляет.
- OFF → ON во время busy: ничего не отправлять немедленно; дождаться первой подходящей паузы и отправить одно `Продолжай`.
- OFF → ON во время уже существующей подходящей паузы: эта пауза сразу приводит к одному `Продолжай`.
- ON → OFF: прекратить будущие автоматические отправки; уже подтверждённый Send не повторять и не пытаться «отменить».
- ON сохраняется между reload/restart как пользовательский выбор.
- Завершение плана не выключает кнопку; для полностью DONE плана просто нет действия.
- Появление нового ACTIVE-плана при уже включённой кнопке автоматически активирует reconcile; отдельного выключения/включения не требуется.

### 6. Ровно одна отправка на паузу

Нужна машинная идентичность паузы, не зависящая от текста ответа.

Предпочтительная основа:

- ключ выбранного контекста: workspace + sessionId + scopeId + chatUrl;
- стабильный opaque `turnId` последнего assistant turn, если он существует;
- для idle-состояния без assistant turn — детерминированный synthetic pause identity из наблюдаемого состояния страницы и plan revision.

Сохранённый checkpoint должен означать только судьбу автоматической отправки `Продолжай` для конкретной паузы: `sending` или `sent`.

Повторные page observations, PlanMonitor events, reload и повторный reconcile не имеют права отправить второе `Продолжай` для той же паузы. Новый assistant turn или другая действительно новая пауза создают новую identity.

### 7. Пользовательское сообщение и draft

Пользователь всегда имеет приоритет над автоматизацией.

- Web Pilot не стирает и не заменяет draft.
- Пока draft присутствует, автоматический Send ждёт.
- Ручная отправка пользователя считается использованием текущей паузы: Web Pilot ждёт ответ на это сообщение и не вставляет дополнительное `Продолжай` рядом с ним.
- После окончания нового ответа, если AutoPlan всё ещё ON и план не завершён, возникает следующая пауза и обычное правило применяется снова.

Не требуется специальное «возобновление по footer» или сохранённый agent signal.

### 8. Временная недоступность не превращается в липкую паузу

Следующие состояния — техническое ожидание, а не выключение цикла:

- plan ещё NONE или только создаётся;
- Workflow Kit transaction временно не подтверждена;
- page reload;
- composer временно недоступен;
- connection error;
- draft;
- busy-turn.

При следующем релевантном событии Web Pilot сам выполняет reconcile. Пользователь не обязан передёргивать переключатель.

Для неопределённого исхода самого Send действует прежнее правило безопасности: тот же Send вслепую не повторять. Но это блокирует только конкретную pause identity, а не весь AutoPlan навсегда.

## Событийная архитектура

Новый AutoPlan не должен добавлять Git polling.

PlanMonitor уже наблюдает current plan и сообщает semantic change. Его событие должно будить AutoPlan reconcile. PageStateSource уже сообщает изменение страницы. Toggle также вызывает reconcile.

Таким образом:

`toggle / PlanMonitor / PageStateSource / selection → reconcile → inspect confirmed plan → dedupe pause → Composer.sendUserMessage("Продолжай")`

В AutoPlan не остаётся отдельного «start message» для агента.

## Обязательные регрессии

### Точный сценарий 01TestAuto

1. AutoPlan сохранён ON ещё до новой сессии.
2. Новый Chat стартует без current scope.
3. Пользователь обычным сообщением поручает создать план.
4. Пока агент отвечает, Workflow Kit меняется NONE → ACTIVE.
5. Web Pilot не вмешивается в busy-turn.
6. Обычный ответ агента заканчивается без любого специального footer.
7. Web Pilot видит idle + ACTIVE unfinished plan и отправляет ровно одно `Продолжай`.
8. Агент выполняет T001, делает commit и заканчивает обычным отчётом без footer.
9. Web Pilot отправляет следующее ровно одно `Продолжай`.

### Переключатель в любое время

Проверить отдельно:

- включение во время busy;
- включение во время уже существующей паузы;
- выключение во время busy;
- повторное включение во время той же паузы;
- включённое состояние после reload/restart;
- полностью завершённый plan.

### Защита от дублей

Проверить:

- несколько одинаковых DOM observation;
- одновременное событие PlanMonitor и завершение assistant turn;
- reload на той же паузе;
- checkpoint `sending` после restart;
- checkpoint `sent` после restart;
- ручное пользовательское сообщение в паузе;
- draft;
- connection error с последующим восстановлением.

Во всех случаях для одной pause identity допускается не более одного автоматического `Продолжай`.

## Реализация: удаление агентского протокола

Удалены стартовое AutoPlan-сообщение, разбор специальных строк ответа и поле `turnSignal` в observer, PageStateSource и diagnostics. Единственный текст автоматической отправки — `Продолжай`; обычное завершение ответа наблюдается без footer. Общий цикл одной микрозадачи с `task:start`, проверкой, `commit --task` и коротким отчётом закреплён в обычном startup-контексте независимо от переключателя. Добавлены регрессии для этого контракта, принятия уже работающего ответа и обычного ответа без footer. Событийный reconcile и восстановление технических ожиданий реализованы следующими T002/T003; результаты описаны ниже.

## Реализация: событийный пересмотр пауз

AutoPlan использует один последовательный `reconcile`, который пробуждают переключатель, PageStateSource, смена выбранного контекста, восстановление готовности страницы и семантическое изменение PlanMonitor. Во время busy план через Git не опрашивается; подходящий idle проверяется по подтверждённому ACTIVE-плану и повторно перед Send. NONE, временная ошибка чтения, transaction, connection error и недоступное поле ввода сохраняют включённый режим и пересматриваются по следующему событию. Периодический опрос Git не добавлен; watchdog только сообщает об отсутствии прогресса. Unit-регрессии включают NONE → ACTIVE во время обычного ответа, совпадающие события страницы и плана и защиту от устаревшего idle во время асинхронного чтения.

## Реализация: переключатель, checkpoint и пользовательский ввод

Идентичность ответа строится из машинного ID сообщения/контейнера, а при его отсутствии — из порядка сообщений; текст ответа не участвует. PageStateSource передаёт непрозрачный ID последнего пользовательского сообщения и роль последнего сообщения, поэтому ручная отправка ожидает нового ответа и после reload/restart. Сохранённые checkpoint версии 2 содержат только контекст, идентичность паузы и `sending`/`sent`; предыдущие паузы и другие разговоры сохраняются, старый одиночный формат читается. Подтверждённый Send сохраняется при OFF сразу после отправки; техническое ожидание и неизвестный Send не выключают пользовательский выбор. Sidebar использует машинный `STALL_WARNING`, а не текст сообщения. Добавлены проверки свежего процесса, старых и новых пауз, переключений, ручного ввода, Stop, ошибок сохранения и стабильности идентичности при изменении текста/замене DOM.

## Проверка: 01TestAuto и границы в Electron

Electron smoke воспроизводит сохранённый ON, новый Chat с NONE, создание ACTIVE-плана во время обычного busy-ответа, ровно одно точное «Продолжай» после idle и следующий обычный отчёт после настоящего task/start/commit. Используются sidebar IPC, реальный Composer, sandboxed preload, PlanMonitor и временный Git checkout. Проверяются Chat/Work, ON во время busy и idle, OFF во время busy и повторное ON, Stop с частичным ответом, сохранение draft, trusted ручной Send и reload, connection recovery без OFF/ON, watchdog, все DONE включая DOCS и совпадающие события без дубля. Fixture сохраняет роли, порядок и машинные ID сообщений через реальную навигацию.

Свежий Electron-процесс читает сохранённый выбор/checkpoint и реальный fixture-plan: busy, уже sent, interrupted sending и последнее ручное сообщение проходят reload без отправки. Interrupted sending моделируется только в отдельной копии fixture-settings. Установленный ProseMirror fixture адаптирован к обычным ответам без startup-инструкции и footer; packaged run прошёл в T005. Найденная проверками потеря trailing progress при быстром idle → busy исправлена: уведомление, уже назначенное реальным изменением текста, передаёт последнюю revision независимо от обновлённого idle timestamp. Unit закрепляет этот порядок; постоянный опрос не добавлен.
