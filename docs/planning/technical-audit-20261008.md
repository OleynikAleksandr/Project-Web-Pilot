# Технический аудит Project Web Pilot — спецификация

## Результат

Проверяемый реестр конкретных замечаний по сопровождаемости и надёжности всего поддерживаемого репозитория с минимальными предложениями исправления. Это исследование, не разрешение на исправления, удаление кода, изменение архитектуры или выпуск. Основной результат — `docs/planning/technical-audit-findings.md`, создаваемый при выполнении плана. При приближении к лимиту 28000 байт UTF-8 реестр делится на `docs/planning/technical-audit-findings-<направление>.md`; основной файл содержит матрицу, оглавление, сводку и ссылки на части.

## Область и базовая линия

Проверить `src/` (включая UI и preload), `packages/workflow-kit/` (источник Kit), `tools/codex-app-server-mcp/`, `scripts/`, исходные `resources/`, `tests/`, `docs/`, `README.md`, `AGENTS.md`, `package.json`, конфигурацию и сценарии запуска/упаковки macOS и Windows. Фиксировать HEAD и Git-состояние в начале, в отчёте отмечать изменение базовой линии. Не изучать как исходники `node_modules`, `.git`, `.harness/runtime`, генерируемый `resources/workflow-kit`, build outputs, пользовательские профили/архивы; проверять **правила** их генерации, исключения и включения в релиз. Действующая архитектура — `docs/architecture/OVERVIEW.md`; модульные контракты — `docs/modules/`.

Предварительная инвентаризация для планирования (не результаты аудита): исходники распределены между Electron-приложением, UI, исполняющими Python-инструментами, Workflow Kit, сборочными скриптами, ресурсами и тестами; имеются две платформы и публичный контракт трёх адаптерных модулей для Web Pilot Sidebar. Стартовые проверки: `git ls-files`, `rg`, просмотр импортов/экспортов, npm scripts и упаковочных правил; специализированные проверки при необходимости писать как временные read-only скрипты вне отслеживаемых файлов. Наличие похожего кода само по себе не является дефектом.

## Методика и доказательства

1. Составить матрицу охвата путей/подсистем и четырёх направлений с пометками проверено, исключено и ограничение. Начать с графа входов: `src/main.mjs`, preload, UI, workers, IPC, CLI и события, точки подключения Kit, запуск и упаковка двух ОС. Сохранить точные команды и результаты безопасных статических проверок.
2. Дублирование: сгруппировать повторные блоки, константы, схемы нормализации, проверки и правила документации. Для каждого кандидата сопоставить потребителей, семантику, историю и платформенные отличия. Предлагать объединение только при доказанном риске расхождения/двойном обслуживании и без новой ненужной связности. Тестовые примеры, независимые platform implementations и сгенерированные копии отличать явно.
3. Ссылки/подключения: извлечь Markdown/HTML ссылки и локальные anchors, import/export и динамические `import`, `require`, worker/resource пути, npm scripts и конфигурации. Проверить путь относительно источника, регистр на Windows/macOS, существование и экспортируемый символ; различать исходный файл, staging-generated и runtime-generated. Для упаковок сверить `asar`, `extra-resource`, `ignore` и generators, а не просто наличие файла в checkout. Исторические Git ссылки проверять в указанном commit/blob. Внешние URL — отдельный список со статусом «не подтверждено», «проверено», «недоступно по сети»; не запрашивать приватные адреса, коннекторы, учётные данные.
4. Неиспользуемое: выявить кандидатов анализом вызовов и входов исполнения, затем проверить динамические строки, IPC handlers, callbacks, событийные подписки, CLI, платформенные ветви, плагины и внешнего потребителя Sidebar. Отрицательный `rg` или сканер — только индикатор, не доказательство. Любые удаления — исключительно отдельное будущее решение.
5. Ошибки/жизненный цикл: проследить типовые цепочки от пользовательского события до фактического результата, promise rejection, границы try/catch, подтверждение успеха, abort/timeouts, создание/освобождение таймеров, слушателей, watcher и child processes. Разобрать гонки смены проекта/чата, навигации, закрытия окна, перезапуска, неизвестного исхода Send/операции. Постоянные службы, специально отделённые от окна, не считать утечкой. Где безопасно — использовать существующие unit/fixture-тесты без реальных чатов, инфраструктуры и изменения состояния; иначе указывать статическое доказательство и предел уверенности.
6. Для каждого замечания подтвердить достижимый путь выполнения или точный конфликт контрактов и оценить вероятность/последствие. При отсутствии доказательств оставить гипотезу; не выдавать косметику за баг. Рассматривать минимальную правку без массового рефакторинга.

## Формат отчёта

Три раздела: A) подтверждённые дефекты; B) кандидаты на упрощение; C) неподтверждённые гипотезы/ограничения. У каждой записи уникальный ID; направление; файл и строка/символ; затронутый сценарий; факт и воспроизведение (команда/тест/трасса/лог без секретов); последствия; серьёзность `critical/high/medium/low` и обоснование; точечное исправление; способ верификации после исправления; риски для macOS, Windows, Workflow Kit, Sidebar и публичных контрактов; статус уверенности. Для низкой уверенности явно указать, что требуется для подтверждения. В отдельной матрице показать проверенный охват и пробелы каждого направления, даже если находок нет. Заключение — приоритизированный краткий список рекомендуемых **отдельных** работ, без их реализации.

## Критерии приёмки аудита

- Все поддерживаемые исходные подсистемы отражены в матрице; исключения и метод проверки реальных точек входа зафиксированы.
- Во всех четырёх направлениях есть метод, проверяемый охват, результат или явное отсутствие подтверждений, ограничения.
- Каждое подтверждённое утверждение имеет локализованное доказательство; гипотезы не смешаны с фактами.
- Нет правок исходников, удаления ресурсов, новых runtime-зависимостей, сборки/подписания/релиза, установки, публикации или разрушительных действий.
- Windows и чистая установка не заявляются проверенными без испытаний пользователем; статические платформенные выводы обозначены как таковые.
- Отчёт не обязывает выполнять предложенные исправления; их объём пользователь утвердит отдельно.

## Правила исполнения

Планирование сейчас включает только подготовку и публикацию этого плана. Реальный аудит запускается только по следующему поручению. Исполнение аудита следует Workflow Kit: одна задача — один подтверждённый commit, с установленным task:start и разрешёнными проверками. Временные проверочные скрипты и выводы хранить в системном tmpdir **вне checkout**, не в проекте; `commit --task` выполнять с явным `--files` только для документов реестра. Для отчётов допустимы безопасные read-only команды, unit/fixture проверки, не меняющие пользовательские данные; перед запуском изучить побочные эффекты. В конце сравнить `git diff --name-only <исходный HEAD>..HEAD` с разрешёнными `docs/planning/technical-audit-*`, отдельно перечислить любые внешние изменения и убедиться в отсутствии непредусмотренных staged/unstaged/untracked изменений. Не управлять UI, не запускать моделирующих агентов или внешние модельные API для реализации, не трогать соседние репозитории. Review ON — только согласование плана через Kit. Никакого delivery-хвоста: новая версия не запрошена.
