# Workflow Kit: документация и восстановление по плану и Git

## Результат
Поручение 06.10.2026: подготовить спецификацию и to-do. Документ заменяет исследовательские границы scope; реализация, выпуск и миграция запланированы на следующие задачи.
Kit изменяется в packages/workflow-kit внутри Project Web Pilot. Поведение одинаково для macOS и Windows; контракты Sidebar сохраняются. 

## Минимальные документы
Документы описывают устройство и требования; ход выполнения сохраняют план, Git и evidence.
- Архитектура: назначение, модули, связи, ограничения, запуск, короткая навигация; до 3000 символов.
- Спецификация модуля: ответственность, поведение, зависимости и критерии; до 8000.
- Контракт фасада: входы, выходы, ошибки и порядок вызова; обычно раздел спецификации. Самостоятельный общий контракт — до 4000.
- Рабочая спецификация scope: результат, изменения, границы и критерии; до 6000. Спецификация нового модуля может одновременно служить планировочным документом.
- To-do: задачи, зависимости, проверки, ссылки на требования и коммиты; ориентир до 700 символов описания задачи без машинных полей.
Пределы — предложение для первой реализации, в Unicode-символах с пробелами. Байты/токены считать отдельно; текст не обрезать и не дробить ради допуска. Объём растёт при новых самостоятельных модулях, не от числа релизов. Устаревшее заменяется, история и дубли не добавляются. Причины важных решений сохраняются кратко рядом с решением.

## Жизненный цикл
Обсуждение/исследование не требует to-do; спецификацию можно готовить отдельно. Наличие плана не разрешает выполнять его вместо обсуждения. Один активный план на checkout; стадии выбираются по поручению пользователя.
Реализация: микрозадача, проверка, управляемый коммит с состоянием плана. Причины решений и ограничения — в задаче/коммите. Незавершённое не помечается DONE.
Полная актуализация действующей документации — перед релизом, с фиксацией до сборки. Между релизами документация описывает последний выпуск; рабочая спецификация, план и Git — текущие изменения. Обязательная DOCS после каждого исследования/нерелизного плана убирается.
Итоги временной спецификации переносятся в действующий контракт при подготовке релиза; временный файл удаляется коммитом без архивной копии. План сохраняет точную Git-ссылку на использованную версию. Отложенные требования не удаляются как завершённые. Сам scope архивируется только по прямому поручению.

## Recovery
Сборщик читает целые документы по списку; модели и пересказа нет.
Общее ядро: короткие инструкции, архитектура с навигацией, точный workspace и свежая сводка Git/незавершённой транзакции.
ACTIVE: добавить целиком to-do, рабочую спецификацию и необходимые источники, выбранные агентом и сохранённые в плане. Общие файлы не дублировать. Агент восстанавливает работу по коммитам и диффам выполненных шагов, проверяет незакоммиченные изменения.
NONE: общие документы и точный указатель на последний закрытый план, его спецификацию в Git и коммиты. Агент читает их перед обсуждением нового scope. Для нового проекта отсутствие прежнего плана нормально.
Дополнительные документы и формы этапов агент получает по необходимости; отдельного recovery-документа не создаёт. Ссылки разрешаются по scope/task и подтверждённым SHA, не только commit message. Удалённая спецификация читается из Git. Все исторические диффы автоматически в старт не включаются.
Размеры файлов/пакета проверяются до отправки, единицы явно обозначены. Превышение бюджета или отсутствие обязательного источника — ошибка без скрытого усечения. Сохраняются контроль свежести, защита приватных путей и посторонних изменений.
Web Pilot отправляет текст; превращение в attachment допустимо. Разрешить чтение полученного вложения и убрать противоречие «без инструментов». Модельные API, обязательные кнопки режимов и классификатор не добавляются.

## Последовательность
T001 — зафиксировать исследование, эту спецификацию и to-do.
T002 — правила, формы и gates Kit: минимальная документация, docs перед релизом, Git-восстановление, работа с отдельной спецификацией, переходы фаз и лимиты. Проверить готовые решения и переиспользовать имеющиеся механизмы.
T003 — сборщик общего/активного recovery, ссылки на планы/спецификации/коммиты, дедупликация и диагностика.
T004 — согласовать Web Pilot, кеш, startup и AutoPlan; подготовить версии и проверки выпуска без сборки.
DOCS — документы изменённого Kit перед выпуском. Массовую ревизию старых документов проекта ещё не выполнять.
T005 — парная сборка Project Web Pilot с новым Kit.
T006 — установка и проверка нового выпуска.
T007 — публикация и сверка GitHub; затем управляемое добавление фазы миграции новым Kit.
После T007 добавить T008 «Привести документы к новой модели» (зависимость T007): сохранить существенные требования, убрать повторы/историю/завершённые временные файлы, исправить ссылки и источники recovery. Затем T009 «Проверить восстановление новой сессии» (зависимость T008): правила, дерево документов и пакеты ACTIVE/NONE согласованы; код/релиз при этой миграции не меняются.
Kit 1.5.6 запрещает обычные задачи после delivery. T002 должен обеспечить последующее добавление T008–T009 штатно, с сохранением DONE и hooks. Не маскировать миграцию под delivery. До T009 переход не объявляется завершённым.

## Проверка результата
Фикстуры: ACTIVE после части коммитов; NONE после закрытия; новый проект; незавершённая транзакция и чужие изменения; удалённая спецификация в Git; отсутствующий источник, дубли и превышение размера. Выбранные документы передаются полностью по одному разу.
Проверить исследование без фиктивного плана, DOCS до явной сборки, продолжение плана после обновления Kit и повторный безопасный запуск миграции.
Нативную Windows и живую новую сессию проверяет пользователь; fixture/smoke/сборка не заменяют приёмку. Агент не управляет UI/VM и не запускает других агентов.
Итог: установленный Kit, действующие документы и стартовый контекст соответствуют друг другу; дальнейшая работа не накапливает историю в спецификациях.
