# Workflow Kit: компактные документы и восстановление контекста

## 0. Решение и границы
Согласовано пользователем 06.10.2026 по ревью С1–С15, П1–П13 и ответу автора ревью. Kit развивается в packages/workflow-kit репозитория Project Web Pilot. Сценарий одинаков для macOS и Windows; публичный контракт внешнего Web Pilot Sidebar сохраняется.
Этот документ определяет целевое поведение. [Переход и проверка](workflow-kit-context-transition.md) — обязательная вторая часть спецификации. До перехода выполняется установленный Kit 1.5.6; новые правила не применяются задним числом.
Один активный план на checkout/worktree. Обсуждение, исследование и отдельная спецификация не требуют фиктивного to-do. Наличие активного плана само по себе не разрешает его выполнять вместо текущего поручения пользователя. План закрывается только по команде пользователя на архивирование; эта команда означает приёмку. Замечания до неё выполняются раундом того же плана.

## 1. Документы: назначение, содержание, срок жизни (С1, С8)
Документы предназначены для продолжения работы: текущее устройство, требования, ограничения и краткие причины действующих решений. Ход разработки восстанавливается по плану, коммитам и диффам. История выпусков и повторяющиеся отчёты в документах не накапливаются.
- AGENTS.md: постоянные проектные ограничения и управляемое указание Kit для прямых клиентов.
- docs/architecture/OVERVIEW.md: назначение, короткая архитектура, карта модулей со ссылками, связи, ограничения, запуск. Навигация вместо отдельного индекса.
- docs/modules/*.md: ответственность модуля, актуальное поведение, зависимости, проверки и существенные причины решений. Контракт фасада: входы, выходы, ошибки, порядок вызовов; самостоятельный документ только для отдельного общего контракта.
- docs/planning/*.md: невыпущенные рабочие спецификации — результат, изменения, границы и критерии. Спецификация нового модуля может служить рабочей спецификацией. Агент выбирает нужные источники и записывает их в context_pack.
- README.md: пользовательское назначение, версия, установка, запуск; без статуса сборки или публикации, ссылок на конкретный релиз и хешей — они в release-manifest.json и GitHub Release. Отдельного changelog нет.
- .harness/plans/todo-plan.md: задачи, причины, зависимости, критерии, проверки и ссылки на коммиты; единственный текущий план, без отдельного TODO/recovery-файла.

Полная актуализация действующих документов — перед каждым новым выпуском, с фиксацией до сборки. Между выпусками канонические документы описывают последний выпуск; рабочие спецификации, план и Git показывают изменения. Обязательная DOCS в плане без delivery не добавляется.
При DOCS выпуска действующие результаты временных спецификаций переносятся в модульные контракты; завершённые временные документы удаляются обычным коммитом без архивных копий. Невыпущенные и отложенные требования не удаляются как выполненные. Точная версия удалённого required-документа сохраняется ссылкой в Git (раздел 5).

| Прежний документ | Целевое место существенного содержания |
|---|---|
| MODULES, DOCUMENTATION_INDEX | OVERVIEW с картой модулей и ссылками; прежние файлы удалить |
| WORKFLOW_START, PRODUCT | README и OVERVIEW; прежние файлы удалить |
| ARCHITECTURE, DECISIONS | Текущие спецификации модулей, причины рядом с решением; прежние файлы удалить |
| CONTEXT_DELIVERY, WORKSPACE_SETUP, PROJECT_ARCHIVE | Соответствующие спецификации в docs/modules/, без истории |
| RELEASE | Короткая процедура в docs/modules/release.md либо AGENTS.md; журнал выпусков удалить |
| VERIFICATION | Команды в workflow.json и тестах, живые проверки в спецификациях модулей; файл удалить |
| CLEAN_INSTALL, TRANSFER_TO_WINDOWS | Установка в README, протокол проверки в модуле первого запуска |
| SOURCE_WORKSPACES | Короткие постоянные ограничения в AGENTS.md |
| docs/design, docs/research, *.history-*.md, выпущенные docs/planning/* | Действующее перенести, затем удалить без копий |

Удаление выполняется только после переноса существенного содержания. Факты выпуска, assets, статусы и хеши хранятся в release-manifest.json и GitHub Release; описательные документы не превращаются в журнал. Временное исключение для текущей спецификации указано во второй части.

## 2. Один предел и проверка коммита (С2)
Единственный числовой норматив — budget.document_bytes в .harness/workflow.json, по умолчанию 28000 байт UTF-8. Он задаёт предел каждого документа агента, README, любого изменяемого .md, включая файлы Kit, и каждой части стартового пакета вместе со служебными заголовками. Прежние нормативы в символах не используются ни в спецификации, ни в шаблонах.
Основание — тест 06.10.2026: файл 50000 байт плотного русского текста, 50 контрольных меток. Чтения порциями 20000 и 30000 байт сохранили все метки и сумму 292647. При 40000 байт внешний вывод ChatGPT с бюджетом по умолчанию 10000 токенов вырезал середину («102 tokens truncated»), M21 не дошла. Это свойство проверенного способа чтения, не универсальный коэффициент байт/токен. Наш MCP exec_command ограничен 32000 байтами и тоже вырезает середину. Рабочий предел 28000 выбран с запасом; если документ в пределах лимита на практике не читается за вызов, пользователь понижает значение в конфигурации.

validateStaged проверяет blobs из index до ветвления по роли и до запуска тестов:
- Каждый добавленный/изменённый/переименованный .md в кандидате коммита обязан укладываться в предел; удалённый файл не имеет нового blob для проверки.
- Единственное исключение — точный путь .harness/plans/todo-plan.md. AGENTS.md целиком и установочные .md исключениями не являются.
- Проверяются коммиты задач и служебные операции: создание/уточнение плана, docs:commit, kit-update и прочие.
- Нетронутые старые большие документы коммит не блокируют; при первой правке их делят на самостоятельные документы.
- Превышение — ошибка, не предупреждение. Диагностика содержит путь, фактический размер UTF-8, предел и команду повтора для данной операции. Правки сохраняются. Агент делит документ и повторяет фиксацию.
- Код не подпадает под ограничение документации. Новые проверки не отменяют проверки состава, транзакций, авторства и приватных путей.

## 3. Владельцы инструкций (С3)
Одно правило имеет один канонический источник. Обнаруженный дубль удаляется из остальных источников.

| Источник | Ответственность |
|---|---|
| Workflow Core | Процесс Kit: план, задачи, commit, DOCS, delivery, раунды |
| PROTOTYPE | Как вести работу и Git внутри задачи |
| Kit-секция AGENTS.md | Только указание прямым клиентам, где получить recovery |
| Проектная часть AGENTS.md | Постоянные ограничения конкретного проекта |
| Обёртка Web Pilot | Только транспорт: идентификаторы, инструкция первого ответа, правила исполнителя |

В ядро входят Workflow Core, PROTOTYPE и проектная часть AGENTS.md. Kit-секция AGENTS.md в Web Pilot повторно не передаётся. Транспортные строки добавляет Web Pilot. Для остальных документов выбор раздела по heading_path больше не выполняется: передаётся документ целиком. Это не отменяет явного отделения управляемой секции AGENTS от проектной.
Шаблоны/справки этапов получаются по необходимости через существующие --help; не включать все формы при старте. Не добавлять модельный классификатор, API модели и обязательные кнопки режимов.

## 4. Документы без плана и раунды (С4, С5, С15)
docs:commit --files … --message … — управляемая фиксация документов. Роль documentation; разрешён любой .md вне .harness/, включая packages/workflow-kit/README.md, packages/workflow-kit/docs/modules/* и выпущенные packages/workflow-kit/docs/planning/*. Для AGENTS.md управляемая секция Kit в index должна побайтно совпадать с HEAD; меняться может только проектная часть. Изменение или удаление управляемой секции этой командой отклоняется; её обновляет установщик.
Разрешено в NONE и ACTIVE без текущей задачи; при IN_PROGRESS запрещено. Коммит содержит Workflow-Scope (NONE либо текущий scope) и Workflow-Role. Проверки: схема, состав, размер, транзакция; набор тестов приложения не запускается. Эта команда не даёт права менять произвольные файлы .harness/.

Раунд доработки:
- Новые задачи идут после существующих; DONE не переставляются и не переписываются. before допустим только перед ещё не начатой задачей.
- Пользователь определяет, нужен ли выпуск. В раунде с выпуском DOCS получает новую итерацию после работы раунда и перед его delivery. Опубликованный тег не переиспользуется.
- Завершённые delivery сохраняют ссылки на конкретную прежнюю итерацию DOCS. Зависимости не переключаются на последнюю итерацию автоматически.
- В раунде без выпуска recovery сообщает об изменениях после выпуска X; дополнительная финальная DOCS не навязывается.
- Правила согласуются с resolveReferences, pre-push, delivery_status, nextTask, отображением плана и AutoPlan.

archive коммитит пустой текущий план с archived_scope_id, без .harness/plans/archive. Закрытый план читается из родителя коммита закрытия: git show <closing-SHA>^:.harness/plans/todo-plan.md. Коммит закрытия определяется по trailers. plan:carryover сохраняет source_commit, не создаёт копию. Миграция прежних сессионных планов также не создаёт архивных копий.
Существующий архив удаляет только install --update ролью kit-update как миграцию формата данных. До удаления проверяются все файлы: каждый отслеживается Git и совпадает с blob HEAD; staged/рабочая правка, отсутствующий tracked файл или untracked файл означают ошибку без удаления. История остаётся в Git. docs:commit для этой очистки не используется.

## 5. Recovery и ссылки на Git (С6–С11)
Сборщик детерминированно читает источники; не вызывает модель и не составляет пересказы.
Общий пакет: ядро, OVERVIEW, точный workspace, состояние Git и незавершённой транзакции.
ACTIVE добавляет рабочую спецификацию, выбранные документы и проекцию всех задач: id, заголовок, why, статус, зависимости, критерии, подтверждённые SHA и файлы. Машинный JSON todo-plan.md вторым экземпляром не передаётся.
NONE добавляет archived_scope_id, SHA коммита закрытия, детерминированный список задач предыдущего плана со статусами/SHA и ссылку на его спецификацию на существующей ревизии. Новый проект без прошлого плана — нормальное состояние.
Recovery перечисляет невыпущенные docs/planning/*: путь, заголовок, размер; содержимое выбирается по необходимости. Дополнительного документа с пересказом recovery агент не создаёт.

Коммиты и диффы передаются ссылками. Пакет содержит staged/unstaged/untracked пути и отдельно посторонние изменения, но не включает текст diff. В ядре правило: «перед реализацией прочитай коммиты, диффы и код, от которых зависит задача; остальное не читай». Обязательного чтения всей истории перед обсуждением нет.
Удаляются включение диффов зависимостей и CHANGE_CONTENT_ON_DEMAND. Старое dependency_task_ids принимается для совместимости, но не добавляет содержимое diff.

context_pack.documents.revision принимает WORKTREE либо точный SHA. SHA читается через git show SHA:path, с существующими проверками безопасности путей. Дедупликация по (path, revision); отсутствующий revision означает WORKTREE; для одной пары required побеждает. Разные ревизии одного пути не смешиваются.
Старый heading_path принимается, но документ читается целиком.
Если операция удаляет required-документ, Kit в той же транзакции переводит соответствующие ссылки на before_head. Сначала проверяется существование blob: созданный и удалённый без коммита документ не получает фиктивную ссылку, операция завершается ошибкой. Отсутствующий файл по ссылке WORKTREE остаётся ошибкой; наличие другой ревизии его не скрывает.
Сохраняются подтверждение references по trailers/scope/task, свежесть снимка, защита приватных путей, транзакций и посторонних изменений.

## 6. Части и доставка (С12)
Kit возвращает части не больше budget.document_bytes каждая, включая служебное оформление. Целые документы и задачи сохраняются единицами, когда помещаются. Для больших единиц одна функция деления: заголовки → абзацы → строки → граница символа UTF-8. Текст не теряется и не повторяется; номер/источник/порядок части определены.
Старый документ сверх предела не блокирует recovery и открытие проекта: выдаётся частями с пометкой «разделить при следующей правке». Это исключение транспорта не разрешает коммитить его новую большую версию.
Размеры показываются в байтах и символах. Удаляются псевдотокены bytes/2 и неиспользуемый soft_exceeded. Общий hard_bytes=180000 сохраняется; превышение общего бюджета — явная ошибка без усечения.

Web Pilot передаёт части отдельными вложениями одного первого сообщения. Текст сообщения короткий: идентификаторы, количество частей, просьба прочитать каждое вложение полностью по одному разу; MCP проекта в первом ответе не вызывать. Инструменты чтения полученных вложений разрешены.
T004 начинается с проверки осуществимости File в DataTransfer существующего synthetic paste на максимуме: 7 файлов по 28000 байт в одном сообщении; все семь должны завершить загрузку до Send. Семь частей — округление вверх 180000 / 28000. Полные семь файлов дают 196000 байт: это отдельная транспортная проба с запасом, предел recovery hard_bytes=180000 не меняется. Живую проверку проводит пользователь. Если ChatGPT Web файлы не принимает, агент останавливается и докладывает; молчаливый fallback к большой текстовой вставке запрещён.
До Send все части должны быть прикреплены и загружены. Сообщение отправляется один раз; частичный сбой не даёт незаметно потерять часть или повторить сообщение. Неопределённый исход не разрешает автоматический дубль.
Кеш использует реальный inspectionInputs(...).key, включая новые источники NONE/planning и новую карту документов; повторная правка уже dirty файла меняет ключ. Тестовый contextInputKey удаляется либо синхронизируется.
