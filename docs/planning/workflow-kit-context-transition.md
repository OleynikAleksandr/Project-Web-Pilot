# Workflow Kit: переход и проверка

Обязательная вторая часть [основной спецификации](workflow-kit-context-refactor.md), согласованной 06.10.2026. Там — постоянные требования; здесь — порядок перехода этого проекта. Критерии, файлы и проверки задач хранятся в текущем плане; их завершённые записи неизменны.

## 1. Порядок внедрения
T001/T001R/T001R2 (спецификация и ревью, без реализации) → T002 (жизненный цикл) → T002A (документы) → T003 (recovery) → T004 (Web Pilot) → T004A (переполнение) → DOCS → T005 (парная сборка macOS arm64/Windows x64) → T006 (установка/переход) → T007 (публикация).
T004 готовит версии Web Pilot 0.6.97 / Kit 1.6.0 и проверки без сборки. T005 выполняется старым Kit; T007 — новым, без пересборки, затем READY_FOR_ACCEPTANCE и остановка. Миграция документов выполнена вне плана после T007 и первого исправительного раунда (T008–T011, выпуск 0.6.98). Дальнейшие исправления идут раундами этого же плана до приёмки пользователем.

Переиспользовать resolveReferences, context_pack, archived_scope_id/source_commit, транзакции, fingerprint, диагностику и --help. Параллельных механизмов не создавать. Новый установщик не восстанавливает упразднённые документы и не дописывает старый индекс; до согласованной миграции старый состав читается.
Sidebar: сохранить экспорты, pageOperation и pageScript/toString-интеграцию. Правки composer допустимы; необходимое изменение публичного контракта проверить и явно описать в коммите. Чужой workspace не менять.

## 2. Проверки
T002/T002A/T003/T004A: kit-check и unit-all. T004: дополнительно electron-smoke. Kit-check не заменяет корневые tests/*.test.mjs; suite, запускаемую commit, второй раз на том же состоянии не выполнять. Служебные/документационные операции проверяют схему и состав без suite приложения, кроме явно назначенных проверок.

Матрица — основная спецификация §2–6 и критерии задач:
- Размер: границы 28000/превышение, UTF-8, index≠worktree, все роли, untouched legacy; docs:commit, защищённые секции и отказ небезопасной миграции.
- Раунды: с выпуском/без, прошлые итерации DOCS, nextTask/pre-push/AutoPlan.
- Recovery: ACTIVE/NONE/новый проект, dirty/transaction, WORKTREE/SHA/before_head/отсутствующий blob, дедупликация/старые поля, целый документ и задача; split по разделу/абзацу/строке/символу; freshness повторной dirty-правки.
- Доставка: полный состав, загрузка до единственного Send, частичные/неопределённые сбои, текст инструкции отдельного чтения.
- T002: служебный коммит между task:start и commit сохраняет файлы/доказательства. T004: полный переход 1.5.6→новый Kit по §4 и конфигурация с legacy token-полями/без них.

T004A проверяет **полную изолированную копию реального проекта** с исходниками нового Kit вместо её установленного runtime, до/после штатной нормализации плана: <=144000 из 180000 байт (запас >=20%), <=7 частей. План не сокращать, бюджет не повышать, обязательный контекст не терять. Восьмая часть даже при сумме <180000 даёт CONTEXT_TOO_LARGE. Проверка входит в оба обязательных checks; реальную .harness/kit не менять до T006. Повторяющиеся требования двух частей спецификации заменены ссылками; плановые/фактические файлы в recovery представлены без дублей, с точным перечислением добавлений и исключений.

## 4. DOCS и переход T006 (С13, П1–П8, П13)
До T006 установлен Kit 1.5.6; его hooks/формат нельзя обходить. Установленные .harness/kit/* вручную не править; Kit-секцию AGENTS меняет install --update, проектную часть — документационная операция.
DOCS актуализирует и фиксирует изменённое поведение до сборки: workflow-kit-recovery, CONTEXT_DELIVERY, context-as-text, WORKSPACE_SETUP, архитектура/OVERVIEW/README, README/спецификация пакета Kit, контракт Sidebar. Уже актуальное не переписывает. Массовую миграцию состава не выполняет; содержание README и перенос документов — основная спецификация §1. Обе части текущей спецификации временно сохраняются до закрытия scope. Противоречивое исследование recovery-on-demand-research.md и ссылка удаляются в T001R; действующие выводы перенесены сюда.

T004 готовит package.json/lock/VERSION, через config:apply обновляет stack и checks/evidence. В budget только добавляет document_bytes=28000, сохраняя обязательные для 1.5.6 soft_tokens/hard_tokens до DOCS, T005 и task:start T006. Новый runtime принимает их и их отсутствие, но не ограничивает ими recovery; удалять не раньше T006. До реализации document_bytes конфигурацию не менять.
paired-release запускается один раз при commit T005; версии повторно не меняются. T006/T007 используют тот же выпуск. release-installed/github-release готовятся T004 с актуальным evidence.

Порядок T006, заранее проверяемый fixture T004 с upgradeFrom 1.5.6:

2. Установить готовое приложение; сохранить filesystem identity корневого macOS app, проверить обе установленные копии/подпись.
3. install --update: отдельный kit-update, смена формата, безопасное удаление прежнего архива планов.

## 5. После плана
1. Claude независимо проверяет результат. Замечания исправляются раундом того же незакрытого плана; это проверка раундов. Кодовые исправления завершаются новым выпуском, DOCS перед delivery.
2. Claude через Mac мигрирует документы вне плана: docs:commit в idle ACTIVE. Архив планов уже обработан install --update; docs:commit его не удаляет.
3. Перед удалением required WORKTREE-документов (включая MODULES/DOCUMENTATION_INDEX) управляемо исправить context_pack: не оставлять отсутствующие пути, сохраняемые исторические required-ссылки закрепить существующим SHA.
4. Передать пользователю анализ и таблицу «существенное требование → новое место». Сохранить ограничения и причины решений, не копировать историю.
5. Push документационных коммитов без переноса опубликованного тега; проверить правила, дерево, ссылки, размеры и recovery. Только после успешной миграции сказать «готово к перезапуску».
6. Пользователь перезапускает приложение и с Claude проверяет новый проект; обновление 1.5.6 с большими документами (readiness, части по заголовкам, отказ при первой большой правке); текущий проект (новая сессия, раунд, docs:commit).
7. Живой ChatGPT и нативную Windows проверяет пользователь. Агент не запускает VM, не управляет UI, не вызывает модельных агентов; Mac fixture/сборка не подтверждают Windows.
8. Пользователь командует архивировать план — это приёмка. Затем удалить обе временные части спецификации через docs:commit, сохранив версии в Git; исправить ссылки, push без переноса тега.
