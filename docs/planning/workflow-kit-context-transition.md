# Workflow Kit: переход, задачи и проверка

Обязательная вторая часть [основной спецификации](workflow-kit-context-refactor.md). Согласовано 06.10.2026. Постоянные требования находятся там; здесь порядок внедрения в текущий проект без преждевременной миграции.

## 1. Последовательность текущего плана
T001 и T001R уже завершены: записи, why, actual_files и commit_ref неизменны. T001R2 фиксирует пять дополнительных уточнений к спецификации и плану до начала T002; реализации в этой задаче нет.
- T002 — жизненный цикл: docs:commit, раунды после выполненного delivery, DOCS только при delivery, архив без копий и безопасная миграция старых архивов установщиком.
- T002A — модель документов: единый предел 28000 байт, index-проверка для задач/служебных операций, владельцы инструкций, новые шаблоны/состав, установка и готовность старых/новых проектов.
- T003 — recovery: WORKTREE/SHA, атомарные ссылки на удалённые required-документы, NONE/ACTIVE, docs/planning, целые документы, общий splitter и ссылки вместо diff.
- T004 — сначала проверка возможности File/DataTransfer в ChatGPT Web: 7 файлов по 28000 байт одним сообщением, все загружены до Send. При отказе остановка с докладом пользователю. После успеха — вложения, freshness, AutoPlan, совместимость Sidebar, upgradeFrom 1.5.6, версии и проверки будущего выпуска без сборки.
- DOCS — актуализировать и зафиксировать документацию изменённого поведения перед выпуском. Состав старого проекта пока массово не перестраивать.
- T005 — парная сборка macOS arm64 / Windows x64 с новым Kit, ещё на установленном Kit 1.5.6.
- T006 — установка готового приложения и штатный переход установленного Kit.
- T007 — публикация и проверка GitHub уже новым Kit, без пересборки. После коммита READY_FOR_ACCEPTANCE и остановка.

Задач T008/T009 нет. Миграция проектной документации вне исполняемого плана после T007 и необходимых раундов доработки, до перезапуска пользователя. Автоматически открывать отдельную фазу миграции запрещено.

## 2. Состав изменений и переиспользование
Переиспользовать существующие resolveReferences (trailers/состав/порядок), context_pack.documents, archived_scope_id, source_commit, транзакции, fingerprint, missing/too-large диагностику и --help. Не создавать параллельный механизм планов, архивов или recovery.
В план включены не только основной код, но и:
- Kit: actions, plan, validate, git-hooks, transaction, simple-workflow, extend-plan, task-update/task-files, session-plans, command-help, cli и JSON schemas;
- установка/контекст: installation-files, installer, inspection-inputs, recovery, project-facts, git, common;
- шаблоны PRODUCT, ARCHITECTURE, START удаляются либо заменяются; WORKFLOW/AGENTS/PROTOTYPE/SPEC/PLAN/CONTINUE/STAGES согласуются с владельцами правил;
- Web Pilot: workspace-setup-worker и проверка готовности, context-session/cache, session-plans, AutoPlan и источники свежести; адаптер ChatGPT при необходимости доставки File;
- fixtures пакета и корневые тесты recovery, workspace-setup, project-doctor, session-plans, session-opening-performance, workflow-kit-source, release-all.

Убрать жёсткую обязательность MODULES/DOCUMENTATION_INDEX/PRODUCT/ARCHITECTURE/WORKFLOW_START из нового формата. Установщик не должен восстанавливать удалённые файлы или дописывать прежний индекс при каждом обновлении. Старый состав до согласованной миграции остаётся читаемым.
Критерий Sidebar: сохранены используемые им экспорты, pageOperation и формат pageScript/toString-интеграции. Не обещать неизменность трёх browser-файлов: доставка File может потребовать правки composer. Необходимое изменение публичного контракта явно отражается в коммите и проверяется; чужой workspace не меняется.

## 3. Проверки задач
T002, T002A и T003 выполняют kit-check и unit-all. Одного kit-check недостаточно: он не запускает корневые tests/*.test.mjs.
T004 выполняет kit-check, unit-all и electron-smoke. Живая проверка ChatGPT пользователем — отдельный необходимый этап проверки осуществимости; fixture не доказывает приём файлов настоящим ChatGPT Web.
Обязательные сценарии:
- docs:commit в NONE/idle ACTIVE и отказ при IN_PROGRESS; любой .md вне .harness/, включая README/modules/planning пакета Kit; отказ для .harness/; корректные trailers; побайтное совпадение Kit-секции AGENTS.md в index с HEAD, отказ при её изменении/удалении;
- раунд после полностью выполненного delivery, с выпуском и без; прежние итерации DOCS, nextTask, pre-push, AutoPlan;
- общий предел на staged blob: ровно 28000, превышение, русский UTF-8, index отличается от worktree; задачи и служебные коммиты; единственное исключение todo-plan.md; untouched legacy не блокирует;
- archive/carryover/legacy migration без копий; install --update удаляет только tracked архивы, совпадающие с HEAD; untracked/изменённый архив вызывает ошибку до удаления;
- ACTIVE после части коммитов, NONE после закрытия, новый проект без истории; dirty/transaction/посторонние изменения;
- required-документ в WORKTREE, существующем SHA и before_head; отсутствующий blob — ошибка; удаление и изменение ссылки атомарны;
- дедупликация (path,revision), старые heading_path/dependency_task_ids; список невыпущенных спецификаций;
- split большого документа, раздела, абзаца, строки и задачи без потерь, на UTF-8 границах, с учётом служебных заголовков; общий потолок 180000;
- свежесть при повторной правке уже dirty источника и новых источников вне плана;
- вложения: проба 7 файлов по 28000 байт, все загружены до Send; полный состав, один Send, частичный/неопределённый сбой без потери части и дубля. Транспортная проба 196000 байт не меняет общий бюджет recovery 180000;
- T002: служебный коммит между task:start и commit не ломает учёт файлов задачи и её доказательства; полный переход разных версий в эту проверку не входит;
- T004: upgradeFrom 1.5.6 и полный переход текущего активного плана — task:start старым Kit → kit-update → commit новым Kit → доступная T007;
- конфигурация нового runtime с soft_tokens/hard_tokens и без них; сохранение этих полей в переходной конфигурации для DOCS, T005 и task:start T006 на Kit 1.5.6.

Не выполнять suite второй раз на том же состоянии, если её запускает commit. Документационные/служебные операции проверяют схему и состав без suite приложения, кроме явно назначенных проверок.

## 4. DOCS, версии и переход (С13, П1–П8, П13)
До T006 установлен Kit 1.5.6: действуют его hooks и формат плана. Новые правила являются результатом разработки; не обходить старые проверки.
DOCS проверяет весь действующий комплект и актуализирует документы нового поведения: workflow-kit-recovery, CONTEXT_DELIVERY, context-as-text, WORKSPACE_SETUP, архитектура/обзор/README и README/спецификация пакета Kit, контракт Sidebar. Неактуальные сведения исправляются; уже актуальное не переписывается.
README содержит версию, установку и запуск; без статуса сборки или публикации, ссылок на конкретный релиз и хешей — они в release-manifest.json и GitHub Release.
Массовое удаление исторических проектных документов в DOCS не выполняется. Обе части текущей спецификации временно сохраняются до закрытия этого scope, несмотря на общее правило удаления выпущенных временных спецификаций.
Противоречивое завершённое исследование recovery-on-demand-research.md удаляется при T001R вместе с навигационной ссылкой: действующие выводы перенесены в эту спецификацию.

.harness/kit/WORKFLOW.md и другие установленные файлы не редактируются вручную. Kit-секцию AGENTS обновляет только install --update отдельным kit-update; проектную часть можно править в соответствующей документационной операции.
Новые версии package.json/lock, пакета Kit и VERSION готовятся в T004. T005 не меняет версии повторно. stack, checks/evidence и budget.document_bytes=28000 в workflow.json обновляются через config:apply в предусмотренной задаче, не ручной правкой управляемого файла. В T004 среди полей budget только добавляется document_bytes; обязательные для Kit 1.5.6 budget.soft_tokens и budget.hard_tokens сохраняются, иначе DOCS, T005 и task:start T006 не пройдут проверку. Новый runtime принимает конфигурацию с ними и без них, но не использует их для псевдотокенного ограничения recovery. Удалять эти поля можно не раньше перехода на новый runtime в T006. До реализации поддержки document_bytes действующую конфигурацию не менять.
paired-release собирает один раз при коммите T005. T006/T007 используют тот же проверенный выпуск, без пересборки; release-installed/github-release подготовлены T004 без старых значений evidence.

Порядок T006:
1. task:start T006 старым Kit.
2. Установить уже собранное приложение; сохранить filesystem identity корневого macOS app и проверить обе установленные копии/подпись.
3. install --update штатно создаёт отдельный kit-update, переводит формат и безопасно удаляет прежний архив планов.
4. commit --task T006 выполнить новым Kit.
5. Подтвердить читаемость плана, неизменность DONE/references, подтверждённый commit T006 и доступность T007.

Полный сценарий перехода заранее проверяется fixture в T004 после добавления upgradeFrom 1.5.6. В T002 проверяется только то, что промежуточный служебный коммит сохраняет учёт файлов задачи и доказательства её выполнения.
Пользователь до конца плана остаётся в открытом чате старого Web Pilot 0.6.96. После установки нового Kit повторное открытие проекта старым приложением может не пройти проверку версии. Работу открытого чата также нужно подтвердить, а не предполагать. При сбое агент сообщает пользователю; использование строки для внешнего клиента — решение пользователя.
T007 новым Kit публикует и сверяет source/tag/assets/manifest и синхронизацию GitHub. После подтверждённого коммита агент останавливается; scope не архивирует.

## 5. После плана: ревью, миграция и приёмка
1. Claude независимо проверяет результат. Замечания агент исправляет раундом того же незакрытого плана; это живая проверка раундов. Если исправления затрагивают код, раунд завершается новым выпуском с DOCS до delivery.
2. Claude через доступ к Mac переводит проектные документы в новую модель вне плана, через docs:commit в idle ACTIVE. Старый архив планов к этому моменту уже обработан install --update, документационная команда его не удаляет.
3. Перед удалением MODULES/DOCUMENTATION_INDEX и других required WORKTREE-источников context_pack управляемо приводится к новому составу. Не оставлять ссылок на отсутствующие файлы. Для сохраняемых исторических required-документов применяются проверенные SHA-ссылки.
4. Пользователю передаются анализ и таблица «существенное требование старого документа → новое место». История не копируется; действующие ограничения и причины решений сохраняются.
5. Документационные коммиты отправляются на GitHub без переноса опубликованного тега. Проверяется согласованность новых правил, дерева документов, ссылок, размеров и recovery. Только после этого сообщается «готово к перезапуску».
6. Пользователь перезапускает Web Pilot. Вместе с Claude проверяет новый проект; обновление старого проекта с Kit 1.5.6 и большими документами (readiness, части по заголовкам, отказ при первой большой правке); текущий проект (новая сессия, раунд, docs:commit).
7. Нативную Windows и живую доставку проверяет пользователь; Mac fixture/сборка не считаются приёмкой Windows. Агент не запускает VM, не управляет UI и не вызывает других модельных агентов.
8. Пользователь командует архивировать план — это приёмка. После закрытия временные части этой спецификации удаляются управляемым документационным коммитом с сохранением доступа к их версиям в Git; очищаются ссылки и выполняется push без переноса тега.

Итог перехода: установленный Kit, действующие документы и стартовый пакет соответствуют друг другу; правила дальнейшей разработки не требуют накопления исторических документов.
