# Жёсткий порядок документации, сборки и публикации

## Результат

Workflow Kit должен передавать каждому новому агенту однозначные правила delivery-порядка и формировать планы так, чтобы эти правила нельзя было случайно нарушить обычным `plan:create` / `plan:extend`.

Обязательные инварианты:

1. Сборка, упаковка, подпись, notarization, создание релиза и публикация на GitHub выполняются **только** внутри активной микрозадачи, где это действие прямо названо. Нельзя запускать их как «вспомогательный» шаг code/test/DOCS-задачи.
2. Перед любой сборкой или публикацией все относящиеся к результату документы должны быть актуализированы и зафиксированы.
3. Если plan содержит delivery-задачи с `verification_kind=package|installed`, системная DOCS должна стоять перед delivery-хвостом, а не после него.
4. Delivery-задачи должны образовывать хвост плана. Для обычного релиза предпочтительна одна последняя явная задача «собрать, проверить и при поручении опубликовать», внутри которой порядок строго: готовые документы → build/package → verification → publish.
5. Если сборки нет, но требуется публикация исходников на GitHub, публикация выполняется только после DOCS и отдельной явной delivery-задачей.
6. Если в плане нет явной delivery-задачи, никакая сборка/публикация не выполняется.

Новые поля схемы не добавлять, если существующих `verification_kind=code|package|installed` достаточно для надёжного порядка.

## Управление работой

Изменения выполняются в canonical workspace `/Users/oleksandroliinyk/VSCODE/WorkflowKit`, но отдельного ACTIVE-плана в этом checkout нет: current plan WorkflowKit остаётся `NONE`. Работой управляет активная T001 плана Project Web Pilot `input-instruction-delivery-ordering-20261003`; это исключает второй незавершённый plan при открытии WorkflowKit как отдельного проекта.

Для доставки новой recovery policy локальная package version Workflow Kit поднята до **1.5.2** с upgrade-path 1.5.1 → 1.5.2. Это не release/publish: GitHub Release и публикация package в этой работе не выполняются. Возможный внешний release — отдельная последующая delivery-задача после DOCS.

## Проверка

- `npm run check` проходит полностью.
- Runtime fixture подтверждает, что recovery содержит новые канонические правила.
- `plan:create` для code-only scope сохраняет обычную финальную DOCS.
- `plan:create` для scope с package/installed delivery размещает DOCS перед delivery-хвостом.
- `plan:extend` сохраняет этот порядок; correction после уже завершённой DOCS переоткрывает DOCS перед незавершённым delivery-хвостом.
- План с обычной code-задачей не получает неявного разрешения на build/package/publish.
- Исторические планы и существующие DONE-коммиты не переписываются.

## Границы

- Не вводить эвристику по словам в title задачи.
- Не добавлять отдельный orchestration framework.
- Не менять модель «один current plan на checkout/worktree».
- Не выполнять build/release/publish в этом scope.
