# T005 — Ошибки и жизненный цикл

Аудит выполнялся по исходникам, без UI, живых пользовательских данных, запуска служб или установки. Точки исследования: `src/{main,context-session,auto-plan,page-state,project-input-watch,plan-review,review-continuation,workspace-session,mac-runtime-switch}.mjs`, связанные проверки и описанные в основном реестре входы. Применены адресное чтение и `rg` по Promise, `.catch`, таймерам, watchers, подпискам и закрытию; отрицательный поиск не доказывает отсутствия дефекта.

## C-LIFE-01 — подавление исключения подписчика состояния страницы (medium, кандидат на надёжность)

`src/page-state.mjs:115–119`: `#notify` перебирает listeners и выполняет `try { listener(event); } catch {}`. **Подтверждённый факт:** синхронная ошибка callback полностью игнорируется — ни вызывающий код, ни диагностика не узнают о ней. Подписка остаётся на месте, будущие уведомления продолжаются; если ошибка постоянна, потребитель может перестать корректно реагировать без видимого сигнала. Риск требует проверки реального подписчика и политики сигналов: изолировать callbacks полезно, но сообщать `onError` или в ограниченный logger, не логируя секреты; не делать исключение одного listener причиной остановки других. Верификация предлагаемой правки: fixture с падающим listener, убеждающаяся в доставке остальным и видимой диагностике. **Доказан механизм молчаливого подавления, не подтверждён пользовательский сбой.** Публичные API Sidebar не менять; одинаковое поведение macOS/Windows ожидается, но не испытано.

## C-LIFE-02 — потеря свидетельства ошибки записи «unknown» (medium, ограничение)

`src/context-session.mjs:395–402`: при ошибке после начала Send код пытается записать `state:'unknown'`, но `updateSession(...).catch(() => {})` подавляет ошибку записи и всё же показывает `send-unknown`. **Подтверждённая последовательность:** если persist откажет, UI сообщает неопределённый исход, а durable запись может не получить новое состояние. Повторная отправка без независимой проверки может быть опасна; нынешняя политика не допускает автоматического повторения неопределённого Send. Нужно проследить восстановление после перезапуска и поведение store при сбое записи — пока не доказана фактическая повторная отправка. Минимальное исправление после проверки: отдельная видимая ошибка сохранения статуса и запрет возобновления как заведомо неотправленного; тест отказа `updateSession` непосредственно после попытки Send и рестарта fixture. Не выполнять живую отправку для проверки.

## C-LIFE-03 — ошибки transient/UI operations могут подавляться намеренно (low)

`src/main.mjs:247` (`executeJavaScript(toolFilterScript(...)).catch(() => {})`) игнорирует сбой фильтра инструментов; в `:367,408,422` аналогичные `catch`, требующие проверки несущественных операций. Для cosmetic DOM filter это может быть осознанная деградация, а не потеря критической операции. Минимальный вариант — техническая ограниченная диагностика без тел беседы, **только** если последующее расследование подтвердит потребность в индикации. Не назначать дефект без трассировки вызова и проверки поведения на navigation/reload.

## Защиты, проверенные чтением (отрицательные результаты)

- **Неопределённый исход и повтор:** `src/context-session.mjs:388–403` различает `sent`, `unknown`, `deferred/cancelled`; `src/auto-plan.mjs:305–328` на `unknown` вызывает pause без повтора и при ошибке checkpoint после успешного Send сохраняет локальное `sent` для подавления повторов. Это подтверждение логики в коде, не живого end-to-end.
- **Таймеры и teardown окна:** `src/main.mjs:1291–1306` на `closed` вызывает dispose/cancel/close для AutoPlan, Review, PlanMonitor, page state, clipboard, startup, diagnostics; `clearInterval(eventRuntimeCheckerTimer)` есть. Дочерние окна уничтожаются, WebContents закрываются. `src/plan-review.mjs:65` снимает timer; `src/auto-plan.mjs:325–327` очищает timer/watchdog; `src/review-continuation.mjs:80` передаёт dispose в flow.
- **Файловые наблюдатели:** `src/project-input-watch.mjs:55–99` заменяет watch при изменении inode, закрывает на `error` и при исчезновении интереса; `close()` снимает retry timer и все watchers. Есть видимый `PLAN_WATCH_FAILED` и ограниченный retry; тихая бесконечная утечка здесь не подтверждена.
- **Очереди сохранения:** `src/workspace-session.mjs:375–389` сериализует операции и удаляет собственные временные файлы после неуспеха; `:396–401` дожидается завершения сохранений перед удалением временных файлов. `.catch(() => {})` на предыдущих tail обеспечивает продолжение очереди после ошибки, а возвращаемая текущая операция может отказать. Это не доказательство ложного успеха.
- **Переключение проекта/чата:** `src/context-session.mjs:395–407` проверяет текущий generation прежде чем показывать состояние; `src/workspace-session.mjs:362–372` проверяет selectedSessionId и выдаёт `SESSION_CHANGED`. `src/main.mjs:1064–1075` учитывает generation при откате навигации. Конкурентное взаимодействие этих защит в живом ChatGPT не испытывалось.
- **Внешние службы:** `src/main.mjs:1302–1306` явно оставляет MCP/туннель работающими при закрытии окна — это предусмотренная архитектура, не утечка. Старые runtime процессы завершаются отдельной миграцией, не обычным закрытием окна.

Выполнения тестов или воспроизведения настоящей отправки не было: поэтому дефекты уровня пользовательского сценария **не подтверждены**.
