# Один репозиторий, контекст текстом, MCP только инструменты, паритет Windows — релиз 0.6.96

Решение пользователя 06.10.2026 по итогам разбора «что было — что стало» после релизов 0.6.86–0.6.95. Тем же днём объём расширен тремя поручениями: включить в релиз исправление дефектов Workflow Kit, сделать macOS и Windows одинаковыми по возможностям и способам, объединить репозитории Project Web Pilot и Workflow Kit.

## Почему

Доставка контекста через MCP (0.6.86–0.6.88) не дала того, ради чего вводилась. Без DOM работать всё равно нельзя: в MCP инструменты вызывает только модель, сервер не может начать сессию или запустить задачу, и проверка 0.6.87 показала, что одни `instructions` вызова не гарантируют, — поэтому в 0.6.88 стартовое сообщение вернулось на DOM. Взамен одной гарантированной вставки появился протокол чтения по частям с ключами и запретами под потолок одного ответа инструмента (около 10 000 токенов у ChatGPT).

Довод «через MCP контекст доступен внешним клиентам» снят: контекст — это текст в папке проекта, и агент с доступом к папке читает его обычными инструментами по одной строке с путём.

Сбои OpenAI начала октября (лимиты, «дополнительная проверка») причиной отказа от вставки не считаются: в те же дни одновременно менялись форма доставки, длина хода (одна микрозадача на ход) и канал (VPS). Причина не установлена.

## Что показал осмотр кода (main `c188d71`, 0.6.95)

- Доставка полного пакета первым сообщением никуда не делась: `startupMessage` в `src/context-session.mjs` и вставка через `ChatGPTComposer.deliver` работают для Windows. macOS переведён на MCP одной строкой — `CodexAppServerRuntime.contextDelivery` возвращает `'mcp'`.
- Пакет на macOS Web Pilot уже получает напрямую от Workflow Kit: `SessionPlans.loadContext` запускает `scripts/workflow.mjs recover --format packet`. Инструмент сервера `workflow_context_recover` клиенту macOS для этого не нужен; он нужен только модели и входит в обязательный список `LocalMcpClient` (`requiredTools`).
- Правила сессии существуют в двух местах: в `startupMessage` (для первого сообщения) и в `tools/codex-app-server-mcp/session-rules.md` (для MCP). Во втором есть две строки, которых нет в первом: про работу с инструментами и про один повтор после блокировки OpenAI.
- Текущий пакет recovery этого проекта — 87 085 байт (59 299 символов): через MCP это четыре последовательных вызова, через поле ввода — одна вставка. Сайт может показать большую вставку как вложение; `ChatGPTComposer` считает отправку состоявшейся в обоих случаях.
- AutoPlan отправляет голое «Продолжай» (`CONTINUE_TEXT` в `src/auto-plan.mjs`), хотя прямо перед отправкой читает актуальный план.
- Блок Workflow Kit в `AGENTS.md` уже говорит агенту: если recovery не доставлен — `./scripts/workflow recover --format text`. Новая версия Kit для внешних клиентов не нужна; не хватает только готовой строки для первого сообщения.
- В меню проекта уже есть «Скопировать полный путь» (`copyWorkspacePath`).

## Результат

1. **Старт сессии.** На macOS Web Pilot отправляет одно стартовое сообщение с правилами сессии и полным пакетом recovery, как на Windows. Правила для macOS дополнены двумя строками из `session-rules.md` — про работу с инструментами и про один повтор после блокировки OpenAI; их даёт runtime исполнителя (`startupRules`), поэтому после W004 то же сообщение получает Windows.
2. **Старт задачи.** Сообщение автопродолжения несёт текст следующей задачи из плана: id, название, зачем, критерии приёмки, файлы, проверки. Первая строка — по-прежнему ровно «Продолжай»; блок задачи помечен как данные плана и не превышает 4 КБ. Задача читается той же проверкой плана, что и раньше выполнялась перед отправкой; если к моменту нажатия Send следующая задача уже другая, сообщение не отправляется (прежняя причина ожидания «план изменился») и готовится заново по следующему событию. Если следующая задача не определена, отправляется прежнее «Продолжай».
3. **Внешние клиенты.** В меню проекта есть «Скопировать строку для внешнего клиента»: имя проекта, папка, указание прочитать `AGENTS.md` и получить recovery в файл командой Workflow Kit, затем прочитать его целиком.
4. **MCP.** `workflow_context_recover`, протокол частей, `session-rules.md`, `active-workspace.json` и инструкция про чтение контекста удалены. Каталог macOS — девять инструментов: `exec_command`, `write_stdin`, `apply_patch`, `view_image`, `bridge_status`, `turn_watchdog`, `computer_list_windows`, `computer_capture_screen`, `computer_capture_window`. Server instructions — короткие правила работы с инструментами.

5. **Workflow Kit 1.5.6.** Исправлены два дефекта Kit. Подробности — раздел «Workflow Kit 1.5.6».
6. **Паритет Windows.** Windows работает через тот же исполнитель Codex App Server с тем же каталогом из девяти инструментов, той же доставкой контекста, теми же каналами ChatGPT и тем же жизненным циклом служб, что и macOS. Прежний Windows-runtime с 38 самодельными инструментами не используется. Подробности — раздел «Паритет Windows».

7. **Один репозиторий.** Workflow Kit становится пакетом `packages/workflow-kit` в репозитории Project Web Pilot; прежний репозиторий на GitHub переводится в архив. Подробности — раздел «Объединение репозиториев».

## Отступление от согласованной формулировки

Пункт «документы задачи вкладываются в сообщение, которым она запускается» сужен до текста самой задачи. Обязательные документы плана (контракт и карты) уже входят в стартовый пакет; собственный список файлов задачи — это то, что она будет править, и он слишком велик для вставки (`docs/VERIFICATION.md` — 548 КБ). Документы задачи агент читает инструментами по мере надобности.

Пункт «recovery готовым файлом в проекте» выполнен без новой возможности в Workflow Kit: файл создаёт сам агент командой из скопированной строки (`recover --format text > .harness/runtime/recovery.txt`), потому что вывод команды целиком не помещается в один ответ инструмента.

## Объединение репозиториев

### Почему

- У Kit один потребитель: Web Pilot берёт его как соседнюю папку (`"@webpilot/workflow-kit": "file:../WorkflowKit"`). Web Pilot Sidebar использует модули ChatGPT из Web Pilot, а не Kit.
- Отдельно Kit не выпускается: последний его релиз — v1.5.1, версии 1.5.2–1.5.5 существуют только в `main` и внутри Web Pilot.
- Каждая правка Kit проходит двойной круг: план, документы и отправка в его репозитории, затем задача в Web Pilot, которая вручную меняет версию, число файлов и SHA-256 в `scripts/check-workflow-kit-dependency.mjs`.
- Документы расходятся: README Kit называл текущим клиентом Web Pilot 0.6.80, когда выпускался 0.6.93; с 0.6.94 каждый релиз содержит отдельную задачу синхронизации.
- Два плана и два набора правил архивирования.

### Что должно стать

- Пакет `@webpilot/workflow-kit` лежит в `packages/workflow-kit` со своим `package.json` и своей версией. Версия остаётся: по ней обновляются установленные копии Kit в проектах.
- История Kit переносится в подпапку одной операцией `git subtree`. Это единственная прямая git-операция релиза, разрешённая пользователем; остальные коммиты — только через Workflow Kit. Если хук Kit её не допускает, файлы переносятся обычным коммитом задачи, а история остаётся в прежнем репозитории.
- Служебные файлы управления прежним репозиторием (`.harness`, `.codex`, `AGENTS.md`, обёртки `scripts/workflow`) в пакет не входят; архив планов Kit остаётся в прежнем репозитории.
- Web Pilot берёт пакет из своего репозитория; закреплённые константы версии, числа файлов и SHA-256 заменяются сверкой подготовленного runtime с исходником пакета. Собственные проверки пакета запускаются из корня (`kit-check`).
- Дублирующие документы верхнего уровня Kit вливаются в документы проекта; в пакете остаются README, техническая спецификация и планировочные контракты.
- Kit, которым выполняются коммиты этого checkout, — по-прежнему установленная копия в `.harness/kit`, а не исходник пакета. Исходник правится задачей, установленная копия обновляется отдельным шагом после проверок.
- После публикации релиза прежний репозиторий `OleynikAleksandr/WorkflowKit` получает в README ссылку на новый дом и переводится на GitHub в архив (только чтение). Локальная папка `/Users/oleksandroliinyk/VSCODE/WorkflowKit` не удаляется.

Если появится второй потребитель Kit, пакет подключается из этого репозитория или выделяется обратно одной операцией `git subtree split`, с историей.

### Как выполнено (M001)

- Импорт — коммит `e1c8c92` с двумя родителями: `547cf3b` (Web Pilot) и `6bbec655497eaea69d5c5825c68e9bdf78a01c18` (WorkflowKit `main`). Команда — `git subtree add --prefix=packages/workflow-kit ../WorkflowKit main`; в сообщении коммита сохранены строки `git-subtree-dir`, `git-subtree-mainline`, `git-subtree-split`, по которым работает `git subtree split`.

Причина: Workflow Kit не включает в коммит задачи пути внутри `.codex` (правило приватных путей), поэтому удалить `packages/workflow-kit/.codex/hooks.json` управляемым коммитом нельзя. Хуки Kit импорту не мешают: `git subtree` создаёт коммит без `git commit`.
- Остальное сделано обычным коммитом задачи: удалены `.gitignore` и `.gitattributes` пакета (блоки установщика Kit прежнего репозитория), зависимость переведена на `file:packages/workflow-kit`, закреплённые версия, число файлов и SHA-256 убраны из скриптов Web Pilot и из проверок пакета.

- `npm run check --prefix packages/workflow-kit` (проверка `kit-check`) запускает четыре скрипта пакета: состав пакета, контракт потребителя, установка в пробный проект, перенос плана.

## Workflow Kit 1.5.6

Работа выполняется после объединения, в `packages/workflow-kit`, обычной задачей этого плана (K001).

1. **Вставка задачи в середину плана.** Сейчас `plan:extend` ставит новую задачу после всех существующих кодовых задач и не умеет дополнять зависимости уже существующих. При выпуске 0.6.93 агенту пришлось назвать задачу `T001A` и запускать её вручную раньше `T002`: порядок в списке остался `T001, T002, T001A`, и Kit не помешал бы начать `T002` первой. Нужно: новая задача может быть поставлена перед указанной незавершённой задачей; зависимости незавершённых задач можно дополнить той же командой; порядок в файле плана и порядок выполнения совпадают; завершённые задачи и правило `work → DOCS → delivery` не затрагиваются.
2. **Подсказка о полях задачи.** Два агента подряд передали `spec` внутри задачи и получили отказ схемы. `plan:extend --help` должен показывать допустимые поля задачи и место `spec` до первой попытки.
3. **Ложный отказ `PRIVATE_CONTEXT` при коммите.** В выпусках 0.6.90, 0.6.91 и 0.6.95 первая в сессии команда `commit --task` отказывала с «Локальные секреты и runtime не включаются в контекст: .codex/hooks.json», хотя файл не менялся и `git status` его не показывал; повтор после `git status` проходил. Причина не установлена. Нужно: воспроизвести, найти и устранить причину; неизменённый `.codex/hooks.json` не останавливает коммит; действительно изменённый приватный путь не попадает в коммит задачи и перечисляется в `excluded_changes`.

### Как выполнено (K001)

- **Вставка.** Поле новой задачи `"before":"T002"` ставит её непосредственно перед ещё не начатой задачей и добавляет той зависимость от новой — Kit не даёт начать T002 первой. Поле верхнего уровня `"dependencies":{"T003":["T001A"]}` дополняет зависимости не начатых задач. Зависимость от задачи, стоящей позже, отклоняется (`TASK_ORDER`), поэтому порядок в файле совпадает с порядком выполнения. Обычная задача ставится перед обычной, delivery — перед delivery.
- **Подсказка.** `plan:extend --help` перечисляет поля задачи и место `spec`; `spec` внутри задачи отклоняется с тем же объяснением.
- **Причина ложного `PRIVATE_CONTEXT` установлена и воспроизведена.** Kit спрашивает у Git список изменённых файлов без обновления индекса. Индекс этого репозитория переписывал Git из виртуальной машины Cowork, через которую агент читал проект: она видит ту же папку с другими владельцем и номерами файлов. После этого родной Git считал изменёнными все 367 отслеживаемых файлов (проверено 06.10.2026: 367 из 367, после `git status` — 0), и первый приватный путь по алфавиту, `.codex/hooks.json`, останавливал коммит. Так же действуют восстановление файлов из копии и `touch`. В выпусках 0.6.90 и 0.6.91 коммиты делал другой агент, но проект в это время читался из той же виртуальной машины.
- **Исправление.** Изменение подтверждается содержимым: хеш файла сравнивается с индексом, индекс не трогается. Действительно изменённый приватный путь в коммит задачи сам не попадает и перечисляется в `excluded_changes`; раньше он останавливал коммит. Явный `--files` с приватным путём по-прежнему отклоняется.
- **Обновление проектов из Web Pilot.** Мастер подготовки проекта (`resources/workspace-setup-worker.mjs`) держал собственный список версий Kit, которые он соглашается обновлять; список заканчивался на 1.4.13, поэтому проект с Kit 1.5.0–1.5.4 при встроенном 1.5.5 получал отказ «версия пока не поддерживается». Обнаружено тестом реального обновления при переходе на 1.5.6. Теперь мастер читает список самого установщика Kit (`upgradeFrom`), и новая версия Kit не требует второй правки.
- Проверка — новый сценарий в `packages/workflow-kit/scripts/check-runtime-fixture.mjs`: вставка, отказы, совместимость прежнего вызова, коммит при «тронутых» файлах, исключение `.env` и изменённого `credentials.json`.

Границы Kit: формат плана и прежние команды совместимы; `recover`, шаблоны `AGENTS.md` и hooks не меняются сверх названного. Версия пакета — 1.5.6; установленный Kit этого checkout обновляется штатной командой после прохождения проверок.

## Паритет Windows

### Что есть сейчас

| | macOS | Windows |
|---|---|---|
| Локальный MCP | исполнитель `tools/codex-app-server-mcp` через Codex App Server, родные инструменты Codex | прежний мост из закреплённого архива `Windows-Codex-Local-2026-09-10.zip`, 38 самодельных инструментов |
| Нужен ли Codex | да | нет |
| Канал ChatGPT | Secure MCP Tunnel или свой сервер (VPS) | только Secure MCP Tunnel |
| Службы | LaunchAgent, исходник исполнителя синхронизируется из приложения, venv в данных приложения | распаковка архива, `setup.ps1`, собственный `control.py` архива |
| Настройки | раздел «Локальные инструменты macOS» с выбором канала; папка runtime не задаётся | раздел «Локальные инструменты Windows»; папка runtime хранится в настройках и регистрации |

Закреплённый архив кроме прежнего моста содержит нужные Windows компоненты: MinGit, ripgrep, tunnel-client, uv; его `requirements.txt` называет тот же `mcp==1.28.1`, что и исполнитель macOS. В архиве есть готовый код Windows для списка окон, снимков и уведомлений (`server/windows_computer.py`, `server/windows_notify.ps1`).

Исходники Codex подтверждают, что нужное на Windows существует: `command/exec` с потоками и PTY (ConPTY) вне Windows-песочницы, оболочка PowerShell по умолчанию, `apply_patch.bat` в PATH процесса. На живой Windows это не проверялось.

### Что должно стать

- **Один исполнитель.** `server.py`, `app_server_client.py` и `control.py` работают на обеих платформах; отличия собраны в платформенных ветках: поиск Codex, оболочка по умолчанию (PowerShell на Windows), проверка `apply_patch`, определение типа и уменьшение изображения, список окон, снимки, уведомления, каталог состояния, запуск и опознание процессов, архив tunnel-client.
- **Один каталог.** Те же девять инструментов с теми же именами, параметрами, описаниями и форматом ответов. Различается только то, что различается в самих системах: оболочка и пути.
- **Одна доставка контекста.** Стартовое сообщение и правила сессии одинаковы; `LocalMcpClient` нигде не требует `workflow_context_recover`.
- **Одни каналы.** На Windows доступны Secure MCP Tunnel и свой сервер (VPS) с тем же переключателем в настройках; туннель VPS — тот же `ssh` с пробросом порта, за запуском и перезапуском следит служба Web Pilot вместо LaunchAgent.
- **Один жизненный цикл.** Приложение само ставит и запускает исполнитель из своего состава, без выбора папки; автозапуск при входе в систему; отказ запуска служб не закрывает приложение. Разделы настроек «Локальные инструменты» на обеих платформах показывают одно и то же: состояние MCP, канал и его переключатель.
- **Переход с прежнего runtime.** При первом запуске 0.6.96 на Windows прежний мост останавливается, его автозапуск убирается, настроенный туннель переносится, если у исполнителя своего нет. Папки пользователя вне данных приложения автоматически не удаляются.
- **Пакет.** Закреплённый архив остаётся источником MinGit, ripgrep, tunnel-client и uv; его состав и SHA-256 не меняются. Наложение правок на прежний мост (`patchWindowsBridgeSource` и связанное) удаляется.

### Как выполнено

**W001 — команды, патч, поиск Codex, статус.**

- Поиск Codex на Windows: явный путь и `CODEX_APP_SERVER_BIN`; `codex.exe` из PATH; родной `codex.exe` глобальной установки npm — `codex.cmd` там только запускает Node, поэтому исполняемый файл берётся из пакета платформы `@openai/codex-win32-x64` (или `-arm64` по архитектуре системы), в том числе когда `%APPDATA%\npm` нет в PATH; ссылка WinGet. Пути приложения ChatGPT на Windows добавлены по предположению и на живой системе не проверены. Раскладка пакета npm сверена с установленным на Mac Codex 0.160.0: `…/@openai/codex/node_modules/@openai/codex-<платформа>/vendor/<триплет>/bin/codex`.
- Оболочка: по умолчанию PowerShell 7, если установлен, иначе Windows PowerShell — тот же порядок, что у Codex. Аргументы строятся как в Codex (`codex-rs/core/src/shell.rs`): `-Command` при `login=true`, `-NoProfile -Command` при `login=false`, `cmd.exe /c`, для bash из Git — `-lc`/`-c`. Перед командой PowerShell ставится строка Codex, включающая вывод в UTF-8.
- **Отступление: `apply_patch`.** Codex кладёт в PATH `apply_patch.bat`, а пакетный файл принимает патч аргументом командной строки (`"codex.exe" --codex-run-as-apply-patch %*`). Многострочный патч так передать нельзя, и он не помещается в предел командной строки Windows (около 32 тысяч знаков; патч допускается до 1 МБ). Поэтому на Windows исполнитель запускает тот же `codex.exe` под именем `apply_patch` и подаёт патч на стандартный ввод — тем же кодом Codex, каким работает псевдоним на macOS. Способ проверен на Mac с родным исполняемым файлом Codex 0.160.0 (патч 64 КБ с кириллицей и папкой с пробелом в имени). На macOS путь через `command/exec` не менялся.
- Остановка App Server на Windows — `taskkill /T /F` по дереву процессов: групповых сигналов в Windows нет.
- Сервер MCP на Windows называется «Codex App Server Local Windows»; каталог состояния — `%LOCALAPPDATA%\WebPilotCodexExecutor`.

**W002 — изображения, окна, снимки, уведомления.**

- Тип изображения определяется по содержимому файла на обеих системах (раньше macOS вызывала `/usr/bin/file`): PNG, JPEG, GIF, WebP, TIFF, HEIC/HEIF/AVIF, BMP, ICO, PSD, ICNS, SVG. Текст и прочие файлы по-прежнему отклоняются.
- Уменьшение `view_image` на Windows — библиотека Pillow (`pillow==11.3.0`, ставится только на Windows): на Windows нет `sips`. Изображение не больше 1600 по длинной стороне возвращается без изменений байт в байт, большее уменьшается с сохранением формата. Ветка проверена на Mac с настоящей Pillow 11.3.0 во временном окружении (PNG 2000×10 → 1600×8, JPEG 4000×3000 → 1600×1200, повреждённый файл → «Image format is not supported»). Без Pillow инструмент отвечает понятной ошибкой, остальные инструменты работают.
- Список окон и снимки на Windows — код из закреплённого архива (`server/windows_computer.py`), перенесённый в `tools/codex-app-server-mcp/windows_desktop.py` без ввода и активации окон: только наблюдение, как на macOS. Поля ответа те же: `window_id`, `title`, `application`, `pid`, `rect`. Снимок окна делается через `PrintWindow`, при отказе — снимком области экрана под окном. `max_dimension`: 0 оставляет размер, иначе длинная сторона ограничивается диапазоном 100–5000.
- Уведомление о завершении хода на Windows — `windows_notify.ps1` из того же архива, запускается скрытым PowerShell; отказ запуска не ломает `turn_watchdog`.
- Проверено на Mac тестами с подменой платформы и подставным рабочим столом; сами вызовы Win32 и окно уведомления на Windows не запускались.

**W003 — службы на Windows: установка, запуск, туннель, автозапуск.**

- `control.py` один на обе системы; команды и JSON-ответы те же. Каталог состояния на Windows — `%LOCALAPPDATA%\WebPilotCodexExecutor`, порты те же (17852 и 17853).
- Компоненты из закреплённого архива (uv, tunnel-client, ripgrep, MinGit) распаковывает приложение (W004) в `runtime\tools` и записывает пути в `runtime\tools.json`. `control.py` принимает только пути внутри этой папки. `setup` ставит собственный Python 3.13 и закреплённые пакеты через uv из архива (`--managed-python`, `--no-config`), tunnel-client берёт из архива и ничего не скачивает сам. Первый раз нужен интернет: uv загружает Python.
- Командам исполнителя в PATH доступны Python окружения, MinGit, ripgrep, uv и папка глобальных установок npm (там лежит Codex CLI).
- Ключ туннеля хранится зашифрованным для текущего пользователя (DPAPI), доступ к папке `private` ограничивается пользователем и системой (`icacls`). Так же был устроен прежний Windows-runtime; его ключ переносится один раз расшифровкой и повторным шифрованием, прежние файлы не меняются.
- Процессы запускаются без окна и консоли, опознаются по времени запуска, пути и командной строке (psutil вместо `/bin/ps`), останавливаются деревом: `python.exe` окружения — это пусковой файл, настоящий интерпретатор и Codex App Server — его потомки. `psutil==7.2.2` ставится только на Windows.
- Автозапуск — команда `autostart --state on|off|status`: значение `ProjectWebPilotCodexExecutor` в разделе `HKCU\…\Run` (права администратора не нужны) запускает `pythonw.exe` с небольшим пусковым файлом в `private`, который выполняет `selector-start` и пишет результат в `autostart.log`. Учётных данных в пусковом файле нет. На macOS команда отвечает отказом: там автозапуск по-прежнему ставит приложение через LaunchAgent.
- Окно ввода ID и ключа туннеля на Windows — форма Windows Forms из прежнего `windows-first-run.py`; текст сообщения и сам сценарий передаются в PowerShell в закодированном виде, ключ читается из вывода и никуда не пишется. Коды ошибок получают приставку `WINDOWS_` вместо `MAC_`.
- Проверено на Mac тестом с подменой платформы, подставными psutil и реестром, подставным шифрованием: пути, состав PATH, отказ на путь вне папки компонентов, хранение ключа, перенос прежнего туннеля, запись и сверка процесса, остановка дерева, автозапуск, команды `setup`, окно ввода. Настоящие вызовы DPAPI, `icacls`, реестра, блокировки `msvcrt` и uv на Windows не запускались.

**W004 — Web Pilot на Windows работает через исполнитель; переход с прежнего runtime.**

- Приложение на Windows создаёт те же объекты, что на macOS: `CodexAppServerRuntime`, `MacSelectedRuntime`, `MacRuntimeSwitcher` (имена классов оставлены, им передаётся платформа). `McpRuntime` и `WindowsRuntimeBootstrap` удалены; папка runtime из настроек больше не читается и не записывается, состояние исполнителя — всегда `%LOCALAPPDATA%\WebPilotCodexExecutor`.
- **Компоненты.** На Windows нет системного Python, поэтому до первого вызова `control.py` приложение само распаковывает из закреплённого архива uv, tunnel-client, ripgrep и MinGit (`WindowsExecutorBootstrap`) и создаёт собственный Python командой `uv venv`. Архив читает собственный небольшой разборщик ZIP (`src/zip-archive.mjs`) вместо PowerShell `Expand-Archive`: сверяются SHA-256 всего архива и каждого вложенного архива по списку `vendor/manifest.json`, CRC-32 каждого файла, имена файлов не могут выйти за папку. Прежний мост из архива не распаковывается. Распаковка проверена на Mac на настоящем закреплённом архиве (размеры `uv.exe`, `tunnel-client.exe`, `cloudflared.exe`, наличие `git.exe`, `sh.exe`, `rg.exe`).
- Для подключения и создания проектов достаточно распакованных инструментов: Git для Workflow Kit берётся из них без запуска служб и без Codex.
- **Отступление от W003: tunnel-client не копируется.** Официальный архив tunnel-client для Windows содержит рядом `cloudflared.exe`; чтобы не разлучать их, на Windows tunnel-client запускается там, куда распакован (`runtime\tools\tunnel-client`). Признаком завершённой установки на Windows служит запись `runtime\setup.json` с хешем `requirements.txt`: `status` сообщает `setup_complete`, и приложение повторяет `setup`, пока тот не завершился, а также после смены закреплённых пакетов. На macOS признак прежний — скопированный tunnel-client.
- Службы на Windows запускаются с рабочей папкой состояния, а не исходника: Windows не даёт заменить папку, которая служит рабочей для запущенного процесса, а исходник исполнителя заменяется при каждом обновлении.
- **Codex.** Добавлен путь официального установщика Codex для Windows (`%LOCALAPPDATA%\Programs\OpenAI\Codex\bin\codex.exe`, команда из README Codex). Если Codex не найден, мастер первого запуска показывает эту команду; отказ не закрывает приложение, следующая проверка повторяет запуск.
- **Переход.** При первом запуске 0.6.96 прежний мост останавливается его же сценарием `windows-control.py` (он остаётся в пакете только ради этого и останавливает лишь процессы, которые сам записал), значение автозапуска `ProjectWebPilotMCP` удаляется, копия моста в данных приложения удаляется; затем `configure-selector` переносит туннель. Папка моста, которую выбирал пользователь, и его состояние с прежним ключом не трогаются. Если остановка не удалась, запуск исполнителя не блокируется, а очистка повторяется при следующем запуске — как на macOS. Следствие: при неудачной остановке прежний tunnel-client и новый могут некоторое время работать с одним туннелем; на Windows это не проверялось.
- Автозапуск на Windows включается после успешного запуска служб и здесь не выключается: неудачный запуск не отменяет прежнюю запись.
- `LocalMcpClient` умеет только `initialize` и `tools/list`: оболочка не вызывает инструменты. По умолчанию требуется один инструмент — `bridge_status`.
- **Настройки и мастер.** Раздел «Локальные инструменты» один на обе системы; разделы «Локальные инструменты Windows» с кнопками установки и два действия IPC удалены, `windows-first-run.py` удалён (окно ввода — общий `tunnel_prompt.py`). Имя подключения в мастере — «Codex App Server Local Windows»; тем, у кого уже есть «Codex Local Windows MCP» с этим туннелем, мастер советует не создавать новое, а обновить список инструментов.
- Проверено на Mac: модульные тесты с подменой платформы, настоящий архив, Electron smoke. На Windows не запускалось ничего.

### Следствия, которые нужно знать заранее

- На Windows появляется новое требование: установленный Codex (CLI или приложение ChatGPT), как на macOS.
- Прежний Windows-runtime убирается без запасного переключателя. Откат — установка 0.6.95.
- Ни один шаг Windows нельзя исполнить на Mac. Проверяются модульные тесты с подменой платформы и состав пакета (`verify:win`); настоящая проверка — на Windows пользователя. До неё Windows-часть релиза считается непроверенной.


## Границы

- Одна микрозадача на ход остаётся.
- Чтение по запросу агента остаётся за инструментами; содержимое файлов от лица пользователя посреди хода не подставляется.
- Запасной вариант доставки — вложение текстовым файлом; в этот релиз не входит и включается, только если полноразмерная вставка даст проблемы.
- Экспорты `src/chatgpt-dom.mjs`, `src/chatgpt-composer.mjs`, `src/chatgpt-experience.mjs` и формат `pageScript` не меняются (контракт Web Pilot Sidebar).
- Имена, параметры, описания и поведение девяти инструментов на macOS, `codex-tools.lock.json` и канал VPS на macOS не меняются.
- Состав и SHA-256 закреплённого Windows-архива не меняются.
- Папки пользователя вне данных приложения автоматически не удаляются; адрес коннектора и ключ туннеля не попадают в репозиторий, журналы и чат.
- В уже привязанные чаты ничего автоматически не отправляется.

Установить 0.6.96, полностью выйти из Web Pilot и открыть снова (на macOS ⌘Q), в ChatGPT в настройках коннектора нажать «Обновить инструменты». На Windows перед этим должен быть установлен Codex.

## Риски

- Большая вставка в начале каждой сессии по времени совпадала с жалобами OpenAI на лимиты. Связь не доказана; если жалобы вернутся, включается запасной вариант с вложением.
- Чаты, начатые в режиме MCP, сохранили отметку доставки другого вида. Они остаются привязанными и показываются как «Сохранённый чат проекта»; контекст в них передаётся только явным обновлением («Обновить контекст»). Подготовленное, но не отправленное короткое стартовое сообщение прежнего вида не отправляется: его заменяет полный пакет.
- AutoPlan — чувствительный механизм (три контракта и разбор инцидента 03.10.2026). Меняется только текст сообщения, логика пауз и контрольных точек не трогается.

- Windows-часть написана без возможности запуска: первая живая проверка почти наверняка найдёт дефекты. Пока приёмка на Windows не пройдена, рабочей версией для Windows остаётся 0.6.95.
- Объём релиза вырос в несколько раз. Если Windows-часть затянется, её можно выпустить следующим релизом, не задерживая macOS и Kit; это решение пользователя.
- Объединение меняет сборочную цепочку (подготовка runtime Kit, проверка состава пакета). Оно выполняется первой задачей, до остальных правок, чтобы поломку цепочки нельзя было спутать с другими изменениями; настоящая сборка всё равно случится только в T006.
- Перевод прежнего репозитория в архив на GitHub обратим владельцем, но после него в старый репозиторий нельзя отправлять изменения: это делается последним шагом, после публикации.
