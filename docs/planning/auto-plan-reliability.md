# Автовыполнение без ложных остановок

Исторический документ архитектуры 0.6.73–0.6.76. С 0.6.77 действующий контракт — [клиентское автопродолжение](auto-plan-client-driven-refactor.md): переключатель не отправляет инструкцию, footer/вопрос не управляет Send. Содержание ниже сохраняет решения и evidence прежнего scope.

## Результат

Режим «Автовыполнение» сохраняет существующую схему: после завершения одной микрозадачи и её коммита Web Pilot проверяет фактический current plan и автоматически отправляет точное «Продолжай». Изменения этого scope устраняют ложные остановки, обнаруженные в реальной работе 02.10.2026, не превращая AutoPlan в отдельного агента и не добавляя новый планировщик.

После исправления пользователь не должен вручную писать «Продолжай» в случаях, когда агент способен продолжать самостоятельно. Остановка с ожиданием пользователя допустима только тогда, когда действительно требуется информация, выбор или решение пользователя.

Уточнение пользователя 02.10.2026: «Автовыполнение» — постоянный переключатель приложения. Пользователь один раз включает его; положение сохраняется до явного выключения, включая полный выход и новый запуск приложения. Ожидание и окончание плана не равны выключению режима.

## Подтверждённые причины текущих остановок

Диагностика 02.10.2026 показала, что автоматическое «Продолжай» само по себе работает, но цикл часто прерывается после этого:

- агент завершает ответ сигналом «Нужен ваш ответ.» даже при технической ситуации, которую можно исследовать и исправлять самостоятельно;
- watchdog через 3 минуты без наблюдаемого изменения текста переводит AutoPlan в paused, хотя ChatGPT всё ещё busy и позже продолжает выдавать результат;
- при наличии пользовательского черновика ChatGPTComposer правильно возвращает DRAFT_PRESENT и не затирает текст, но AutoPlan после этого полностью приостанавливается;
- состояние «Отправляем „Продолжай“…» существует слишком коротко, поэтому пользователь практически не видит факт автоматического продолжения;
- diagnostics пишет phase=paused без машинно-различимой причины, что затрудняет разбор реальных сбоев.

## Требуемое поведение

### 1. Сигнал «Нужен ваш ответ.»

Стартовая инструкция AutoPlan должна однозначно требовать этот сигнал только тогда, когда без информации, выбора или решения пользователя корректно продолжать невозможно.

Техническая ошибка, упавший тест, несовместимость, проблема сборки, Git/MCP или другая исследуемая агентом ситуация не являются основанием автоматически звать пользователя. Если агент может продолжить диагностикой или исправлением, итоговый сигнал остаётся «Готов продолжать.».

Существующие ограничения сохраняются: не более одной микрозадачи за turn, проверка и commit перед DONE, безопасная контрольная точка для длинной работы, запрет модельного делегирования без прямого поручения.

### 2. Watchdog не останавливает работающий turn

Три минуты без наблюдаемого текстового продвижения при busy=true становятся диагностическим предупреждением, а не причиной pause.

Web Pilot:
- не нажимает Stop;
- не отправляет повторное сообщение;
- не выключает AutoPlan;
- сохраняет текущий run и продолжает ждать штатного завершения turn;
- снимает/обновляет предупреждение при следующем наблюдаемом продвижении.

Терминальная ошибка связи, ручной Stop и другие уже существующие реальные причины остановки остаются отдельными.

T002 сохраняет текущий run и его поколение при busy=true; UI показывает предупреждение, diagnostics содержит STALL_WARNING. Следующее изменение содержимого снимает предупреждение и снова включает watchdog; штатное завершение ответа проходит прежнюю проверку плана и автоматическое «Продолжай». Если busy и контрольная точка так и не появились, прежняя безопасная остановка сохраняется с причиной NO_CHECKPOINT.

### 3. Черновик не выключает AutoPlan

Если автоматическое «Продолжай» не отправлено из-за DRAFT_PRESENT:
- черновик пользователя не изменяется;
- режим остаётся включённым, но suspended;
- UI сообщает, что ожидается отправка пользовательского сообщения;
- после фактической ручной отправки сообщения в том же документе режим возобновляется через существующий resume-flow без дополнительного автоматического «Продолжай».

Это тот же принцип, который уже применяется после ручного ввода/Stop/вопроса агента.

T003 обрабатывает только подтверждённый deferred/DRAFT_PRESENT как ожидание пользовательского Send. Текст остаётся у Composer без изменений; AutoPlan хранит suspended run и показывает включённую кнопку. Ревизия ручной отправки фиксируется до проверки поля, чтобы не потерять сообщение, отправленное во время асинхронной проверки. После него проверяется current plan и возобновляется наблюдение ответа без дополнительной отправки. Неизвестный исход Send не превращается в возобновляемое ожидание черновика.

### 4. Видимость автоматического продолжения

После успешной автоматической отправки «Продолжай» состояние sidebar должно оставаться понятным пользователю, например:

«Автовыполнение: автоматически отправлено „Продолжай“ №N — агент работает.»

Не требуется хранить историю текста чата или новый журнал действий. Достаточно счётчика текущего запуска и понятного статуса.

T004 считает только подтверждённую отправку точного «Продолжай»: стартовая инструкция, ручное сообщение, deferred и unknown счётчик не увеличивают. Sidebar добавляет постоянную строку с номером к текущему состоянию, поэтому она остаётся видимой при проверке, работе, предупреждении, паузе и завершении. При смене разговора или scope чужой счётчик не показывается; новый фактический запуск начинает отсчёт заново.

### 5. Диагностика причин

События AutoPlan должны записывать безопасный reason code для значимых остановок/ожиданий, без текста разговора. Минимально различать:
- AGENT_WAIT;
- DRAFT_PRESENT;
- MANUAL_STOP;
- MANUAL_INPUT;
- CONNECTION_ERROR;
- PLAN_CHANGED_OR_TRANSACTION;
- SEND_UNKNOWN;
- STALL_WARNING;
- NO_CHECKPOINT.

Набор кодов может быть расширен при реализации, если это требуется существующими ветками состояния.

T004 передаёт reason вместе с событиями state для каждого pause и STALL_WARNING. Дополнительные причины: MANUAL_OFF, DOCUMENT_RELOADED, DOCUMENT_CHANGED, SELECTED_CONTEXT_CHANGED, PAGE_NOT_READY, PLAN_UNAVAILABLE, PLAN_INACTIVE, PLAN_READ_ERROR, NO_PLAN_PROGRESS, SEND_NOT_SENT, SEND_ERROR и CHECK_OR_SEND_ERROR; завершение обозначено PLAN_COMPLETED. В логе остаются только фаза, безопасные коды, числовые значения и вид отправки; сообщения UI, текст разговора, URL и секреты в новые поля не записываются.

### 6. Постоянный выбор пользователя

Сохранение положения кнопки реализуется отдельной задачей T006 через существующие настройки приложения, без нового хранилища.

- Только явное включение или выключение пользователем меняет сохранённый выбор.
- Работающий ответ, пауза, вопрос, draft, watchdog, смена разговора и завершённый план не выключают переключатель.
- После перезапуска или reload Web Pilot проверяет фактический current plan и выбранный разговор; подходящий незавершённый план продолжается без повторного нажатия кнопки.
- При busy=true приложение ждёт окончания ответа; настоящий вопрос ждёт ответа пользователя, черновик сохраняется, неизвестный исход Send не повторяется вслепую.
- При всех DONE режим остаётся включённым, но новых сообщений для этого завершённого плана нет.

T006 отделяет сохранённый `autoPlanEnabled` от текущей фазы AutoPlan. Настройки приложения атомарно сохраняют оба положения кнопки; пауза, выбор разговора, reload и завершение плана не меняют этот выбор. В том же `settings.json` хранится только отметка последнего Send (контекст, непрозрачный идентификатор ответа, sending/sent), без текста диалога. Она записывается до click: неопределённый исход не повторяется после перезапуска. Восстановление проверяет Git-план и страницу, принимает работающий turn без Send, сохраняет ожидание вопроса и draft, а новую подтверждённую контрольную точку продолжает точным «Продолжай». Старый footer перед более новым пользовательским сообщением не считается новой контрольной точкой. Проверка использует настройки с диска, отдельные свежие Electron-процессы для on/off и настоящий Chromium reload; live-приёмка остаётся пользовательской.

В обычном цикле агент выполняет одну микрозадачу, проверяет её, фиксирует commit и заканчивает ответ. Web Pilot проверяет current plan и самостоятельно отправляет точное «Продолжай». Длинная незавершённая работа может закончить ответ на безопасной точке без DONE; следующий turn продолжает её, проверив уже запущенный процесс.

## Фиксация реализации T006 / T008

Коммит T006 `9529607` сохранил план, описание поведения и тест идентичности контрольной точки в `tests/page-state.test.mjs`. Node suite и Electron smoke прошли на полном рабочем дереве, однако восемь файлов реализации и интеграционных проверок остались вне этого коммита: они были изменены до регистрации `task:start`, поэтому Workflow Kit исключил их автоматически. Правки принадлежат этой работе и сохранены без потерь.

Отдельная T008 фиксирует эти исходники и проверки явным списком `commit --input`, вместе с этим пояснением. Сборка T007 зависит от T008; реализацию нельзя считать поставленной только по прежнему коммиту T006. После фиксации должны пройти назначенные unit/smoke и остаться чистое рабочее дерево.

## Проверка

Обязательны существующие Node tests и Electron smoke.

T005 объединяет сценарии в изолированном Electron: настоящий sidebar → IPC → AutoPlan → Composer → preload observer работает с частично выполненным Git-планом для ChatGPT и Work. Проверяются автоматическое «Продолжай», сохранение draft и native Send, ручной Stop, вопрос «Нужен ваш ответ.» с последующим пользовательским решением, busy watchdog и завершение всех задач. Отдельные реальные DOM-сценарии без итогового сигнала и с connection alert проверяют отсутствие повторной отправки; неизвестный исход Send и смена контекста дополнительно покрываются Node suite. Это fixture-проверка, а не приёмка живого ChatGPT.

Проверки должны воспроизводить именно наблюдавшиеся сценарии:
- «Готов продолжать.» → план незавершён → автоматическое «Продолжай» действительно отправлено;
- busy остаётся активным дольше watchdog-порога → AutoPlan не переходит в paused;
- после watchdog-предупреждения последующий прогресс и завершение turn по-прежнему приводят к обычному продолжению;
- DRAFT_PRESENT не стирает черновик и оставляет режим способным возобновиться после ручной отправки;
- «Нужен ваш ответ.» по-прежнему ждёт пользователя и после его сообщения корректно возобновляется;
- видимый статус содержит устойчивый факт последней автоматической отправки, а diagnostics — reason code для пауз/предупреждений;
- смена разговора, connection error, неизвестный исход Send и завершённый план не вызывают небезопасную отправку;
- оба положения кнопки сохраняются после выхода и повторного запуска; подходящий незавершённый план возобновляется без повторного включения и дублирования сообщений.

## Границы

- Не переписывать AutoPlan с нуля.
- Не добавлять второй агент, модельный API, новый сервис или периодический polling Git.
- Не затирать пользовательский draft ради автоматизации.
- Не ослаблять проверки фактического current plan и Workflow Kit transaction.
- Не автоматизировать нажатие нативных safety/permission диалогов ChatGPT.
- Изменения относятся к Workspace & Sessions / AutoPlan и существующему ChatGPTComposer/PageStateSource только в необходимом объёме.
- Парная сборка нового release выполнена в T007. Отдельное прямое поручение пользователя на публикацию получено 02.10.2026; GitHub-публикации выполняются T010–T012 после T009 и до финальной DOCS.
