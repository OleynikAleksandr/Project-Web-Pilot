# Проверки и выпуск надёжного завершения

## 3. Принадлежность и каскадная очистка исполнителей

Исполнитель — дочерняя запись проекта, даже если у него отдельная папка. Сохранить parentProjectId вместе с parentWorkspace, scope, assignmentId, originSessionId в проекте/сессии. Сверять с назначением Kit и identity родителя при создании, восстановлении, проекции, архиве и удалении. Не выводить исполнителя отдельным обычным проектом при отсутствии/архивировании родителя.

Миграция старых записей — только по доказательствам: живой совпадающий родитель и assignment binding/история Git. Совпадение пути/имени недостаточно при повторной папке. Неподтверждённая связь показывается отдельным понятным состоянием восстановления, не удаляется автоматически и не назначается новому владельцу. Отсутствующий родитель не даёт права удалять чужую папку.

После подтверждённого удаления родителя единая операция очищает его дочерние локальные записи, живые runtime ссылки, назначения/checkpoints/разрешения/диагностику/архив и доказанно принадлежащие worktree. Использовать существующий журнал и последовательную остановку очереди, сохранять список конкретных identities до удаления файлов, продолжать идемпотентно после restart. Защиты активности, незавершённой работы, symlink/подмены пути и чужого проекта сохраняются. Не удалять облачные чаты и общий профиль ChatGPT. Чужие одноимённые проекты и новая identity в прежней папке сохранены.

Проверить archive -> delete, missing parent, несколько исполнителей, смешанные legacy/new записи, restart посреди очистки, заменённый worktree, повторную папку. Не исправлять вручную данные завершённого пользовательского теста.

## 5. Правила планировщика и выпуск

Обновление Kit 1.7.2 явно поддерживает upgradeFrom 1.7.1; kit-check проверяет реальный install --update с этой версии. DOCS включает first-run-onboarding, parallel-assignments и runtime-lifecycle. Перед удалением тестового проекта пользователь поручает остановить оставленный сервер по его session ID и дождаться подтверждённого завершения; живой сервер не удаляется вместе с файлами молча.

В исходных инструкциях Kit закрепить выбор декомпозиции по проверяемому результату, смысловым зависимостям, контрактам, пересечениям записи, размеру необходимого контекста, рискам интеграции и стоимости координации/проверок. Нет нормы числа файлов/строк/задач или выдуманного порога выгоды. Снимок parallel — возможность, не приказ; аргументировать решение. Benchmark не запускать; реальное использование parallel в этой сессии запрещено. Kit обновлять из packages/workflow-kit штатным install --update, управляемую .harness/kit не править вручную.

Перед delivery обновить версии приложения/Kit, lockfiles и evidence полной конфигурацией config:apply. Выполнить регрессию и актуализировать все действующие документы в DOCS; перенести действующий контракт этой спецификации в docs/modules и удалить временную spec с Git-ссылкой в required-контексте по правилам Kit. README отражает новый выпуск. Правило полного выпуска для продуктовых задач закрепить в постоянных правилах проекта без изменения глобальных инструкций или чужих репозиториев.

Delivery отдельно: paired-release при commit запускает единственную парную сборку; затем установка готового staging в /Applications с сохранением identity/подписи, без пересборки и перезапуска работающего приложения; затем шесть assets, manifest, tag на sourceCommit, main и GitHub Release. Перед записью проверять назначения/symlink, секреты не выводить. Ошибка сборки не разрешает обход проверок или неподтверждённую публикацию. Повторное использование только проверенной готовой сборки.

## 6. Матрица приёмки и задачи

T001 — lifecycle MCP + read_only запуск + проекция блокировок, включая настоящий отказ записи и доступность сервера на Mac, ошибки/restart/legacy.
T002 — финальное поручение/наблюдение ответа/интеграция, после T001. Сценарии: последний READY до DONE; all DONE/OFF при pending; busy/draft/Stop; duplicate/restart/sending unknown; неверный чат/два проекта; конфликт/ошибка проверки без второго merge.
T003 — ownership и каскадная очистка, независима по смыслу от T002, выполняется последовательно по поручению пользователя.
T004 — весь согласованный сайдбар/переключатель/контекст; после T003 для точной проекции исполнителей.
T005 — сквозная регрессия, правила планирования и подготовка версий/Kit; зависит от T001–T004. Реальные временные Git-worktree + T001->T002/T003/T004->T005 и сервер, контроль main и один финальный ответ TEST FIXTURE, AutoPlan OFF. Это тест алгоритма, не делегирование модели и не реальная parallel-реализация.
DOCS — действующие документы и инструкция пользовательского повторного теста, после T005.
T006 — единственная парная сборка 0.6.110 после DOCS.
T007 — установка готового macOS выпуска после T006.
T008 — публикация GitHub после T007, окончательная сверка после push.

Проверки из существующей конфигурации: unit-all для кодовых задач, executor-channel для MCP, project-lifecycle для удаления, electron-smoke для UI и сквозной регрессии, kit-check и codex-tools-live перед DOCS. Delivery: paired-release / release-installed / github-release. Предварительные повторы полных suite без изменения относящихся условий не нужны, назначенные проверки исполняет commit.

Чистый повторный пользовательский тест после полного выхода и запуска 0.6.110: создать временный проект с тремя независимыми инструментами и финальной задачей, включить AutoPlan, проверить промежуточные интеграции, оставленный read_only сервер, автоматическое возвращение в основной чат и один итоговый ответ без «Продолжай» пользователя. Проверить переключение второго проекта/черновик/перезапуск, удалить первый проект через подтверждение и убедиться, что его исполнителей нет, сосед сохранён. Не использовать реальные проекты для разрушительных сценариев. До этого теста не считать parallel принятым и не использовать его для дальнейшей реальной работы.

Автоматические fixtures, HTTP, упаковка и Mac sandbox не подтверждают живой ChatGPT/Claude, native Windows или чистую ОС. Указывать фактические ограничения в финальном отчёте. План остаётся READY_FOR_ACCEPTANCE до прямой пользовательской приёмки.
