# Родные инструменты Codex в MCP на macOS — релиз 0.6.92

Поручение пользователя 05.10.2026: изначальная задумка была не изобретать собственные инструменты, а дать веб-модели инструменты самого Codex — напрямую или, если прямого пути нет, через Codex App Server. Прежний этап (scope 035) заменил исполнителя на App Server, но каталог оставил самодельным. Решения пользователя: начать с macOS; перейти на вариант «большая часть инструментов — родные Codex»; корзину (удаление с возвратом) оставить; в ChatGPT он работает в режиме «Allow all actions». Windows — отдельным этапом после проверки на macOS.

## Что показал осмотр (main `7d3aed8`, 0.6.91; Codex CLI 0.160.0)

- `tools/codex-app-server-mcp/server.py` отдаёт 38 инструментов. Из Codex App Server используются четыре метода: `command/exec`, `fs/readFile`, `fs/writeFile`, `fs/readDirectory`. Остальное — собственный код: поиск, git, чтение и запись файлов, замена текста, бинарные правки, процессы, корзина. `apply_patch` в каталоге — это `git apply` обычного diff, а не патч Codex. Этот каталог повторяет каталог удалённого Codex Local Mac: в спецификации scope 035 записано требование «поверхность не уже Codex Local Mac».
- Готового сервера от OpenAI нет. `codex mcp-server` удалён (в 0.160.0 команды нет, документация отправляет на App Server). Пакет `@openai/codex-shell-tool-mcp` (MCP-сервер с одним инструментом `shell`) был экспериментальным, рассчитан на Codex как клиента, не обновляется с марта 2026 и удалён из репозитория.
- В репозитории `openai/codex` (Apache 2.0) модель действует локально тремя инструментами: `exec_command` с парным `write_stdin`, `apply_patch`, `view_image`. Поиск — обычный `rg` через команду. Остальные инструменты (план, вопросы пользователю, запуск агентов) обслуживают цикл самого Codex. Исполнители инструментов находятся в `codex-core` и связаны с сессией и подтверждениями; сборка из исходников означала бы свой форк (128 крейтов, с марта версия выросла с 0.116 до 0.160).
- Всё нужное уже есть в установленном бинарнике и обновляется вместе с ним. Проверено на этом Mac без thread и turn: `command/exec` принимает `tty`, `streamStdin`, `processId` и имеет парные `command/exec/write` и `command/exec/terminate`; внутри выполнения команды в `PATH` лежат родной `apply_patch` (патч в формате Codex применён во временной папке: файл изменён, второй создан) и `rg` — и в login-оболочке, и в обычной.
- Определения инструментов Codex — это код (`codex-rs/core/src/tools/handlers/shell_spec.rs`, `view_image_spec.rs`) и одна грамматика (`codex-rs/core/assets/tools/apply_patch.lark`). Команды, которая выгружала бы их из бинарника, нет. Теги версий в репозитории есть (`rust-v0.160.0`).
- Текущий `run_command` обрезает вывод на 120 000 символов, а ChatGPT показывает модели около 10 000 токенов одного результата: длинный вывод сейчас режется уже на стороне ChatGPT. У `exec_command` в Codex бюджет вывода по умолчанию — те же 10 000 токенов.
- От имён удаляемых инструментов вне `server.py` и его теста ничего не зависит: приложение требует от сервера только `bridge_status` и `workflow_context_recover`.

## Результат

1. **Каталог macOS — 13 инструментов вместо 38.**

   | Инструмент | Происхождение |
   | --- | --- |
   | `exec_command`, `write_stdin`, `apply_patch`, `view_image` | форма Codex 0.160.0 |
   | `workflow_context_recover`, `bridge_status`, `turn_watchdog` | наши, без изменений |
   | `computer_list_windows`, `computer_capture_screen`, `computer_capture_window` | наши, без изменений |
   | `delete_path`, `list_trash`, `restore_trash` | наши, без изменений — корзина по решению пользователя |

   Удаляются 28 имён: `list_drives`, `file_info`, `list_directory`, `read_file`, `read_binary`, `search_files`, `search_text`, `make_directory`, `write_file`, `write_binary`, `patch_binary`, `replace_text`, `copy_path`, `move_path`, `run_command`, `run_command_batch`, `start_process`, `process_status`, `read_process_output`, `list_processes`, `stop_process`, `list_repository_tree`, `read_repository_file`, `search_repository`, `git_status`, `git_diff`, `git_log`, `git_show`. Прежний `apply_patch` (`git apply`) заменяется родным под тем же именем. Всё, что делали удаляемые инструменты, агент делает командами: `rg`, `git`, `cat`, `sed`, `ls`, `mkdir`, `cp`, `mv`.

2. **`exec_command`** — имя, параметры и текст ответа как в Codex. Параметры: `cmd` (обязателен), `workdir` (обязателен — см. «Отступления»), `shell`, `login`, `tty`, `yield_time_ms`, `max_output_tokens`. Команда запускается через `command/exec` как `[оболочка, -lc или -c, cmd]`: оболочка по умолчанию — оболочка пользователя, `login` по умолчанию включён. Ждёт до `yield_time_ms` (по умолчанию 10 000, от 250 до 30 000 мс). Если процесс завершился — возвращает код выхода и вывод; если ещё работает — номер сессии. Ответ — текст в формате Codex: `Chunk ID`, `Wall time`, `Process exited with code N` либо `Process running with session ID N`, `Original token count`, `Output:`. Вывод обрезается по бюджету токенов с сохранением начала и конца.

3. **`write_stdin`** — `session_id` (обязателен), `chars`, `yield_time_ms`, `max_output_tokens`. Пишет в stdin работающей сессии (`command/exec/write`) и возвращает новый вывод в том же формате; пустой `chars` — опрос без записи. `yield_time_ms` по умолчанию 250 мс: непустая запись clamp-ится к 250–30000 мс, пустой poll — к локальному диапазону 5000–60000 мс. Сессии с `tty` принимают управляющие символы, в том числе Ctrl-C. Неизвестная или завершённая сессия — ошибка с понятным текстом.

4. **`apply_patch`** — `patch` и `workdir` (оба обязательны). Исполняет родной `apply_patch` Codex внутри `command/exec`, патч передаётся через stdin. Формат — Codex (`*** Begin Patch` … `*** End Patch`; добавление, удаление, изменение и перенос файла), описание формата в подсказке инструмента взято из грамматики Codex. Пустой патч, патч без `*** Begin Patch`, патч больше 1 МБ и отсутствующая папка отклоняются до запуска. Ошибка самого `apply_patch` возвращается его текстом. Если в установленном Codex команды `apply_patch` нет, инструмент отвечает отдельной понятной ошибкой, а `bridge_status` показывает это заранее.

5. **`view_image`** — `path`. Возвращает изображение с диска так же, как снимки экрана: уменьшенным до 1600 точек по большей стороне. Отсутствующий файл, не изображение, файл больше 20 МБ и путь к ключам и учётным данным отклоняются.

6. **Подсказки агенту.** В `instructions` сервера (после неизменённых первых 512 символов) и в правила сессии добавляется короткий текст из базовых инструкций Codex и наше правило: искать через `rg`, файлы править через `apply_patch` и не перечитывать их после успешного патча, удалять через `delete_path`, а не `rm`.

7. **Сверка с версией Codex.** `tools/codex-app-server-mcp/codex-tools.lock.json` хранит версию Codex, с которой сверены определения, тег репозитория и SHA-256 трёх исходных файлов определений. `npm run check:codex-tools` скачивает эти три файла по тегу установленной версии Codex и сравнивает: совпало — код 0; расхождение — код 1 и имена изменившихся файлов; нет сети или тега — код 2 с причиной. `bridge_status` показывает закреплённую и установленную версии Codex, совпадают ли они и доступен ли `apply_patch`. Определения в каталоге сами не меняются: расхождение — сигнал пересмотреть их и обновить lock-файл. Исполнители (команды, патч, поиск) обновляются вместе с Codex без нашего участия.

8. **Windows не меняется**: прежний каталог Codex Local Windows и его правила.

9. Релиз **0.6.92**: версия → DOCS → парная сборка → установка в `/Applications` → GitHub Release (шесть файлов) и синхронизация `main`.

## Отступления от формы Codex и их причины

- **`workdir` обязателен** у `exec_command` и `apply_patch`; в Codex он необязателен и берётся из thread. У MCP нет рабочей папки разговора, а «проект, открытый в Web Pilot» может смениться, пока агент продолжает работу в чате другого проекта. Команда или патч в чужом проекте хуже лишнего параметра; вызов без `workdir` получает ошибку с объяснением.
- **Нет параметров подтверждения и песочницы** (`sandbox_permissions`, `justification`, `prefix_rule`) и `environment_id`. Подтверждений в MCP нет; команды исполняются с правами пользователя, как нынешний `run_command`.
- **`apply_patch` — функция со строкой `patch`.** В Codex это инструмент свободного формата с грамматикой; MCP описывает только функции с JSON-параметрами.
- **`max_output_tokens` не больше 10 000**, сколько ChatGPT показывает модели из одного результата. Токены считаются как байты, делённые на четыре, как в Codex.
- **Пустой опрос `write_stdin` ждёт от 5 до 60 секунд** (в Codex до 300): вызов через туннель не должен висеть дольше; нынешний проверенный предел одной команды — 120 секунд.
- **`view_image` без параметра `detail`.**
- **Ответы — текст без структурированной копии**, иначе клиент показывает модели содержимое дважды.

## Исправление 0.6.93 — stdin-контракт команд

Пользовательская проверка уже выпущенной 0.6.92 выявила один дефект нового `exec_command`: `LocalFacade.exec_command` всегда запускал `command/exec` с `stream_stdin=True`. Поэтому обычная `tty=false` команда получала открытый stdin, и `rg -n "add"` без пути, `grep`, `cat` и другие stdin-aware программы могли ждать ввод вместо обычного завершения. Это расходилось с закреплённым Codex `rust-v0.160.0`: в `process_manager.rs` non-TTY процесс создаётся с закрытым stdin (`stdin_open: tty`), запись процесса хранит `tty`, а `write_stdin` для non-TTY разрешает только одиночный `U+0003`; любой другой непустой ввод возвращает `stdin is closed for this session; rerun exec_command with tty=true to keep stdin open`.

Контракт 0.6.93:

- `exec_command(..., tty=false)` запускает App Server с закрытым stdin; `tty=true` по-прежнему держит stdin открытым и принимает обычный `write_stdin`.
- Сервер хранит для каждой продолжающейся command session и cursor, и `tty`. Пустой `write_stdin` остаётся опросом для обоих режимов.
- Для `tty=false` непустой `write_stdin` принимает только точный `U+0003`: MCP вызывает `command/exec/terminate`, возвращает обычный формат завершённой команды и закрывает сессию. Любые другие символы отклоняются приведённым выше текстом Codex без остановки процесса; следующий пустой poll продолжает работать.
- `yield_time_ms` и `max_output_tokens` больше не отклоняются только из-за выхода за диапазон: числовые значения приводятся к допустимому диапазону. Для `exec_command` `yield_time_ms` — 250–30000 мс. Для `write_stdin` default — 250 мс: непустой `chars` clamp-ится к 250–30000 мс, пустой poll — к локальному диапазону 5000–60000 мс. `max_output_tokens` — 1–10000. Строка вместо числа остаётся ошибкой.
- `exec_command` и `write_stdin` получают непустые tool/parameter descriptions на основе `shell_spec.rs` Codex с явными локальными отличиями: обязательный `workdir`, stdin только при `tty=true`, Ctrl-C для обычной сессии, локальные пределы ожидания и максимум 10000 output tokens.
- Первые 512 символов server instructions, `apply_patch`, `view_image`, корзина, recovery/status/watchdog, инструменты наблюдения, Windows-runtime и `codex-tools.lock.json` не меняются.

## Границы

- Только macOS. Windows-runtime, его каталог, overlay и правила первого сообщения не меняются.
- Исполнитель остаётся прежним: Codex App Server без модельного хода (`turn/start` запрещён). Исходники Codex не собираются и не копируются в проект, кроме текста описаний трёх инструментов.
- `workflow_context_recover`, `bridge_status`, `turn_watchdog`, три инструмента наблюдения и корзина не меняют имён, параметров и поведения.
- Запрет управления интерфейсом (0.6.90) остаётся в правилах и в `instructions`.
- Команды исполняются с правами пользователя, как сейчас; новой песочницы и новых проверок путей для команд не добавляется, существующие для `view_image` и корзины сохраняются.
- Канал VPS, туннель, selector, установка и запуск служб не меняются.
- Ключ туннеля и адрес коннектора не попадают в репозиторий, журналы, диагностику и чат.
- Живую работу агента в ChatGPT проверяет пользователь; агент не запускает VM и не использует Computer Use.

## Риски

- **Поведение веб-модели с новым каталогом не измерено.** Ожидание, что ей привычнее команды и патч Codex, основано на том, как эти модели работают в Codex, а не на проверке в веб-ChatGPT. Проверка — первая сессия пользователя после установки; откат описан выше.
- **Обязательный `workdir` — отличие от Codex.** Модель может сначала вызвать команду без него и получить ошибку; текст ошибки называет параметр.
- **Процесс, оставленный работать.** Отдельного инструмента остановки больше нет: агент останавливает процесс через Ctrl-C в сессии с `tty` или командой `kill`. Сессии хранятся в памяти сервера и теряются при перезапуске служб.
- **Старые чаты** вызывают прежние имена и получают ошибку, пока модель не увидит новый каталог.
- **Codex App Server помечен experimental.** Изменение `command/exec` или исчезновение `apply_patch` из `PATH` сломает родные инструменты; это видно в `bridge_status` и в тестах `executor-channel` на новой версии Codex.
- **Две платформы работают по-разному**, пока Windows остаётся на прежнем каталоге.
- **Сверка определений зависит от GitHub**: без сети она сообщает «не проверено», а не «совпало».
