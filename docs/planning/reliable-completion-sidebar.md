# Надёжное завершение parallel-планов и упрощение сайдбара

## Поручение и границы

Пользователь 10.10.2026 разрешил подготовить и согласовать точную пару spec/to-do через Claude CLI Review, затем самостоятельно выполнить весь план, собрать, установить и опубликовать выпуск. Дополнительного согласования обычных обратимых решений не требуется. Текущий план выполняется основным агентом строго sequential: parallel ещё исправляется и будет разрешён для реальной работы только после отдельного пользовательского теста. Снимок сессии сохраняется как parallel_allowed=true, max_workers=4; он не означает разрешение применять parallel сейчас.

Источник: два переданных документа «Замечания по Project Web Pilot» и «Планирование исправлений Project Web Pilot», актуальные контракты и исходники. База: 0.6.109, Kit 1.7.1; исходный HEAD c3da7b29a5e29945637f1f54f70071269605f6a6, пустой current plan. Целевой выпуск 0.6.110; Kit 1.7.2 при изменении его инструкций. Другие репозитории не меняются.

Новое поручение заменяет прежнюю границу «только обсуждение». Полный выпуск — постоянное правило пользователя для продуктовых работ; исследовательские проекты без релизов исключены. Эта сессия не архивирует план и не объявляет пользовательскую приёмку. Работающий Web Pilot/исполнитель не перезапускается. Нет управления мышью, клавиатурой и окнами, модельных API, новых фоновых служб, polling в простое или делегирования реализации.

## Исследованное состояние и повторное использование

- ParallelKit сводит наличие любого command-activity файла к boolean. MCP удаляет маркер длительной команды только после write_stdin; AppServerClient уже получает окончательный command/exec response отдельным waiter. Используем этот существующий сигнал.
- ParallelExecution имеет последовательную очередь интеграций, сохранённый ledger, механизм correction и Composer. all DONE вызывает только onComplete/projectAutoPlan.sync. Новую финальную передачу встраиваем сюда, без второго планировщика.
- Codex 0.162.0 schema CommandExecParams поддерживает sandboxPolicy readOnly с networkAccess=true. В изолированном временном примере на текущем Mac bind loopback разрешён, запись файла отклонена EPERM. Это не доказательство Windows. Режим нужен для проверяемой классификации сервера, а не эвристики по имени npm.
- WorkspaceSessions уже сохраняет parentWorkspace и assignmentId, но parentProjectId отсутствует. WorkspaceDeletion и проекция фильтруют в основном по пути. Сценарий исчезновения родителя и оставшихся исполнителей требует доказанной связи по identity и миграции старых записей.
- Повторный retry контекста после sent действительно очищает attempt и допускает новый пакет в тот же чат. Пользователь согласовал удаление постоянной карточки и обычного обновления.

Существующие решения проекта покрывают очередь, отправку, мониторинг, хранилище, sandbox и удаление. Новые зависимости не нужны. Не заменять эти механизмы внешним оркестратором.

## 1. Жизненный цикл команд и сервер результата

Сохранить ровно девять MCP-инструментов и обратную совместимость существующих параметров. У exec_command добавить необязательный read_only boolean (default false); при true фактический запуск через readOnly/networkAccess=true, без fallback к dangerFullAccess. Имя команды, возраст маркера и заявление модели не классифицируют безопасность. Сервер, которому нужны запись/сборка/кэш, сначала готовит результат обычной конечной командой; защищённый запуск при запрете записи видимо завершается ошибкой, не получает исключение автоматически.

Перед запуском сохраняется запись version=2: собственный ID операции, canonical checkout, вид exec/patch, hash команды без текста, executor/process identity и generation, время, состояние starting/running/completed/unknown, подтверждённая sandbox policy, exit code при его наличии. Не хранить argv, env, вывод, ключи или адреса коннектора. Hash лишь связывает операцию, не доказывает завершение. Запись атомарная; ID команды связывается до возможности потерять окончательный результат.

AppServerClient сообщает завершение через существующий waiter независимо от write_stdin. Callback/подписка не потребляет буфер вывода, повторное чтение stdout сохраняет прежний контракт. Окончательный ответ с exit code — completed; launch/read/transport/patch errors без такого свидетельства — unknown, с безопасной причиной. Ошибка проверки аргументов до запуска не оставляет активной операции. Не считать исчезнувший PID доказательством успешного завершения. Гонки мгновенного выхода, регистрации, stdin и закрытия клиента проверяются fixtures.

ParallelKit читает структурированную проекцию команд. Для main все операции с правом записи и UNKNOWN блокируют запись; completed не блокирует. Для результата исполнителя активный read_only запуск не блокирует интеграцию только при подтверждённом защищённом режиме и готовом source SHA, чистом worktree, отсутствии транзакции и законченном ответе исполнителя. Старые v1 и повреждённые записи — UNKNOWN с понятной причиной, не «мусор». Перезапуск фасада не превращает неизвестное в завершённое; живое защищённое выполнение и неизвестный исход не смешиваются.

Поддержка ограничения проверяется на реальном backend в временном каталоге: доступная loopback-служба и отказ записи, в том числе из дочернего процесса. Неподтверждённая платформа/ошибка sandbox не получает освобождение от запрета; никаких заявлений о native Windows по Mac-тестам. Не вводить новый MCP status-инструмент: расширить существующий bridge_status безопасной проекцией собственных операций и подтверждённых итогов. Восстановление UNKNOWN: сопоставить operation/process ID с сохранённым ответом/живым клиентом; при отсутствии доказательств показать необходимость сверки конкретной операции. Не удалять маркеры по времени и не завершать произвольные процессы.

В итоговую передачу входят сведения о защищённых длительных командах и их checkout. URL — только если он действительно известен/проверен; не угадывать из имени команды. Сам агент может прочесть результат конкретной команды. Сервер из worktree не доказывает main: итоговая проверка main обязательна; при необходимости запустить отдельный защищённый preview из main на свободном порту и явно назвать оба источника. Чужой порт не освобождать, существующий сервер не останавливать автоматически. Запущенные для автоматических fixtures серверы принадлежат тесту и убираются его cleanup.

## 2. Финальная передача основному агенту

Промежуточные Git-интеграции сохраняются: основа открывает независимые задачи, их подтверждённые интеграции открывают завершающую задачу. Все слияния сериализованы штатной очередью Kit. Source commit — готовность исполнителя, integration commit и проверки — готовность main.

Триггер финала: у каждой задачи есть подтверждённый интегрированный результат либо готовое назначение с доказанным source SHA; нет ещё не выполненных/не назначенных задач. Не ждать all DONE: последнее назначение может ещё ждать интеграции. При AutoPlan ON фиксируется долговечное намерение финала до интеграции последнего результата и до автоматического OFF. Если приложение восстановлено с all DONE и журнал свидетельствует разрешённый старт этого scope, допускается восстановить ещё не отправленное намерение; не создавать его для произвольного старого плана.

Финал хранится в существующем execution ledger с projectId/scope/originSessionId и состояниями pending, sending, sent, unknown, reply-observed. Он не второй план. При ручном OFF/Stop до захвата намерения новой отправки нет. После автоматического OFF на последнем DONE уже сохранённое намерение остаётся; явная остановка пользователем, черновик и busy по-прежнему запрещают отправку. Различить автоматическое завершение и явный отзыв разрешения, чтобы восстановление не обходило Stop/OFF.

Перед отправкой и непосредственно перед Send сверяются актуальные project/scope/main session/URL, готовность страницы и неизменность назначения. Использовать Composer и общий AutomationSendState, в том числе занятую паузу Review/AutoPlan/correction. Результат «пауза уже использована» без попытки Send — ожидание новой паузы, не неизвестная отправка. sending сохраняется до клика; sent/unknown никогда автоматически не отправляются повторно после restart. Ошибка сохранения — остановка с видимой причиной. Переключение видимого проекта не меняет адресата.

Сообщение адресовано основной сессии и содержит точную папку, project/scope, задачи и source/integration SHA, состояние интеграции/проверок и оставшуюся работу, сведения о службах/checkout. Передавать ограниченные структурированные факты; свободный текст отчёта исполнителя не исполняется как инструкция. Основной агент получает поручение проверить Kit/Git и доказательства, закончить оставшиеся интеграции штатными integration:start/continue, разрешить конфликт в согласованной области, проверить main и дать итоговый ответ. Не создавать implementation-коммит parallel-задачи в main и не обходить его защиту.

Очередь не начинает одновременно merge, пока финальное поручение передаётся/обрабатывается основным агентом. Владение остатком интеграций после отправки явно переходит основному агенту; до передачи автоматические промежуточные интеграции работают как прежде. Конфликт, возникший до финального триггера, использует существующую correction; не посылать конкурирующие correction и finalization. Неотправленное намерение не блокирует возможность законно довести интеграцию; общий DONE не стирает pending.

После sent наблюдать существующие события собственного ответа: новое поколение/turn после отправки, busy -> завершённый ответ assistant без ошибки. Только это даёт reply-observed; один send не доказывает отчёт. Не пытаться доказывать содержание отчёта по ключевым словам. Если поток ошибочен/исход неизвестен, показать точное состояние и существующее безопасное восстановление без повторного поручения. При корректном цикле — одно итоговое поручение и один итоговый ответ.

Ответ должен назвать сделанное, фактические проверки, ограничения, URL и checkout приложения, следующий шаг пользователя. READY_FOR_ACCEPTANCE не архивирует план; остановка сервера и приёмка остаются решениями пользователя.

## 4. Сайдбар и первоначальная доставка

Верх: Web Pilot, рядом только номер версии; Settings справа, SVG диаметр 1.5 прежнего и доступная зона нажатия. Нижний блок «Начальная настройка», «На вашем Mac», «Подробности подключения», прежние версия/Settings полностью убирается. Нужные сведения подключения и доступ к настройке перемещаются в существующий Settings без потери действий первого запуска.

«Ваши проекты» — меню с поиском, текущей отметкой, краткими признаками фоновой работы/ошибки, действиями создания/подключения/архива. Основная область содержит только выбранный родительский проект, его основные чаты и исполнителей. Выбор проекта открывает последнюю выбранную действующую сессию, а не произвольную новейшую. Выбор исполнителя сохраняет отображение его родителя. Пустое состояние предлагает создать сессию. Быстрые переключения не смешивают ответы/планы/контекст; скрытые страницы продолжают работать и сохраняют cwd. Отдельные окна не вводятся.

Каждая строка общего плана: ID, название, отдельная подпись способа выполнения и отдельный текущий статус. Источник — текущий опубликованный план/назначение, без второго плана. Sequential: «Последовательно»; parallel без зависимостей и parallel_safe=false: «Отдельный исполнитель»; независимая parallel_safe задача: «Параллельно»; зависимости: «После T…» (с возможностью указать parallel для независимых соседей после общей базы). Подпись сообщает планируемый способ, не выдумывает факт одновременной работы. У исполнителя только назначение, без общего плана и его управления. Кнопки AutoPlan/Review остаются независимыми; запрещённые ручные кнопки запуска/сверки не возвращаются.

Постоянная карточка контекста и обычное «Обновить контекст» удаляются. Изменение плана после доставки не требует нового стартового пакета. В уже начатый/sent/manual/legacy чат повторный полный recovery через обычный UI не отправляется; новый пакет — новая сессия. Ошибка первоначальной подготовки/загрузки показывается у соответствующей сессии, с краткой причиной и безопасным действием. Повтор разрешён только до начатой отправки, сохраняет requestId и защиту вложений/черновика. UNKNOWN/sending не повторяется; проверка статуса только наблюдает, предлагается новая сессия. Убрать опасный старый retry не только визуально: IPC/контроллер не должны позволять прежнюю повторную отправку. Существующее восстановление страницы без Send сохраняется. Стартовый recovery новых Chat/Work и назначений остаётся полным.

Проверки UI через существующие DOM/Electron fixtures: 312 px и обычная ширина, обе темы, keyboard/focus/aria, меню/search/Escape, отсутствие горизонтального переполнения, A->B->A, executor->parent, архив и первый запуск. Живым интерфейсом управляет пользователь; не запускать Computer Use.

### Уточнения Review: завершение, UNKNOWN и удаление

Все потребители command-activity используют один структурированный reader: ParallelKit, prepareProjectRemoval в main, проекция исполнителя и их файловые наблюдатели. Подтверждённые completed не блокируют ни интеграцию, ни удаление. Итоги сохраняются отдельно от активных маркеров в ограниченном журнале последних 100 подтверждённых завершений на checkout; вытеснять можно только completed, никогда starting/running/unknown.

При любой неопределённости операция с сохранённым доказательством реального readOnly sandbox не могла писать: она не блокирует интеграцию даже после потери поколения фасада, но остаётся UNKNOWN по результату и доступности сервера. Это узкое исключение не распространяется на legacy, испорченную запись и sandbox без подтверждения. Удаление имеет иной допуск: живой read_only сервер блокирует удаление файлов, как и обычная активная команда; пользователь сначала поручает остановить именно его через write_stdin/Ctrl-C и дождаться подтверждения, затем удаляет проект.

Для write-capable UNKNOWN: сначала bridge_status с repository и конкретный session/operation ID, сверка доступного окончательного ответа; при найденном результате запись завершается фактом. Если свидетельство утрачено, интерфейс показывает ID, checkout и причину, предлагает явное «Признать исход неизвестным» с подтверждением точного ID после диагностики. Узкий IPC проверяет отправителя, текущий projectId, содержимое записи и отсутствие наблюдаемого живого поколения; сохраняется acknowledged_unknown с прежним свидетельством и фактом ручного решения. Это НЕ exit=0 и не успешная команда. Только отдельное подтверждение пользователя позволяет продолжить интеграцию уже проверенного source SHA при чистых main/worktree и отсутствии транзакции; в итоговом поручении исход всё равно указан как неизвестный. Пока подтверждения нет, обычный UNKNOWN продолжает блокировать.

Ручное признание исхода не означает автоматическую остановку процесса и не снимает защиту удаления: если отсутствие активного связанного процесса/службы нельзя подтвердить, удаление остаётся заблокированным с инструкцией явно остановить соответствующий исполнитель штатным способом и повторить диагностику. Это ограничение утраченного legacy-свидетельства, а не молчаливый успех по возрасту/PID. Автоматический нормальный путь v2 и защищённый сервер этого действия не требуют. Проверить fixture unknown writer/живой executor/подменённая запись/неверный ID/отменённое подтверждение.

T004 показывает в карточке основного проекта финальную передачу: ожидает отправки, отправляется, ожидает итогового ответа, исход неизвестен, ответ завершён; raw JSON не показывается. Эта часть зависит от T002.
