# Проверка установки на чистых системах

## Согласованный этап — clean-install-lab-027

16.09.2026 пользователь поручил начать с виртуальной macOS и добавить виртуальную Windows, чтобы шаг за шагом довести готовые поставки Web Pilot до самостоятельной установки на новом компьютере, а затем подготовить понятные подсказки по шагам.

Владелец — Release & Local Installation (`docs/RELEASE.md`); смежные контракты — Runtime Lifecycle и Workspace Setup. Текущий scope подготавливает стенд и фиксирует исходный первый запуск 0.6.26. Изменения приложения и будущий интерактивный мануал определяются по наблюдаемым результатам отдельными согласованными задачами.

## Стенд и изоляция

Используется готовый открытый UTM из официального GitHub-релиза. Основной Mac на момент подготовки: macOS 26.6.2 / arm64, 256 GiB RAM, 28 логических CPU, около 208 GiB свободно на Data. UTM и виртуальные машины до подготовки не обнаружены в стандартных папках.

Рабочая папка стенда: `~/Documents/WebPilot-Test-Lab/`. Диски ОС, IPSW/ISO и локальные снимки не включаются в Git. Документы проекта хранят только воспроизводимые действия, версии, контрольные суммы и несекретные результаты.

- Сначала macOS через Apple Virtualization и автоматический выбор совместимого IPSW самим UTM. Начальные ресурсы: 4 CPU, 12 GiB RAM, разреженный диск 64 GiB.
- Затем Windows из официального образа Microsoft. Архитектура должна быть записана явно: текущая поставка Web Pilot — Windows x64; ARM64-гость с эмуляцией приложений не подтверждает работу на нативной x64 Windows. Полная эмуляция x64 на Apple Silicon существенно медленнее. Выбор гостя уточняется перед созданием; неподдерживаемые ограничения ОС не обходятся.
- Пользовательский вход, секреты туннеля, системные разрешения и лицензионные действия выполняются штатно. Ключи и пароли не попадают в документы, Git, сообщения или снимки.
- Основной Web Pilot, рабочий Codex Local Mac, туннель, проекты и их профили сохраняются. В гостя передаются только готовые ZIP/app и отдельные тестовые файлы; домашняя папка и рабочий репозиторий не подключаются общей папкой.
- Перед установкой Web Pilot сохраняется остановленная чистая копия VM штатным способом. Повторная проверка начинается из неё.
- Node.js, Git и MCP с компьютера разработчика вручную не переносятся. Если поставка требует недостающий компонент, это фиксируется как результат, а не скрывается предварительной установкой.

## Computer Use

Управление возможно через видимое окно UTM на основном Mac без установки второго MCP в госте для начальной настройки. Проверка `computer_status` 16.09.2026: accessibility=true, post_events=true, screen_recording=false. До пользовательского включения записи экрана локальному MCP нельзя считать наблюдение GUI доступным; обход системного разрешения не применяется. Реальная видимость/ввод должны быть отдельно подтверждены на гостевом окне.

## Исходные факты поставки 0.6.26

| Компонент | macOS arm64 | Windows x64 |
| --- | --- | --- |
| Electron/Chromium и Workflow Kit | Внутри app | В полной распакованной папке рядом с EXE |
| Node для Workspace Setup | Ищется в /opt/homebrew/bin/node или /usr/local/bin/node; отдельного bundled Node нет | Portable Node 22.17.0 включён |
| MCP runtime | Включены source ZIP и uv; предусмотрен bootstrap | Включён source/vendor ZIP; предусмотрен bootstrap |
| Python и зависимости | Создаются/скачиваются при bootstrap | Создаются/скачиваются при bootstrap |
| tunnel-client | Скачивается при bootstrap | Включён vendor archive |
| Git для Workflow Kit | Используется системный git | MinGit есть в MCP payload, но WorkspaceSetup не передаёт WORKFLOW_GIT_BIN/HOME; требуется чистая проверка |
| Настройка личного туннеля | CLI предусмотрен; специального Mac onboarding UI нет | Кнопка запуска настройки в Settings |

Основание — чтение `src/main.mjs`, `src/platform.mjs`, `src/workspace-setup.mjs`, `src/mac-runtime.mjs`, `src/windows-runtime.mjs`, `src/mcp-runtime.mjs`, bundled control/setup и фактических ресурсов обоих пакетов. Это анализ состава/кода, а не пройденная установка на чистой ОС. В существующих tests bootstrap частично имитируется; успешный smoke не подтверждает чистую установку. Одиночный Windows EXE без ресурсов не является самостоятельной поставкой.

## Последовательность исходной проверки

1. Открыть чистую гостевую ОС, записать версию/архитектуру и отсутствие дополнительных инструментов разработчика.
2. Передать проверенный готовый пакет 0.6.26; записать его SHA-256.
3. Распаковать и запустить приложение штатно; фиксировать каждое сообщение/ошибку.
4. Создать отдельный тестовый проект; проверить bootstrap, Node/Git, локальный MCP и путь первичной настройки туннеля.
5. После пользовательской настройки аккаунта проверить передачу контекста и простое разрешённое действие с тестовым файлом внутри гостя.
6. Перезапустить приложение и гостя; проверить сохранность настроек и отсутствие повторной установки.
7. Записать шаг, ожидаемый результат, фактический результат, необходимость участия пользователя и подходящую короткую подсказку.
8. Отдельно предъявить подтверждённые blockers для следующего изменения приложения. Запуск через основной MCP не выдаётся за работу гостевого MCP.
