## Передача следующему scope — последовательность проверки

1. Открыть чистую гостевую ОС, записать версию/архитектуру и отсутствие дополнительных инструментов разработчика.
2. Подтвердить выбранную версию готовых пакетов и записать SHA-256; пользователь выбрал 0.6.27 для macOS.
3. Распаковать и запустить приложение штатно; фиксировать каждое сообщение/ошибку.
4. Создать отдельный тестовый проект; проверить bootstrap, Node/Git, локальный MCP и путь первичной настройки туннеля.
5. После пользовательской настройки аккаунта проверить передачу контекста и простое разрешённое действие с тестовым файлом внутри гостя.
6. Перезапустить приложение и гостя; проверить сохранность настроек и отсутствие повторной установки.
7. Записать шаг, ожидаемый результат, фактический результат, необходимость участия пользователя и подходящую короткую подсказку.
8. Отдельно предъявить подтверждённые blockers для следующего изменения приложения. Запуск через основной MCP не выдаётся за работу гостевого MCP.

Проверки выполнены без кликов, ввода, активации окон и перезапуска служб: чтение источников и журналов, запросы состояния/окон и снимки уже видимого окна Test-macOS. | Операция | Через loopback MCP на основном Mac | Через доступный инструмент чата |
| --- | ---: | ---: |
| computer_status | 11,18–31,05 мс, три вызова | 2011 мс, один вызов |

| Снимок того же окна, максимум 1024 px | 299,73 мс | отдельно не измерялось |

Loopback включает обработчик, локальный HTTP и сериализацию результата; внешний замер включает весь путь вызова/возврата инструмента, но не последующее рассуждение модели. Это небольшая диагностическая выборка, не p95 и не SLA. Квитанции без изображений/секретов: .harness/runtime/clean-install-lab-027/loopback-latency.json и capture-latency.json.

Подтверждённые факторы:
- Накладное время внешнего вызова существенно больше времени локальной операции. Отдельные list/activate/click/capture требуют отдельных round trip и последующего анализа результата. Строго необходимая последовательность умножает задержку даже при исправной сети.
- PNG окна 1600×1037 занимает около 1,75 MB, представление base64 — 2 339 172 символа. При лимите 1024 px — 1 059 572 символа base64. Backend сначала запускает системный screencapture, затем уменьшает и повторно кодирует PNG. Это стоимость пути снимка; замер не позволяет приписать всё внешнее время только размеру.
- Два дисплея дают виртуальный рабочий стол 4096×1152 points с началом x=-2048. Снимок всего стола при лимите 1600 уменьшает его ширину до 39%; чтение небольших элементов становится труднее. Снимок только окна 1730×1121 сохраняет около 92,5% масштаба. Координаты ввода относятся к исходным points, а не к уменьшенному изображению; ошибочное преобразование может вызывать повторные попытки.
- В текущем bridge_mcp.py Computer Use handlers объявлены синхронными. Установленный MCP Python SDK 1.28.1 вызывает синхронную функцию непосредственно внутри async dispatch, без thread offload. В обработчиках есть блокирующие subprocess.run и time.sleep; общий RLock сериализует ввод/снимки. Следовательно, медленная синхронная операция способна задержать обслуживание других запросов. Её причинная связь с конкретным двухминутным сбоем не доказана.
- В tunnel.out.log 17.09 наблюдаются poll timeout/backoff и сетевые ошибки can't assign requested address, в частности 08:57–09:00 +02:00. Во время этой диагностики обычный run_command_batch завершился HTTP 504 / MCP request timed out; последующее чтение подтвердило отсутствие его первого ожидаемого файла. Значит, в этом случае проблема возникла до ожидаемой файловой операции, а не внутри screenshot handler. Последующие вызовы снова занимали около двух секунд.
- В mcp.err.log есть ClosedResourceError при отправке в закрытый stream и RuntimeError: Unexpected ASGI message 'http.response.start' sent, after response already completed. Стек проходит через stateful Streamable HTTP MCP/Starlette/Uvicorn. У этих строк нет достаточной корреляции с конкретным tool request, поэтому нельзя объявлять их единственной причиной задержек.

Следующий проверяемый этап улучшения MCP: добавить несекретные request timings на границах получения/начала/окончания/ответа; воспроизвести восстановление транспорта после смены сети и закрытой сессии на отдельном стенде; вынести блокирующие desktop-операции с event loop с сохранением очереди и взаимного исключения; исследовать ограниченный action+capture/batch интерфейс и более компактные снимки. Версии библиотек менять только после воспроизводимого теста. Автоповтор кликов/ввода после неоднозначного timeout недопустим без проверки состояния.

Обнаружены проблемы транспорта и издержки текущей схемы, но точная доля сети/туннеля, серверной сессии, доставки изображения и времени модели в прежней работе не измерена.
