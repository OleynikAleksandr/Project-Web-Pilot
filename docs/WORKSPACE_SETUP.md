# Создание и подключение workspace

## Пользовательский порядок

«Создать проект»: ввести имя и выбрать родительскую папку. Приложение показывает полный конечный путь и список добавляемых файлов. «Открыть папку»: выбрать существующую папку и получить результат проверки. Если выбран подкаталог Git-проекта, перед подтверждением показывается фактический корень.

Готовый проект можно открыть. Если комплекта нет, предлагается подготовить папку; если отсутствуют локальные команды или Git-проверки совместимой установки — восстановить их. Изменённые файлы ядра, повреждённый план, отсутствующие обязательные документы, неподдерживаемая версия и конфликтующие пути останавливают подготовку с конкретным объяснением. Приложение не перезаписывает их автоматически.

Создание устанавливает Workflow Kit 1.4.1: инструкции, документацию, каталог, навигационный legacy-план и фасад планов сессий, команды, Git-проверки и совместимость с Codex. Начальное состояние NONE / DISCOVERY сохраняет обязательные ссылки на OVERVIEW, MODULES и DOCUMENTATION_INDEX; задачи и стек не назначены. После открытия ChatGPT получает полный пакет по CONTEXT_DELIVERY; первый ответ не требует проверки Codex hooks или ACK.

## Проверка готовности

При первом подключении, установке, обновлении и ремонте проверяются manifest и контрольные суммы принадлежащих комплекту файлов, обязательные документы и инструкции, каждый канонический план и его Git references, запуск команд, наличие и целостность секций Git-проверок и COMPLETE recovery. Пользовательские редактируемые документы не сравниваются с исходным шаблоном. Проверяющий worker распознаёт версии 1.0.0, 1.1.0, 1.2.0, 1.3.0, 1.4.0 и 1.4.1. Целостные 1.1/1.2/1.3/1.4.0 предлагают штатное обновление до 1.4.1; reconnect локальных компонентов относится к совпадающей текущей версии. Неизвестный изменённый runtime автоматически не заменяется.

Состояние фактического Codex SessionStart не служит условием открытия в Web Pilot. Сохранённые файлы совместимости комплекта не выдаются за проверенную доставку в Codex. Контекст здесь передаёт само приложение.

## Сохранение файлов

Предварительная проверка не меняет выбранный проект. Применение использует текущий fingerprint и повторную проверку; если папка изменилась, требуется новый просмотр. Разрешение хранится только в основном процессе как одноразовый непрозрачный token, привязанный к папке и режиму. Из веб-страницы ChatGPT этот интерфейс недоступен.

Исходное ядро сохраняет существующие файлы, AGENTS, документацию и Git hooks, дополняя только предусмотренные секции. Конфликты не перезаписываются. Если до установки уже были изменения, они не входят в служебный коммит. Установка может остаться с ожидающим install:commit, о чём интерфейс сообщает; исходный staging сохраняется. При отсутствии автора истории интерфейс позволяет указать имя и email только для выбранного проекта.

## Runtime

Полный комплект и изолированный обработчик находятся в ресурсах приложения. Обработчик запускается отдельным процессом настоящего Node.js 22+ с явной папкой и JSON-входом. Electron не копируется в проект под видом Node. На текущем Mac используется существующий Node из /opt/homebrew/bin или /usr/local/bin. Отсутствие Node выдаёт понятную ошибку до создания папки. Поставка отдельного Node для другого Mac остаётся за рамками этой локальной сборки.

## Интерфейс Web Pilot

В меню «Ваши проекты» находятся «Создать проект» и «Открыть папку проекта». Создание запрашивает имя и расположение, затем показывает конечную папку и раскрываемый список изменений. Подключение показывает результат проверки до открытия. Применение выполняется кнопкой «Создать и открыть», «Подготовить и открыть», «Восстановить и открыть» либо «Открыть проект» в зависимости от фактов проверки.

Отмена предварительного просмотра не создаёт папку и возвращает текущую сессию. Ошибка проверки сохраняет выбранный чат; приложение показывает конкретные файлы и кнопку повторной проверки. Сохранённые проекты, отдельные сессии, новые чаты и восстановление после запуска тоже проходят проверку готовности. Дерево сессий сохраняется. После открытия под путём видны версия проверенного комплекта и существенные замечания.

## Workflow Kit 1.2 upgrade

Project Web Pilot различает совместимую установку 1.1 и повреждённый/неизвестный runtime. Неизменённый owned runtime 1.1 предлагается как `upgrade`, а не как reconnect: Kit обновляет owned `.harness/kit` и launchers, обновляет только подтверждённые managed sections, обновляет plan template если пользователь его не менял и создаёт недостающие `docs/MODULES.md` / `docs/architecture/OVERVIEW.md`. Активный todo-plan, workflow config и пользовательские editable документы не перезаписываются.

Если owned runtime или критическая managed section не совпадает со старым manifest, автоматический upgrade блокируется. `DOCUMENTATION_INDEX.md` является исключением: каталог штатно развивается вместе с проектом, поэтому upgrade сохраняет его содержимое и только аддитивно добавляет новые MODULES/OVERVIEW строки. Upgrade создаёт отдельный `kit-update` commit через те же Git hooks. Fresh install 1.2 сразу создаёт module map/overview и `include_last_completed_task=false` в пустом plan.

## Первая сессия Chat / Work — scope 011

При создании нового проекта и при первом подключении готовой папки, которой ещё нет в локальном списке Web Pilot, preview показывает выбор «Первая сессия проекта: Chat | Work». Default — Chat; выбор хранится только в текущем setup flow и после отмены сбрасывается. Повторное открытие уже зарегистрированного проекта не показывает этот выбор и не создаёт новую session.

Создание дополнительных sessions перенесено из карточки контекста в меню `⋯` проекта: `Новый Chat` и `Новый Work`. Карточка контекста управляет только выбранной session. В дереве рядом с названием каждой session отображается read-only badge Chat/Work.

## Windows Node: запуск и диагностика

Windows-поставка содержит portable Node.js 22.17.0 вне app.asar; он первый в списке кандидатов, затем проверяются системные пути и PATH. Установка отдельного Node для полной готовой поставки не требуется. Этот путь уже добавлен 12.09.2026 в commit 0fb755e; более ранние версии зависели от системной установки.

Исправление windows-node-setup-019 очищает только окружение дочерних Windows-процессов от NODE_OPTIONS/NODE_PATH независимо от регистра ключей. Системное окружение не меняется. Запуск версии и worker выполняется без консольного всплывающего окна. NODE_MISSING означает отсутствие доступного кандидата и предлагает распаковать всю Windows-папку; NODE_TOO_OLD указывает найденную версию; NODE_START_FAILED показывает путь и код запуска без stderr/окружения. Другой исправный кандидат используется; повторная проверка после ошибки выполняется заново. Поведение macOS не меняется.

## Workflow Kit 1.3 и Доктор проекта

Версия 1.3 сохраняет navigation-context в NONE, добавляет последнюю DOCS-задачу и отделяет готовность от пользовательской приёмки. Обычная проверка открытия остаётся строгой. При ошибке доступен Доктор проекта по `docs/modules/project-doctor.md`: он работает через bundled worker и запускает ремонт только явной кнопкой. Settings можно открыть и из заблокированного setup. После ремонта полный readiness/recovery проверяется повторно; неизвестные повреждения остаются явным blocker.

T011: Workflow Kit 1.4.0 добавляет upgrade с 1.3.0, предварительную проверку новых файлов ядра и резервную копию перед заменой. Readiness проверяет контекст каждого канонического плана; Doctor проверяет все планы, восстанавливает только читаемую проекцию и сохраняет их в backup. Pre-push разрешает commit references всех планов. Согласование manifest допустимо только с полностью совпадающим доверенным комплектом, неизвестные изменения не перезаписываются.

## Ускорение полной диагностики — scope 029 / T003

Доверенный worker использует одну inspectWithDiagnostics вместо повторного inspect в doctor и отдельных recover-процессов. Каждый канонический план остаётся проверенным, а COMPLETE берётся из того же согласованного результата. Общий fingerprint охватывает все входы, сравнивается до/после; при изменении возможен один повтор и затем явная ошибка. Активная commit transaction не разрешает ready. Установка/upgrade/repair сохраняют строгий путь и backup. Раннее открытие выбранной сессии выполняется следующими задачами.

T004: WorkspaceSetup.ready для уже подключённого проекта использует ограниченный readiness-кэш с worker fingerprint; preview/apply первого подключения и ремонта кэш не подменяет. Каждый cache hit проверяет актуальный ключ, включая содержимое документов/планов, Git и hooks; изменившийся проект проходит полную инспекцию заново. Одновременно выполняется один worker-check и хранится только последний ожидающий выбор. Ошибки доступны для повтора.

## Открытие подключённого проекта — scope 029 / T005

В исходниках сохранённая сессия открывается по короткой проверке пути, project identity и собственного плана. Полная проверка WorkspaceSetup.ready выполняется в фоне с ограниченным кэшем; для её ошибки доступны повтор и Доктор. Сохранённый чат доступен для просмотра, но controller доставки ждёт ready и окончания текущей навигации. Первое подключение, установка и legacy migration сохраняют preview/apply. Это изменение ещё не выпущено: постоянный app и ZIP обновляются в T009.

T008: холодная проверка после изменения timestamps больше не обновляет индекс через Git diff и не вызывает собственный повтор. В сопоставимом двухплановом проекте полная инспекция занимает 3.25–3.36 с (исходники, текущий Mac); 30 одинаковых readiness-запросов объединяются в одну работу. Изменившиеся реальные входы по-прежнему требуют новой проверки.
