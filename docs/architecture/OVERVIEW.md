# Краткая архитектура проекта

Состав и связи (06.10.2026): **Workflow Kit** — планы и recovery, пакет `packages/workflow-kit` этого репозитория; **Web Pilot Sidebar** — отдельно разрабатываемый браузерный интерфейс в своём репозитории. [Рабочие каталоги и границы интеграции](../SOURCE_WORKSPACES.md).

Project Web Pilot — Electron-приложение для macOS arm64 и Windows x64. Слева проекты, разговоры и текущий план; справа настоящий ChatGPT Web в изолированном Chromium. Файлы и команды доступны через MCP/tunnel; модельные API не используются.

Не запускай codex exec, других модельных агентов и не делегируй им работу, если пользователь прямо этого не попросил. Штатный codex app-server как локальный исполнитель MCP без модельных запросов разрешён.

## Основные контракты
- Один checkout/worktree имеет один current plan: .harness/plans/todo-plan.md. Chat/Work sessions — разговоры с собственными URL, title и временем. Session ID не выбирает plan; legacy ownership только история. Независимая работа — отдельный worktree.
- Workflow Kit — пакет `packages/workflow-kit` этого репозитория (с 06.10.2026; раньше отдельный репозиторий WorkflowKit, история перенесена), @webpilot/workflow-kit **1.5.6** в source 0.6.96 (35 файлов; новая задача ставится перед указанной, `plan:extend --help` перечисляет поля задачи, изменения подтверждаются содержимым файла — ложного `PRIVATE_CONTEXT` нет). В опубликованной 0.6.95 — 1.5.5 (компактный recovery: формы и карты по запросу; push только после DOCS). resources/workflow-kit — копия для приложений, создаётся автоматически и сверяется с исходником пакета файл в файл; .harness/kit — установленный runtime проекта. Последний отдельный релиз пакета — 1.5.1. Спецификация — [packages/workflow-kit/docs/modules/workflow-kit-package.md](../../packages/workflow-kit/docs/modules/workflow-kit-package.md).
- Recovery строит Kit. С 0.6.96 на macOS и Windows новая сессия получает полный актуальный пакет первым сообщением вместе с правилами работы с инструментами; MCP контекст не доставляет. В 0.6.86–0.6.95 на macOS агент читал контекст через MCP `workflow_context_recover` по частям по короткому стартовому сообщению — этот путь удалён, чаты того времени остаются сохранёнными; просмотр старого разговора не отправляет его повторно. Paste использует обработчик страницы; передача завершается после Send без сверки текста и ожидания ответа. При неопределённом исходе автоматического дубля нет.
- PageStateSource получает события из sandboxed isolated preload только основного ChatGPT document. Проверяются frame/origin/document/sequence. Агентский секундомер следует Stop; busy не доказывает серверное состояние.
- ContextCache, fingerprint и проверка recovery принимают workspace без session selector; кеш общий для чатов checkout. Пакет recovery по-прежнему строит Workflow Kit, а актуальность проверяется перед вставкой. Настройка туннеля на обеих системах идёт через мастер и общий `tunnel_prompt.py` исполнителя.
- PlanMonitor независим от доставки. Файловые сигналы означают перечитывание, а не журнал. Ошибки видимы, повторы ограничены; полный fingerprint остаётся перед вставкой.
- AutoPlan выполняет один последовательный событийный reconcile по toggle, странице, выбранному контексту и PlanMonitor. Saved on/off независим от фазы; busy не вызывает Git polling. Перед Send повторно проверяется подтверждённый ACTIVE-план. Native turn/user IDs, наблюдаемые циклы генерации и v3 checkpoint ledger исключают дубль sending/sent между OFF/ON, reload и restart. Draft сохраняется, ручной Send ждёт нового ответа; Stop с частичным ответом допускает подходящую idle-паузу. Текст ответа не определяет отправку. Watchdog только сообщает STALL_WARNING; sidebar показывает подтверждённый счётчик, diagnostics — причины без содержимого разговора.
- С 0.6.96 сообщение автопродолжения — «Продолжай» и текст следующей задачи плана (`continueMessage`, не более 4096 байт) с пометкой, что это данные плана, а не новое поручение; если следующая задача сменилась между подготовкой и Send, отправка отменяется. Логика пауз и контрольных точек не менялась.
- ConversationRecovery ограниченно восстанавливает известный URL при terminal stream error, включая Resume stream unavailable. Черновик, ручной Stop и rate limit учитываются; восстановление страницы не равно повторной генерации.
- Project Doctor чинит известные служебные неисправности current plan. Исторические планы не блокируют readiness.
- Панель настроек — src/ui/settings-panel.mjs (settingsPanelView). Кнопка «Архив…» открывает отдельное окно с archive:* IPC; скрытого встроенного архива и старых pilot:* обработчиков удаления нет. settings хранит workspace для выбора проекта в Докторе, включая ошибку восстановления удаления при старте; archives в снимке остаётся для наблюдения за архивированием.
- Общие файловые функции находятся в src/common.mjs: потоковый SHA-256, exists (строгий режим для очистки истории) и создание ошибок fail. src/tunnel-setup.mjs объединяет обмен с first-run helper, передачу credentials через stdin и фильтрацию ошибок; платформенные обёртки задают прежние env, классы ошибок и пользовательские сообщения. Scripts импортируют src, обратных зависимостей нет; самостоятельные Python/resources-workers не зависят от src.
- **Состав пакета (с 0.6.91).** В `app.asar` обеих платформ попадают только `src`, `node_modules`, `package.json` и `LICENSE`: `--ignore` упаковщика в `package.json` — список разрешённого, а не исключений. `verifyPackagedSources` (`scripts/release-all.mjs`, `PACKAGED_ROOTS`) останавливает сборку, если в корне пакета есть что-то ещё. Новая папка в корне проекта в пакет не попадает; если она нужна приложению, её добавляют в оба места.
- **Архив компонентов Windows (с 0.6.91).** `Windows-Codex-Local-2026-09-10.zip` — шестой файл каждого релиза, в Git его нет. С 0.6.96 из него используется только папка `vendor`: uv, tunnel-client, ripgrep и MinGit; прежний сервер инструментов из архива не распаковывается и не запускается. `ensureWindowsRuntimePayload` (`scripts/prepare-windows-toolchain.mjs`) берёт его из кеша `.harness/runtime/windows-payload`, из `WEB_PILOT_WINDOWS_RUNTIME_ARCHIVE` или скачивает из последнего GitHub Release; любой источник сверяется с SHA-256 из `src/windows-runtime.mjs`. `release-manifest.json` описывает файл в `windowsRuntimeArchive`, список имён релиза — `releaseAssetNames(version)`.
- С 0.6.96 MCP обеих систем — 9 инструментов: `exec_command`, `write_stdin`, `apply_patch`, `view_image`; `bridge_status`, `turn_watchdog`; `computer_list_windows`, `computer_capture_screen`, `computer_capture_window`. Сервер отдаёт только инструменты; `workflow_context_recover` удалён. В 0.6.95 каталог macOS — эти девять и `workflow_context_recover`. В 0.6.92–0.6.94 каталог включал ещё три инструмента корзины (`delete_path`, `list_trash`, `restore_trash`); 0.6.95 их убрала. 0.6.93 исправила command-session stdin/timing; source 0.6.94 — Wall time/race, единая обрезка 8000, полный tool schema, image hint и общее retry-rule без изменения каталога. Старые 28 файловых/поисковых/git/process tools удалены: поиск и Git идут через `exec_command`, текстовые правки — через `apply_patch`, удаление — `rm` в `exec_command` или `*** Delete File` в `apply_patch`, откат — через git. Кода Sky, `node_repl` и MCP-thread нет. Windows остаётся на прежнем overlay и в 0.6.95 не меняется. Запрет управления интерфейсом действует на обеих платформах.
- На macOS и, с 0.6.96, на Windows один локальный backend — исполнитель Codex App Server (MCP «Codex App Server Local Mac» / «Codex App Server Local Windows»): исходники `tools/codex-app-server-mcp`, состояние `~/Library/Application Support/WebPilotCodexExecutor` или `%LOCALAPPDATA%\WebPilotCodexExecutor`. На Windows приложение сначала распаковывает компоненты закреплённого архива и создаёт собственный Python (`WindowsExecutorBootstrap`), автозапуск — запись в `HKCU\…\Run` через `control.py autostart`, прежний сервер инструментов останавливается один раз при переходе. Нужен установленный Codex. Windows-часть на настоящей Windows не проверялась. `src/mac-runtime-switch.mjs`: `CodexAppServerRuntime` (команды `control.py`, установка, ввод туннеля через `tunnel_prompt.py`), `MacSelectedRuntime` (backend и канал ChatGPT), `MacRuntimeSwitcher.activate` (LaunchAgent, selector, канал, запуск MCP и туннеля, одноразовая очистка прежнего runtime). Подготовка не фатальна: установленные службы поднимаются при запуске приложения, на новом Mac — мастером первого запуска после Git; ошибка показывается в сайдбаре, следующее обращение к службам повторяет подготовку. Без туннеля MCP запускается, а туннель только отражается в статусе. App Server выполняет локальные инструменты без модельного turn/start. Службы живут независимо от UI.
- Канал ChatGPT (`chatgptChannel`: `secure-tunnel` | `vps`) хранится в настройках Web Pilot и в `selector.json` executor (`chatgpt_channel`, команды `configure-channel`, `stop --tunnel-only`); `selector-start` при входе в систему в режиме VPS tunnel-client не поднимает. На Windows (с 0.6.96) туннель VPS держит наблюдатель `control.py vps-supervise` (`WindowsVpsTunnel`), кнопка VPS в настройках активна только при настроенном сервере с работающим туннелем. Туннель VPS — `src/vps-tunnel.mjs`: LaunchAgent `com.oleynik.vps-mcp-tunnel` с `ssh -R 127.0.0.1:17842:127.0.0.1:<порт MCP> vps-mcp-tunnel` (KeepAlive); plist переписывается только при смене порта, блок `Host vps-mcp-tunnel` в `~/.ssh/config` создаёт `vps-server`. В режиме VPS поле `tunnel` статуса отражает канал VPS; адрес коннектора в статус попадает только скрытым, полный — только в буфер обмена по кнопке.
- Новый этап дополняет current plan через plan:extend. Для code-only scope DOCS завершает задачи; при package/installed delivery DOCS располагается перед delivery-хвостом и переоткрывается при поздней correction-работе. Архивирование — только по прямому поручению; исторический plan:carryover 1.5.1 сохраняет точный архив прошлого scope.
- Парный выпуск macOS/Windows — npm run build; сохранять identity постоянного app и Finder-алиас. Для локальной macOS-подписи используется явно выбранный пользователем сертификат UkrHD через штатную signing configuration; автоматического выбора и ad hoc fallback нет. Native Windows/live ChatGPT проверяются отдельно; VM и Computer Use не запускать.
