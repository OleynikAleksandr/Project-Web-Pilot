# Жизненный цикл локальных команд

Команды MCP, очередь интеграций и удаление проекта используют один структурированный источник состояния. Код: tools/codex-app-server-mcp/server.py и app_server_client.py; клиент — src/command-activity.mjs, parallel-kit.mjs, execution-projection.mjs и main.mjs.

## Запуск и завершение

Exec и apply_patch атомарно создают version=2 запись в .harness/runtime/command-activity/<id>.json. Поля связывают operation ID, workspace/cwd, executor instance/PID, поколение App Server, process_id, состояние и время. Сохраняется хеш команды, без исходного текста, вывода и секретов. starting переходит в running; callback терминального события App Server сохраняет completed receipt с фактическим exit_code и снимает active marker независимо от очередного write_stdin. История completed ограничена последними 100 записями.

write_stdin читает прежнюю сессию и может явно остановить её, но не является единственным свидетелем завершения. Потеря транспорта/поколения без terminal event означает unknown, не exit 0. Отсутствующий PID и возраст записи не доказывают успех; автоматического удаления stale-маркеров или убийства процессов нет. bridge_status(repository) раскрывает только разрешённые поля операций и receipts. События файла будят очередь, функционального polling в простое нет.

## Сервер предпросмотра

Явный exec_command(read_only:true) требует реальную файловую sandbox ReadOnly с разрешённой сетью. На каждое поколение App Server probe подтверждает отказ записи и сетевой bind. Неподдерживаемая защита возвращает ошибку до запуска; fallback к writable запрещён. Сборка/установка зависимостей выполняются заранее отдельными обычными командами. Тип команды не выводится из её имени, порта, stdout или возраста.

read_only_verified + sandbox_policy=readOnly + process_id позволяют интеграциям и финальному отчёту идти при живом сервере: тот не может менять checkout. Удаление проекта блокируется любой живой командой, включая такой сервер. Останавливается только конкретная сохранённая серверная сессия по явному поручению; завершение плана само сервер не останавливает.

## Неизвестный исход

readCommandActivity возвращает commands, commandActive, deletionBlocked и services. Повреждённая/неизвестная запись закрывает допуск, не превращается в завершённую. Активный writer блокирует интеграцию и удаление; подтверждённый read-only не блокирует интеграцию даже при потере наблюдения, поскольку файловая защита остаётся границей.

Для unknown writer с отсутствующим процессом исполнителя доступно адресное подтверждение пользователем: точный ID, digest неизменённой записи, подтверждение ID и повторная проверка отсутствующего executor PID. acknowledgeUnknownCommand атомарно пишет acknowledged_unknown, не выдумывает exit_code и не убивает процесс. Это снимает блок интеграции по явно принятому неизвестному исходу. Удаление остаётся заблокированным: смерть исполнителя не доказывает отсутствие его writer-потомка. Исключение — подтверждение записи предыдущей загрузки ОС. В остальных случаях нужны диагностика и явная остановка конкретного процесса; нельзя удалять запись ради обхода проверки.

## Проверки и ограничения

Unit проверяет завершение, malformed/legacy/unknown, точное подтверждение и разные допуски интеграции/удаления. Реальные тесты Mac подтверждают событие completion без повторного write_stdin и отказ файловой записи в sandbox. Electron fixture использует настоящий read-only HTTP-сервер: URL доступен после интеграции финальной задачи и отчёта, удаление запрещено до его явной остановки. Native Windows sandbox и живой ChatGPT требуют отдельной пользовательской приёмки; упаковка Windows их не доказывает.
