# Review — согласование нового плана

Независимое ревью планировочного документа и машинного to-do plan через Claude CLI до публикации ACTIVE scope. Главный агент — ChatGPT Web; он пишет документы, читает отзывы, формулирует позицию и выполняет план. Claude только рецензирует. Workflow Kit управляет состоянием и публикацией; Web Pilot показывает кнопку и при необходимости продолжает разговор. Расширение ACTIVE и явный `plan:carryover` сохраняют обычный контракт первой версии.

## Управление

В карточке плана две независимые кнопки, доступные и при NONE: «Включить/Выключить Review» и «Включить/Выключить автовыполнение». У обеих ON зелёный (`#087c45`, светлая и тёмная темы), OFF — обычный вид; `aria-pressed` обозначает состояние, название — следующее действие. Review по умолчанию OFF. Выбор Review принадлежит checkout и переживает перезапуск; AutoPlan хранится отдельно в settings.json. При ACTIVE Review задаёт режим следующего нового плана, не перезапускает выполнение.

Слева от текста статуса — декоративный `#plan-review-indicator` (`aria-hidden`); текст остаётся `role=status`. RUNNING с подтверждённым runner и PUBLISHING показывают спиннер; AGREED/PUBLISHED — статический успех; PREPARED/AUTHOR_PENDING — статическое ожидание. NEEDS_USER, STALE, ошибки чтения, очистки, подтверждения работы или сохранения продолжения — внимание. При OFF нет фиктивной активности, при `prefers-reduced-motion` нет анимации. `PlanReviewClient` проверяет RUNNING через `reviewStatus`: watchdog каждые ≤15 с только до started_at + 905 с; вне RUNNING и после dispose таймера нет. Потерянный PID → NEEDS_USER; неподтверждённая работа или дедлайн → внимание без автоповтора. Отсутствие видимого прогресса ChatGPT не считается потерей связи ([восстановление](context-delivery.md)).

Review OFF публикует план обычным способом; ON предварительно согласует спецификацию и задачи. Каждый новый scope получает AutoPlan OFF. После публикации пользователь включает автовыполнение данного проекта для последовательного продолжения либо выдачи parallel-групп. Состояние других проектов не меняется.

Кнопка ON разрешает рецензента без отдельного подтверждения каждого раунда. OFF полностью возвращает обычную публикацию, в том числе после спора: отдельного разрешения обхода нет. Кнопка сама не публикует план. При OFF во время Claude будущие раунды и продолжения прекращаются; запущенный процесс учитывается до завершения. Если план уже опубликован и начат, его открытые файлы удаляются после закрытия процесса.

Нужен доступный локальному исполнителю, авторизованный пользователем Claude CLI с поддержкой `claude-opus-5-5` и `--effort high` (Windows — `claude.exe`). Автоматической установки, логина или смены модели нет. Старый Kit даёт сообщение об обновлении через Доктор. Review не меняет AutoPlan, не добавляет разрешение исполнения и не создаёт план чата.

## Код и границы

- Kit: `packages/workflow-kit/src/lib/plan-review.mjs` — подготовка, состояние, разрешение проблем, проверка публикации и очистка; `claude-review.mjs` — процесс и результат; `actions.mjs` — общая нормализация, создание scope, `task:start`; `cli.mjs`, `command-help.mjs`, `recovery.mjs`, `inspection-inputs.mjs` — команды и контекст.
- Web Pilot: `src/plan-review.mjs` (`PlanReviewClient`) — данные выбранного checkout; `review-continuation.mjs` (`ReviewContinuation`) — продолжение на паузе; `automation-send-state.mjs` (`AutomationSendState`) — общая защита отправок Review/AutoPlan; `main.mjs` — события и соединение модулей.
- UI: `#plan-review-toggle`, `#plan-review-message`; `preload.cjs` → `pilot:plan-review({workspace,enabled})`. Обычная проверка `assertLocalSender`, строгий boolean и совпадение выбранной папки (`REVIEW_SELECTION_CHANGED`). Клиент импортирует доверенный комплектный Kit, не исполняет код из выбранного проекта.
- Путь запуска: ChatGPT → существующие MCP `exec_command`/`write_stdin` → установленный Kit → Claude CLI. Девять MCP-инструментов остаются прежними; нет новой службы, модельного API или опроса в простое.

## Файлы и состояние

Единственный источник политики и стадии — `.harness/runtime/plan-review/state.json`; отсутствующий файл означает OFF. Записи атомарны под коротким `operation.lock`; `generation` увеличивается. Копии настройки Review в settings.json нет. Ошибка чтения видима, не трактуется как OFF.

Папка `.harness/runtime/plan-review/<run-id>` содержит снимки спецификаций, полный вход scope, нормализованный план, позиции автора, запросы, stdout/stderr, машинные отзывы и metadata. Всё вне Git. Рабочая спецификация заранее находится по итоговому пути `docs/planning/*.md`. Снимки не являются вторым current plan и не входят в required recovery.

Состояние хранит базовые HEAD/revision, SHA-256 входов, номера раундов, Claude session ID, пути результата, ошибку и `review_history` успешных отзывов с позициями автора. Ошибка следующей попытки не стирает предыдущий успешный отзыв и обязанность ответить на него.

Обновление с Kit 1.6.3 сохраняет Review и получателя, старый отзыв принимает respond. После изменения HEAD коммитом kit-update нужны актуальные prepare/run; переход проверен на fixture, не в живом ChatGPT/Windows.

`review:prepare` требует явного `recipient_session_id` из стартового сообщения Web Pilot либо `scope.session_id`; при наличии обоих они совпадают. Это адрес доставки, не владелец и не отдельный план чата. Новый цикл без ID, неверный формат и конфликт — `REVIEW_RECIPIENT` до запуска. Вне Web Pilot явно задают `recipient_mode: manual` без ID: автоматической доставки нет. Следующие раунды наследуют адресата. Смена ID (включая прежний null) требует `recipient_change_note` ≥10 символов с прямым поручением пользователя; state сохраняет from/to/note. Выбранный в панели чат не основание для подстановки, старые данные без ID догадкой не исправляются.

Стадии: IDLE → PREPARED → RUNNING → AUTHOR_PENDING либо AGREED; ошибка или предел раундов → NEEDS_USER; отмена → CANCELLED; публикация → PUBLISHING → PUBLISHED. STALE зарезервирован для проекции устаревших входов; команды возвращают `REVIEW_STALE` при несовпадении SHA/HEAD/revision и требуют подготовки актуальной пары.

## Действия основного агента

1. Прочитать recovery и поручение. При Review ON подготовить спецификацию и JSON полной формы scope. Каждая часть спецификации — в `approved_scope.documentation_paths` и required `context_pack.documents`. Проверки задач берутся из действующей `.harness/workflow.json`; для нового проекта сначала настроить их через `config:apply`, сохранив остальные поля.
2. Получить форму: `./scripts/workflow review:prepare --help`. Сохранить JSON вне Git, например `.harness/runtime/review-input.json`: `{scope, documents, recipient_session_id}` с точным Session ID стартового сообщения. Выполнить `review:prepare --input <файл>`.
3. Выполнить `review:run`. Это долгая команда текущего хода: ожидать exec session через `write_stdin`, без `nohup`, `&` или повторного запуска. После прерывания сначала `review:status`.
4. Прочитать весь успешный отзыв и сохранить позицию через `review:respond --input <файл>`, включая финальный approved с minor. Исправления и нужные исполнителю решения внести в публикуемые spec/критерии. Для изменённой пары — `review:prepare` с той же scope_id, затем `review:run`; необязательный `response` описывает изменения и не заменяет сохранённую позицию.
5. Неизменённая approved-пара с позицией accept — `review:publish` без формального нового раунда. Изменение проверенных документов требует нового согласия; позиция автора его не заменяет. Не объявлять замечания снятыми от имени Claude.
6. При NEEDS_USER сохранить позицию, если есть успешный отзыв, выполнить `review:acknowledge`, сообщить причину и спросить пользователя. Затем ждать. По ответу: `review:resolve --action retry|publish|cancel --note "решение пользователя"`. Retry разрешает ещё попытку сверх лимита; publish — публикацию со спором или после ошибки; cancel освобождает checkout. `review:cancel --note …` отменяет незапущенный цикл. Агент не меняет enabled самостоятельно.

При OFF публикация обычная, согласия Claude не требуется даже после NEEDS_USER. Для связанного подготовленного плана можно использовать `review:publish`; обычные `scope:create`/`plan:create` также разрешены. Отсутствие пользовательского ответа при ON не заменяется решением агента.

### Позиция автора

Вход `review:respond`: `{round, disposition, position}`. `round` — номер последнего успешного отзыва из `review:status`, даже если более поздняя попытка завершилась ошибкой. `position` ≥40 символов: что принято/отклонено и почему, оставшиеся разногласия, решения и их места в spec/критериях либо почему новых решений нет. `disposition`: `accept` — согласен; `revise` — исправлю документы; `needs_user` — существенный нерешённый спор, требуется пользователь.

Kit сохраняет `round-N-author-*.json` с номером раунда, отзывом и его SHA, digest плана, SHA спецификаций и позицией; нового раунда нет. Файл привязан к проверенной паре, даже если рабочие документы уже исправлены. Позиции проверяются перед следующим prepare/run и публикацией при ON: отсутствие — `REVIEW_RESPONSE`, изменение сохранённого отзыва/позиции — `REVIEW_RESPONSE_STALE`. needs_user переводит цикл в NEEDS_USER; запись позиции не заменяет решение пользователя. Семантику текста и перенос решений проверяет автор: длина и SHA не являются автоматическим смысловым арбитражем.

Явное `resolve publish` после NEEDS_USER допускает публикацию при оставшемся споре, не объявляя его снятым. Успешный отзыв на текущую пару всё равно требует позиции; при ошибке без такого отзыва она не нужна. Проверки актуальности пары сохраняются. Note пользователя переносится в `user_decisions` опубликованного плана. Остальные существенные решения должны быть в spec/критериях до финального ревью: временные позиции удалятся при начале выполнения.

## Контракт runner

Один новый UUID с `--session-id`, последующие раунды — ровно тот же ID через `--resume`. Нет `--continue`, fork или молчаливой новой сессии. Начальный лимит — четыре раунда, 30 CLI turns и 900 секунд на запуск. `--max-turns` допускает 1–100, `--timeout-ms` — 100–900000. Timeout завершает только собственный дочерний процесс (TERM, затем KILL через 5 секунд).

Аргументы передаются массивом, `shell:false`, prompt — stdin, полный stdout/stderr — файлы. Флаги: `--model claude-opus-5-5 --effort high`, `--output-format json --json-schema …`, Read/Glob/Grep, dontAsk, permission-prompts none, strict-mcp-config, disableAllHooks, disable-slash-commands, no-chrome. Память и история разрешены; свежие решения пользователя и снимки важнее прошлого контекста. Ограничения инструментов не объявляются изоляцией всей памяти или файловой системы.

Успех требует exit 0, `subtype=success`, `is_error=false`, точного session ID, модели в modelUsage, корректного вердикта и неизменных входов. Effort подтверждается argv; внутренние рассуждения не измеряются. Runner сам связывает результат с SHA, не просит модель вычислять хеши.

Вердикт: `approved|changes_requested`, непустой summary, findings с уникальными id, severity `critical|major|minor`, status `open|resolved|accepted_limitation`, reason. Approved с незакрытым major/critical отклоняется как `REVIEW_FORMAT`; accepted_limitation допустим для minor. При ошибке формата, CLI, авторизации, модели, session, SHA или timeout — NEEDS_USER, не согласие. Потерянный PID ожидающего процесса даёт `REVIEW_INTERRUPTED`; неизвестный процесс не запускается повторно автоматически.

Lock удерживается только на коротких переходах. Metadata записывается до объявления результата готовым. Завершение сливает актуальную политику кнопки, не возвращает старое enabled.

## Публикация и очистка

`prepareReview` использует тот же `buildScopePlan`, что `createScope`: рецензент получает нормализованные задачи, зависимости и DOCS. `plan:create` при ON возвращает `REVIEW_REQUIRED` до изменения checks. `scope:create` внутри lock проверяет точную пару, позиции и approved + accept либо явное resolve publish. Фиксируются проверенные спецификации и план, посторонние dirty документы не входят; checks не заменяются. Закоммиченные blobs сверяются с SHA (допускается CRLF→LF). Это защита workflow от ошибок, не криптографический барьер против агента с полным файловым доступом.

После неопределённого коммита — штатные status/repair, затем повтор `review:publish`. Повтор подтверждённой публикации идемпотентен. AutoPlan не начинает связанный ACTIVE при Review ON до подтверждения PUBLISHED; при OFF действует обычная проверка плана и транзакции.

Успешный первый `task:start` запускает `cleanupReview` в Kit, поэтому ручной старт и AutoPlan равнозначны, открытый Web Pilot не нужен. Проверяются scope/run, принадлежность пути checkout, отсутствие symlink и необычных файлов. Удаляется только зарегистрированная папка данного ревью; соседние папки, старые эксперименты и глобальная история Claude сохраняются. RUNNING/NEEDS_USER не очищаются. Если при OFF задача началась во время Claude, runner завершает очистку после закрытия своих файлов.

После очистки остаётся минимальное состояние с политикой, идентификаторами и фактом публикации/уборки, без архива отзывов. Спецификация и current plan остаются. Ошибка уборки видима в результате команды, recovery и UI; начатая задача не откатывается. Повтор `task:start` до раннего возврата повторяет очистку; уже отсутствующая папка считается удалённой.

## Автоматическое продолжение

Обычный путь — основной агент ведёт раунды в текущем ходе. Если он остановился, файловый сигнал state.json через ProjectInputWatch и подходящая пауза страницы запускают ReviewContinuation даже при NONE и AutoPlan OFF. Он повторно использует машину AutoPlan и Composer: правильный workspace/session/URL, готовая страница, нет busy/draft, ручной Stop запрещает продолжение до нового пользовательского сообщения. Review OFF прекращает будущие отправки.

Перед самой отправкой повторно проверяются выбранные workspace/session/URL, сохранённые run/generation и recipient_session_id, даже если файловый сигнал ещё не пришёл. Чужой чат/checkout не получает продолжение. Автосообщение «Продолжи ревью нового плана» требует status, review:respond на успешный отзыв, переноса решений и нового согласия после изменений; выполнения кода оно не разрешает. При NEEDS_USER допустимо одно уведомление агенту, затем acknowledge/notification_handled останавливает продолжения до решения пользователя.

Общий AutomationSendState защищает отправки Review и AutoPlan на одной паузе разговора независимо от смены scope: сохраняет sending до Send, sent после. UNKNOWN не повторяется. Дополнительно сохраняются checkpoint продолжения и ручные остановки в settings.json (`projectAutoPlan[workspace].sessions[sessionId].automationCheckpoint` для живого основного чата, `reviewCheckpoint`; прежний общий automationCheckpoint сохраняется для пути без runtime), без текстов документов/беседы. Журналы ограничены 400 записями. Общий журнал использованной паузы сохраняется между scope, разрешение AutoPlan следующему плану не переносится. Нативные диалоги разрешений не нажимаются.

## Проверки и пользовательская приёмка

Автоматические: `kit-check` — временные Git-проекты, имитация CLI, позиции каждого успешного раунда/approved, неизменённая и изменённая пара, resolve publish со спором и без отзыва, SHA, OFF, repair, cleanup/symlink. `unit-all` — startup → prepare → продолжение, пауза/restart, неверный или чужой ID, явный подхват, Stop/draft/UNKNOWN, watchdog, переход с выпущенного Kit 1.6.3. `electron-smoke` — обработчики preload/IPC, четыре сочетания кнопок в двух темах, aria, индикаторы/reduced motion, STALL без recovery и защищённая перезагрузка на TEST FIXTURE. Это не приёмка живого ChatGPT или полного цикла реального Claude. Сообщённые пользователем результаты прежних тестовых проектов не подменяются fixture-проверками; сами эти проекты не изменяются.

После полного перезапуска установленного приложения пользователь проверяет на временном проекте:
1. Обновить Kit через Доктор, если требуется; убедиться, что Claude CLI авторизован у исполнителя.
2. На незавершённом ACTIVE проверить ON/OFF обеих кнопок и восстановление того же плана после перезапуска. Новый scope должен получить AutoPlan OFF. При NONE включить только Review: дождаться реальных отзывов, позиции на каждый раунд (включая approved) и ACTIVE; выполнение само не начинается. Во время Claude — текст/спиннер, в ожидании пользователя — статический знак; длительное молчание не открывает recovery.
3. Проверить паузу между раундами без Manual Stop: продолжение только своему чату, в том числе после перезапуска; чужому чату ничего не отправляется. До старта задачи проверить финальную позицию и решения в spec/критериях. Затем начать первую задачу: удалён только свой run, опубликованные документы и соседние папки сохранены.
4. При Review ON дождаться публикации нового временного последовательного плана, проверить AutoPlan OFF и включить его: выполнение начинается автоматически. Parallel-план запускает группы при AutoPlan проекта ON; дальнейший сценарий — [приёмка исполнителей](parallel-execution-acceptance.md).
5. Проверить Review OFF с обоими положениями автовыполнения. Ошибку авторизации и спор моделировать только в тестовом окружении: агент спрашивает пользователя, материалы остаются, повтор разрешается ответом.

Живой ChatGPT, чистая macOS и native Windows остаются отдельной пользовательской приёмкой. Кросс-сборка Windows и подмена платформы не подтверждают native Windows.
