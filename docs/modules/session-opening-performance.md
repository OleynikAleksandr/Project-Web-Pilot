# Быстрое открытие сессий и планов

## Контракт

Scope session-opening-performance-029 принадлежит существующим модулям Workspace & Sessions и Workflow Kit / Context Recovery. Первые пять микрозадач завершены и проверены пользователем. Поручением 17.09.2026 разрешено продолжить текущий план до нового релиза и финальной DOCS, объединить нужные изменения в main и удалить лишние рабочие деревья и ветки. План остаётся в этой сессии; архивирование не поручено.

Вход: канонический workspace, сохранённый projectId, явный sessionId, собственный planId/revision и поколение навигации. Выход: свежая проекция именно выбранной сессии (включая NONE и подготовленные здесь планы), начало загрузки её URL и отдельное состояние полной проверки: checking, ready или error. Старый результат не меняет новый выбор, даже при A→B→A.

### Быстрое чтение и полная готовность

Подключённый проект сначала проходит короткое чтение пути, идентичности и принадлежащего сессии канонического плана. Используется доверенный поставляемый фасад Workflow Kit; код из непроверенной папки проекта не импортируется. Отсутствующий/неоднозначный владелец не подменяется последним чужим планом. Свежая проекция показывается до полной диагностики и до сетевой готовности ChatGPT.

Сохранённый чат открывается для просмотра без ожидания MCP/tunnel и повторной отправки контекста. Новая сессия и явное обновление требуют актуальной полной готовности и COMPLETE recovery именно выбранного адреса; проверки перед Send сохраняются. До T006 фоновая проверка консервативно не разрешает прикрепление контроллера, способного отправлять контекст.

Полная проверка продолжает проверять все канонические планы, Git references, обязательные документы, manifest/owned files, hooks и launcher. Первое подключение, установка, reconnect, upgrade и явный Doctor используют строгий путь. Ошибка фона видима с повтором и доступом к Доктору; просмотр старого чата не равен готовности отправить новый контекст.

### Фасады и реализация

- Workflow Kit сохраняет владельца plan/recovery: штатные Git pretty formats для trailers, пакетные операции Git там, где профиль доказывает пользу, один проверенный результат plan/history/recovery внутри одной операции inspect. CLI-ответы и семантика ошибок совместимы.
- WorkspaceSetup сохраняет изолированный доверенный worker и строгий preview/apply. Короткий fingerprint и проверка готовности используют те же входы и границы, без второй сборки контекста.
- Небольшой WorkspaceReadiness helper хранит только readiness в памяти (не более четырёх результатов); одинаковые запросы объединяются. Число выполняемых проверок ограничено, очереди устаревших выборов не накапливаются. Ошибки не кэшируются как успех.
- WorkspaceSessions сохраняет атомарную очередь записей. Тяжёлые чтения не удерживают общую очередь IPC. Поколение выбора проверяется до публикации проекции, URL, health и прикрепления контроллера; закрытие окна отменяет публикацию.
- SessionPlans читает доверенный фасад; session store не становится копией задач. ContextCache остаётся отдельно адресованным workspace/sessionId/planId.

### Актуальность

Отпечаток до и после проверки охватывает канонический корень, HEAD, index, изменения файлов по содержимому, refs/replace и существенную Git config, canonical plan inventory и содержимое, workflow config, required-документы всех планов и task inputs, manifest/owned files, hooks, launcher, transaction и версию поставляемого Kit. Изменение файла с прежними размером/mtime обнаруживается. Одного TTL, mtime либо количества файлов недостаточно.

Внутреннее переиспользование validation ограничено одной проверкой; произвольный внешний объект не может подменить validation. Результат состояния A нельзя выдать за готовность состояния B. Допустим один ограниченный повтор при изменении входов; далее явная ошибка. Новые/удалённые/привязанные/архивированные планы, upgrade/Doctor и перезапуск инвалидируют соответствующее состояние. Сомнительные состояния и активная транзакция не разрешают кэшированный успех.

## Границы

Сохраняются Chat/Work и URL, ручное создание подготовленного продолжения, NONE, текущая сортировка дерева/три строки/прокрутка, темы и тонкие линии 0.6.28. Не меняются внешний Codex Local runtime, WF001, пользовательские VM, профили и облачные чаты. Новых зависимостей и постоянной службы кэширования нет. Установленный и bundled Kit синхронны; manifest согласуется только штатным доверенным upgrade/Doctor.

## Проверка и цели

Исходная диагностика 17.09.2026: preview 16134/16488 мс на 0.6.28, HEAD d07ac2c, два канонических плана; чтение своего плана 11/5/5 мс, contextInputKey 36/28/25 мс. Это наблюдения, не обещанная итоговая скорость. Новая сессия добавила третий план; сравнения обязаны указывать состав.

Цели текущего Mac: p95 локального показа свежего плана и начала loadURL ≤1 с по 30 переключениям; ≤2 с от shell-ready на каждом из пяти запусков. Полный app-start-to-plan измеряется отдельно. Полная проверка сопоставимого проекта должна ускориться минимум на 60%. Сетевая загрузка ChatGPT и MCP round trip не включаются в локальные измерения.

T001 сохраняет повторный baseline и методику; T002–T005 — профильные regression и локальные измерения. Полная матрица гонок, 30 переключений/5 стартов и масштабирование относятся к T008; packaged замеры и обе поставки — к T009. CI/source timings не выдаются за packaged результат, native Windows/чистые VM — за выполненные без запуска.

Проверяются неоднозначные/повторные trailers, continuation lines, Unicode, Workflow-Iteration, нелинейная история/replace refs, неверные dependency order и состав коммита; все планы и COMPLETE; NONE и prepared links; разные workspace, A→B→A, закрытие окна, изменения HEAD/index/документов/планов/транзакции, stale/error retry и отсутствие повторной отправки.

## T001 — повторный baseline

На неизменённом d07ac2c с двумя планами preview: 16139.02 / 15743.49 / 15998.36 мс, 1283 процесса Git на вызов, включая вложенные recover. В текущем checkout с третьим планом: 17113.72 мс и 1417 процессов. Собственное чтение плана занимает 3.50–4.33 мс. Методика, raw samples и отдельные startup-измерения описаны в docs/VERIFICATION.md; это исходные source-измерения до реализации. Windows payload: MinGit 2.55.0.windows.5, фактический native запуск не проведён.

## T002 — пакетные операции Git

Git log читает trailers одним процессом в NUL-разделённых полях; редкие сообщения с patch divider --- сохраняют штатный interpret-trailers --parse. Git rev-list проверяет несколько зависимостей одним обходом графа; одиночная зависимость использует merge-base. Самописного графа и долговременного кэша объектов нет. Повторные полные чтения остаются предметом T003. Сопоставимые preview: 8127.5 / 7689.2 / 7663.3 мс, медиана быстрее на 51.9%; 583 процесса Git вместо 1283.

## T003 — одна согласованная проверка

recoverState всегда самостоятельно проверяет план и историю и возвращает packet/validation/snapshot одной операции; status использует этот результат. inspectWithDiagnostics собирает все планы и диагностику за один проход, worker берёт COMPLETE из него и не вызывает отдельные recover для современной версии Kit. Общий inspectionInputs проверяет актуальность до/после; изменение входов допускает один повтор и затем CONCURRENT_CHANGE. Полный preview двухпланового baseline: 3292.95 / 3020.55 / 3054.24 мс, медиана −80.9%; 213 Git-процессов и два log вместо 1283/десяти.

Отпечаток хеширует байты объявленных входов всех планов, owned/managed anchors, hooks, global attributes/excludes, обычный/split index, refs/config и служебные receipts/transaction. Посторонние файлы учитываются по именам/status: их содержимое не входит в recovery, поэтому чужие symlinks/submodules/большие файлы не блокируют проверку. Крупные native executables учитываются по resolved identity, dev/inode, size, ctime/mtime и mode; одного mtime недостаточно. fsmonitor выключен для fingerprint. Ключ вычисляется worker-процессом, не синхронно в Electron main.

## T004 — readiness в памяти

WorkspaceReadiness хранит до четырёх готовых результатов, один выполняемый worker и один последний ожидающий workspace. Одинаковые запросы объединяются, вытесненный ожидающий выбор получает READINESS_SUPERSEDED. Перед reuse worker заново вычисляет content-key; cache hit не запускает inspect. До/после новой проверки ключи должны совпасть, transaction и отмена исключают ready-кэш. Ошибки не кэшируются; возможен один повтор при гонке. preview/apply/явная invalidateReadiness используют строгую инвалидизацию, перезапуск начинает с пустого кэша. RecoveryCache остаётся отдельным.

## T005 — ранняя проекция и навигация

В исходниках единый openConnectedSession открывает сохранённый выбор при запуске, переходе между сессиями и смене проекта. readSessionPlans использует доверенный bundled фасад и проверяет project identity; installed JavaScript не импортируется для показа плана. Существующая миграция legacy evidence и первое подключение сохраняют полный строгий путь. NONE и prepared links читаются по выбранному sessionId.

Чтение selectSession выполняется до очереди записей; атомарный save проверяет поколение до rename, а при отмене во время rename восстанавливает прежний снимок внутри той же очереди. Запросы навигации проходят отдельно от очереди IPC, сайдбар принимает следующий клик сразу. Поколение async action сохраняется через AsyncLocalStorage: старый обработчик не перехватывает новый выбор, собственная актуальная ошибка не теряется после await. Закрытие окна отменяет callbacks.

Фоновый readiness имеет отдельные checking/ready/error и кнопки повтора/Доктора. Controller прикрепляется только после готовности выбранного адреса и окончания его loadURL; новая навигация отменяет прежний controller. Settings/cancel возвращаются к уже загруженному DOM без обязательной перезагрузки, сохраняя черновик и ответ. Детальная интеграция доставки и before-Send остаётся T006; релиз — T009.

## T006 — доставка только из актуального состояния

Сохранённые sent/legacy/unknown чаты открываются без runtime.ensure, прогрева и новой сборки recovery. Подготовка запускается только для новой или явно обновляемой сессии; ожидание composer/черновика допускает адресованный прогрев. warm использует тот же load: холодная подготовка проверяет ключ до/после, готовый кэш — один раз при чтении, без дополнительного одинакового вычисления.

В приложении ключ RecoveryCache строится из текущего результата WorkspaceSetup.ready и нормализованных sessionId/planId. Он включает общие входы полной проверки, а адрес остаётся отдельным. Ошибка readiness или вычисления ключа запрещает сборку/отправку, не подменяется TTL. Перед Send повторно проверяются готовность, ключ, адрес и поколение; старый пакет без ключа требует новой подготовки. Неактуальный уже вставленный черновик сохраняется как prepared-stale. Канонический builder и внешний runtime не меняются.

## T007 — совместимый Workflow Kit 1.4.1

Patch-версия сохраняет схемы планов и публичные CLI-ответы. Fresh install использует 1.4.1; целая 1.4.0 обновляется штатным upgrade с backup. Worker и Doctor явно поддерживают прежнюю 1.4.0. Doctor также проверяет required-документы отдельных задач всех канонических планов; отсутствие файла не исправляется догадкой. Installed/bundled синхронны, manifest текущего проекта согласован штатным Doctor после проверки полного совпадения.

## T008 — проверка и дополнительное устранение повторов

Trace2 первого холодного прохода выявил запись stat-cache индекса из Git diff, несмотря на GIT_OPTIONAL_LOCKS=0. Это вызывало повтор recovery и полной инспекции. Общий Git facade использует штатный `-c diff.autoRefreshIndex=false`; явные stage/commit и обязательные locks сохраняются. Пустое изменение только mtime проверяется без записи index, реальные HEAD/index/plan/document/transaction после вставки по-прежнему блокируют Send. См. [Git diff.autoRefreshIndex](https://git-scm.com/docs/git-config#Documentation/git-config.txt-diffautoRefreshIndex).

Финальный полный preview сопоставимого проекта (340 commits, два плана с 14/13 задачами, revisions 622/474): 3246.1 / 3357.1 / 3268.9 мс, медиана 3268.9 мс, на 79.6% быстрее baseline 15998.36 мс. Во всех трёх вызовах 213 Git-процессов и два log. Добавление 200 commits: 3726.7 мс и те же 213 процессов; четыре плана и 542 commits: 4607.9 мс, 301 процесс/четыре log. 30 одновременных readiness-запросов дают одну инспекцию и максимум один worker. Полные raw samples и UI/startup evidence — docs/VERIFICATION.md и локальная папка T008-profile.
