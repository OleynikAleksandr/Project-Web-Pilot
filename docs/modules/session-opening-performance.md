# Быстрое открытие сессий и планов

## Контракт

Scope session-opening-performance-029 принадлежит существующим модулям Workspace & Sessions и Workflow Kit / Context Recovery. Пользователь разрешил выполнить первые пять микрозадач и остановиться с отчётом; оставшиеся задачи, финальная DOCS и выпуск продолжаются только после следующего поручения.

Вход: канонический workspace, сохранённый projectId, явный sessionId, собственный planId/revision и поколение навигации. Выход: свежая проекция именно выбранной сессии (включая NONE и подготовленные здесь планы), начало загрузки её URL и отдельное состояние полной проверки: checking, ready или error. Старый результат не меняет новый выбор, даже при A→B→A.

### Быстрое чтение и полная готовность

Подключённый проект сначала проходит короткое чтение пути, идентичности и принадлежащего сессии канонического плана. Используется доверенный поставляемый фасад Workflow Kit; код из непроверенной папки проекта не импортируется. Отсутствующий/неоднозначный владелец не подменяется последним чужим планом. Свежая проекция показывается до полной диагностики и до сетевой готовности ChatGPT.

Сохранённый чат открывается для просмотра без ожидания MCP/tunnel и повторной отправки контекста. Новая сессия и явное обновление требуют актуальной полной готовности и COMPLETE recovery именно выбранного адреса; проверки перед Send сохраняются. До T006 фоновая проверка консервативно не разрешает прикрепление контроллера, способного отправлять контекст.

Полная проверка продолжает проверять все канонические планы, Git references, обязательные документы, manifest/owned files, hooks и launcher. Первое подключение, установка, reconnect, upgrade и явный Doctor используют строгий путь. Ошибка фона видима с повтором и доступом к Доктору; просмотр старого чата не равен готовности отправить новый контекст.

### Фасады и реализация

- Workflow Kit сохраняет владельца plan/recovery: штатные Git pretty formats для trailers, пакетные операции Git там, где профиль доказывает пользу, один проверенный результат plan/history/recovery внутри одной операции inspect. CLI-ответы и семантика ошибок совместимы.
- WorkspaceSetup сохраняет изолированный доверенный worker и строгий preview/apply. Короткий fingerprint и проверка готовности используют те же входы и границы, без второй сборки контекста.
- Небольшой WorkspaceReadiness helper хранит только readiness в памяти (не более четырёх результатов); одинаковые запросы объединяются. Число выполняемых проверок ограничено, очереди устаревших выборов не накапливаются. Ошибки не кэшируются как успех.
- WorkspaceSessions сохраняет атомарную очередь записей. Тяжёлые чтения не удерживают общую очередь IPC. Поколение выбора проверяется до публикации проекции, URL, health и прикрепления контроллера; закрытие окна отменяет публикацию.
- SessionPlans читает доверенный фасад; session store не становится копией задач. ContextCache остаётся отдельно адресованным workspace/sessionId/planId.

### Актуальность

Отпечаток до и после проверки охватывает канонический корень, HEAD, index, изменения файлов по содержимому, refs/replace и существенную Git config, canonical plan inventory и содержимое, workflow config, required-документы всех планов и task inputs, manifest/owned files, hooks, launcher, transaction и версию поставляемого Kit. Изменение файла с прежними размером/mtime обнаруживается. Одного TTL, mtime либо количества файлов недостаточно.

Внутреннее переиспользование validation ограничено одной проверкой; произвольный внешний объект не может подменить validation. Результат состояния A нельзя выдать за готовность состояния B. Допустим один ограниченный повтор при изменении входов; далее явная ошибка. Новые/удалённые/привязанные/архивированные планы, upgrade/Doctor и перезапуск инвалидируют соответствующее состояние. Сомнительные состояния и активная транзакция не разрешают кэшированный успех.

## Границы

Сохраняются Chat/Work и URL, ручное создание подготовленного продолжения, NONE, текущая сортировка дерева/три строки/прокрутка, темы и тонкие линии 0.6.28. Не меняются внешний Codex Local runtime, WF001, пользовательские VM, профили и облачные чаты. Новых зависимостей и постоянной службы кэширования нет. Установленный и bundled Kit синхронны; manifest согласуется только штатным доверенным upgrade/Doctor.

## Проверка и цели

Исходная диагностика 17.09.2026: preview 16134/16488 мс на 0.6.28, HEAD d07ac2c, два канонических плана; чтение своего плана 11/5/5 мс, contextInputKey 36/28/25 мс. Это наблюдения, не обещанная итоговая скорость. Новая сессия добавила третий план; сравнения обязаны указывать состав.

Цели текущего Mac: p95 локального показа свежего плана и начала loadURL ≤1 с по 30 переключениям; ≤2 с от shell-ready на каждом из пяти запусков. Полный app-start-to-plan измеряется отдельно. Полная проверка сопоставимого проекта должна ускориться минимум на 60%. Сетевая загрузка ChatGPT и MCP round trip не включаются в локальные измерения.

T001 сохраняет повторный baseline и методику; T002–T005 — профильные regression и локальные измерения. Полная матрица гонок, 30 переключений/5 стартов и масштабирование относятся к T008; packaged замеры и обе поставки — к T009. CI/source timings не выдаются за packaged результат, native Windows/чистые VM — за выполненные без запуска.

Проверяются неоднозначные/повторные trailers, continuation lines, Unicode, Workflow-Iteration, нелинейная история/replace refs, неверные dependency order и состав коммита; все планы и COMPLETE; NONE и prepared links; разные workspace, A→B→A, закрытие окна, изменения HEAD/index/документов/планов/транзакции, stale/error retry и отсутствие повторной отправки.

## Основа решения

Используются штатные средства Git и существующий worker:
- https://git-scm.com/docs/pretty-formats — формат %(trailers:only,unfold);
- https://git-scm.com/docs/git-interpret-trailers — семантика parse, divider и continuation;
- https://www.electronjs.org/docs/latest/tutorial/performance — не блокировать main process тяжёлой работой.

## T001 — повторный baseline

На неизменённом d07ac2c с двумя планами preview: 16139.02 / 15743.49 / 15998.36 мс, 1283 процесса Git на вызов, включая вложенные recover. В текущем checkout с третьим планом: 17113.72 мс и 1417 процессов. Собственное чтение плана занимает 3.50–4.33 мс. Методика, raw samples и отдельные startup-измерения описаны в docs/VERIFICATION.md; это исходные source-измерения до реализации. Windows payload: MinGit 2.55.0.windows.5, фактический native запуск не проведён.
