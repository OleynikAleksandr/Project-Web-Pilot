# Пользовательская приёмка параллельного исполнения

Протокол выполняет пользователь на установленном выпуске. Автоматические fixtures пройдены, но не подтверждают работу реального ChatGPT, чистой ОС или native Windows. До прямой приёмки план остаётся READY_FOR_ACCEPTANCE; агент его не закрывает.

## Подготовка

Полностью выйти из Web Pilot и открыть через прежний алиас. Вверху панели должна быть 0.6.110; Kit тестового проекта обновить до 1.7.2 через Доктор. Работающий app/MCP агент при выпуске не перезапускает. Использовать новый ненужный тестовый проект и вручную войти в ChatGPT. Основной сценарий повторить отдельно в Chat и Work. Дальнейшую параллельную реализацию разрешать только после этой приёмки.

## Пять задач, общий результат и сервер

1. В Settings задать разрешение parallel и лимит 3, затем создать новую основную сессию. План: T001 — общая основа; T002/T003/T004 — три независимых инструмента с зависимостью от T001; T005 — итог на основе всех трёх. Непересекающиеся области записи не заменяют смысловую проверку зависимостей. При Review ON согласовать обычным способом.
2. Включить AutoPlan после публикации. T001 идёт одна; три инструмента стартуют после подтверждённой интеграции основы и получают её в базе; T005 ждёт все три интеграции. Изменение Settings не перенастраивает уже созданный план.
3. Проверить только дерево выбранного проекта, его основную сессию и группу исполнителей. В меню доступны поиск, фоновые работа/ошибка и соседние проекты. Переключение возвращает последнюю выбранную сессию, не меняет cwd/работу остальных. В плане ID, название, способ и статус читаются отдельно; галочка только после проверенного merge.
4. Выключить AutoPlan во время инструментов: новые назначения и сообщения не отправляются, уже начатые команды/допустимые интеграции завершаются. Включить снова. Отдельно проверить черновик и ручной Stop: автоматического сообщения нет; новый явный пользовательский ход снимает Stop.
5. После подготовки приложения запустить штатной exec_command с read_only:true HTTP-предпросмотр и записать его URL/session ID. Не использовать обход sandbox или эвристику по имени команды. Сервер должен оставаться доступен во время последних интеграций и после финала. Если на данной ОС защиту подтвердить нельзя, записать отказ, не объявлять проверку успешной.
6. До последнего DONE основная сессия получает ровно одно финальное поручение: завершить Kit-интеграции, проверить общий main, выдать итог и URL. Проверить актуальное содержимое по URL из main. После финального ответа нет нового «Продолжай» при переключении, событиях и restart. AutoPlan выключен по completion, план остаётся READY_FOR_ACCEPTANCE и не архивируется. Соседний проект сохраняет своё разрешение.

## Последовательный режим и неизменность настроек

Изменить Settings уже после создания основной сессии: её сохранённое разрешение и лимит не должны меняться. В новой сессии с разрешением OFF либо лимитом 1 обычный последовательный план выполняется основным чатом без исполнителей. Старый чат и старый план без новых полей открываются без повторной доставки и сохраняют последовательное поведение.

## Перезапуск и безопасное восстановление

На отдельном тестовом запуске перезапустить приложение при незавершённой работе. Проверить прежние чаты/папки, отсутствие повторных назначений и Send. Pending финализации после completion-OFF сохраняется; ручной OFF/Stop, черновик, недоступная страница и sending/UNKNOWN не дают повтор. Сохранённое время не включает закрытый интервал. Прежний ошибочный main-старт восстанавливается Kit 1.7.2 только при доказанном составе, без удаления посторонних изменений.

Если реальная ошибка связи возникла сама, проверить блок восстановления: он относится к своему чату, открывает тот же URL без повторной отправки; черновик, UNKNOWN, ручной Stop и пауза ограничения запросов защищены. Обычное длительное ожидание ответа не является ошибкой связи. Не изменять профиль или сеть ради искусственного повреждения.

## Исправление интеграции

При возникшем конфликте или провале объединённых проверок основной план остаётся незавершённым, другие интеграции и новые группы ждут. При AutoPlan ON и готовом основном чате поручение передаётся автоматически, без дополнительной кнопки; OFF, черновик и активная команда блокируют отправку. Одно поручение приходит именно в основной чат, содержит операцию, причину и команду продолжения; повторные события и UNKNOWN его не дублируют. После исправления и успешных проверок принимается одна интеграция. Ошибка запуска Node отображается как ошибка окружения и не передаётся агенту как конфликт кода. Не создавать конфликт в важном проекте ради этого пункта; автоматическая проверка конфликта уже есть на временном fixture.

## Удаление и повторное имя проекта

При действующем read-only сервере архивировать ненужный проект и попробовать удаление через приложение: DELETE_PROJECT_BUSY, файлы/дети сохранены. Явно остановить точную серверную сессию, получить новое подтверждение и удалить. Проверить отсутствие родителя, всех его исполнителей и локальных разрешений, включая restart; соседний проект цел. Новый проект в той же папке не наследует старую identity, AutoPlan/Review и назначения. Чужие, грязные, неизвестные или подменённые дети удаляться не должны.

## Фиксация результата

| Сценарий | Статус до пользовательской проверки |
| --- | --- |
| Реальные Chat и Work, пятизадачная цепочка, один финал, живой сервер | Открыт |
| AutoPlan ON/OFF, последовательный режим, старые чаты | Открыт |
| Перезапуск, связь, черновик и неизвестный исход | Открыт |
| Исправление реального конфликта | Открыт; fixture не заменяет этот результат |
| Запуск через прежний macOS-алиас | Открыт |
| Native Windows и первый запуск на чистой ОС | Открыты |

Для каждого выполненного пункта записать версию, ОС, Chat/Work и наблюдаемый результат. Невыполненный пункт не отмечать успешным. Сборка Windows на Mac подтверждает упаковку, а не native Windows. Общая фраза «всё работает» означает общую приёмку, а не доказательство каждого непроверенного сценария.
