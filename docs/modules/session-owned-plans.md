# Планы сессий и подготовка продолжения

## Статус реализации

Согласованный 17.09.2026 контракт реализован по прямому поручению пользователя в новой сессии. Выпуск 0.6.28 / Workflow Kit 1.4.0 подготовлен для пользовательской проверки: macOS app обновлён, обе поставки проверены. Все микрозадачи фиксируются отдельными управляемыми коммитами; scope архивируется только по отдельной прямой команде пользователя. Историческое ограничение предыдущей сессии «только подготовить план» исполнено и больше не ограничивает авторизованную реализацию.

Предыдущий scope завершил стенд UTM Clean/Test macOS и Windows ARM64 и диагностику задержек Computer Use. Сведения и отложенная работа сохранены в [CLEAN_INSTALL](../CLEAN_INSTALL.md). Первый запуск Web Pilot в гостях и исправления MCP/tunnel не входят в этот scope.

## Принятый пользовательский сценарий

1. Каждая сессия имеет собственный план либо пока не имеет scope. Открытие любой сессии сразу показывает её собственный план, включая незавершённые и полностью выполненные задачи.
2. Полностью выполненный план остаётся доступным. Пользователь пишет агенту новое поручение в этой же сессии; агент добавляет микрозадачи в её план. Кнопка «+ Задача» не нужна.
3. Обязательная кнопка «Принять» и варианты «Принять и завершить / Принять и продолжить» исключаются из обычного перехода между сессиями. Завершение задач и документов не архивирует план, не создаёт сессию и не вызывает выбор Chat/Work автоматически.
4. В текущей сессии пользователь и агент могут обсудить и подготовить план будущей сессии с использованием текущего контекста. Собственный план текущей сессии при этом сохраняется.
5. Кнопка «Создать сессию с этим планом» открывает СУЩЕСТВУЮЩУЮ карточку выбора Chat / Work. После выбора создаётся сессия с подготовленным планом, решениями и ссылками на необходимые документы. Отмена выбора ничего не создаёт и сохраняет черновик.
6. После создания исходная сессия сохраняет карточку продолжения: название, раскрываемый просмотр того же плана и переход к его сессии. Это ссылка на один план, а не независимо редактируемая копия.
7. Существующие «Новый Chat / Новый Work» в меню проекта создают самостоятельную сессию без scope. Она получает общую навигацию существующего проекта, но не присваивает себе план другой сессии. Новый план обсуждается с агентом.
8. Само создание следующей сессии разрешено независимо от завершённости текущего плана. Возврат в прежнюю сессию не меняет порядок дерева, чужой план или состояние чужой работы.
9. Пользовательская оценка результата сохраняется как часть диалога; она не является обязательной кнопкой закрытия. Явное архивирование/удаление сессий и проектов остаётся отдельным существующим действием. Облачные чаты не удалять.

## Сайдбар и принятый макет

В выбранной сессии:
- «План этой сессии»: название, ход работы и микрозадачи. Без ручной кнопки добавления задач и без кнопки приёмки.
- «План следующей сессии»: обсуждаемый черновик будущего плана, его микрозадачи, документы и кнопка создания сессии.
- Когда черновик получил свою сессию, тот же блок показывает связь с продолжением, раскрываемый просмотр и переход.
- В новой сессии этот план показывается как собственный; исходная сессия доступна по связи происхождения.
- При отсутствии scope отображается понятное пустое состояние; чужой последний план не подставляется.

Принятый интерактивный пример сохранён в [session-plan-navigation](../design/session-plan-navigation.md). HTML там — иллюстрация состояний и переходов; примерные названия/числа задач не являются заданием текущего scope. При интеграции переиспользовать текущие стили, карточку выбора Chat/Work, меню, сортировку новых сессий сверху, прокрутку трёх строк и обе темы. Не переносить прототип как отдельное приложение.

## Владельцы, фасады и инварианты

Работа совместная для существующих модулей **Workflow Kit / Context Recovery** и **Workspace & Sessions**. Новый параллельный менеджер задач не создавать.

- Workflow Kit хранит канонические планы и их историю, управляет задачами/коммитами и формирует контекст. Один и тот же plan/scope имеет стабильный идентификатор при подготовке, привязке и дальнейшем просмотре.
- Workspace & Sessions хранит связь sessionId с собственным plan/scope и происхождение продолжения. Полные задачи в локальном session store не дублируются.
- Web Pilot отображает данные и доставляет уже сформированный Workflow Kit пакет; модельные API и самостоятельная повторная сборка контекста в оболочке не добавляются.
- Входы операций: явный workspace, sessionId, plan/scopeId, ожидаемая revision; при создании также experience Chat/Work.
- Выходы: собственный план сессии либо пустое состояние, список подготовленных здесь планов/ссылок, новая связанная сессия, канонический recovery именно выбранного плана.
- Нужны операции чтения плана сессии, подготовки будущего плана, привязки при ручном создании и продолжения старого плана. Facade: plan:view, plan:prepare, plan:bind, plan:adopt; существующие scope:create/plan:apply/task:start/commit/recover получают --session и при необходимости --plan.
- Просмотр чужого связанного плана не переключает владельца команд агента. Команда из старого чата не должна изменять план, который пользователь только что выбрал в другом чате.
- Идентичность плана важнее глобального «последнего активного». Совместимость с текущим CLI/путём todo-plan реализовать явно; один общий mutable указатель не может быть единственным источником принадлежности.
- Один пишущий агент на worktree сохраняется. Блокировка/проверка revision защищают существующие транзакции, а не требуют закрывать планы остальных сессий.
- Двойной клик, повтор команды или сбой после привязки не создают дубликат сессии и не теряют черновик. После перезапуска восстанавливаются исходная сессия, новая сессия, их планы и связь.
- Commit references, отдельный commit каждой микрозадачи и финальная DOCS сохраняются. Новое поручение к выполненному плану сохраняет прежние DONE-задачи/коммиты и обеспечивает повторную актуализацию документов после новых задач.

## Миграция и границы

Сохранять с backup существующие sessions, chatUrl, experience, имена, архивные планы и Git-историю. Старый план привязывать к сессии только при наличии достоверной связи; не угадывать по названию и не раздавать всем старым сессиям последний scope. Отсутствие восстановимой связи явно зафиксировать и сохранить доступ к историческому плану. Schema v6 сохраняет backup v1–v5; автоматическая привязка использует только уникальные facts доставленных пакетов. При неоднозначности связь остаётся unresolved с явным пояснением в UI.

Изменение затрагивает установленный и поставляемый Workflow Kit, его инструкции, шаблоны, recovery, readiness/doctor и старую логику перехода после приёмки. Обновлять две копии ядра синхронно; manifest/install/upgrade согласовывать штатно. WF001 не менять. Изменения внешнего Codex Local runtime не предполагаются: сначала использовать существующую точку входа; если потребуется расширение внешнего протокола, описать конкретную необходимость, а не править его без отдельного поручения.

На старте checkout был 0.6.26, установленный app — 0.6.27. Сверка src в app.asar выявила только изменённый src/ui/index.html; его тонкие линии и обводка сохранены. Следующий выпуск — 0.6.28.

## Проверка результата

Проверить на fixtures: два разных незавершённых плана в одном проекте; возврат в выполненный план и новая задача через команды агента; черновик с сохранением исходного плана; отмена Chat/Work; создание с подготовленным планом в обоих режимах; отсутствие дублей; сохранение связи и общих данных плана; самостоятельные Chat/Work с NONE; перезапуск/миграция; правильный plan в recovery и кэше; отказ устаревшей записи; DOCS после продолжения; архив/doctor без потери данных.

Существующие Node suite и Electron smoke обязательны перед поставкой. Не использовать реальные профили/чаты для разрушительных сценариев; для реализации этого scope управление пользовательскими VM через Computer Use не требовалось. Последующие разрешения и испытания первого запуска записаны в docs/CLEAN_INSTALL.md. Обе платформы сохраняют единый source. Новый macOS app и отдельные macOS/Windows ZIP готовятся после реализации для проверки пользователя по RELEASE; не объявлять непроведённую проверку в чистых ОС успешной.

## Уточнение реализации T001 — 17.09.2026

В новой сессии пользователь разрешил реализацию. В исходниках проверены фасады `plan/actions/transaction/recovery`, `WorkspaceSessions`, `ContextSession` и `ContextCache`. Сохраняются уже применяемые atomic rename, Git hooks, optimistic revision и одна блокировка worktree; новая СУБД/очередь/параллельный менеджер не нужны. Подобные стандартные подходы разделения workspace state и транзакционной проверки прежнего значения используются в VS Code и Git; сторонний task framework здесь не уменьшает число интеграций.

Каноническая единица — существующий Markdown-plan со стабильным `scope_id` (planId) и полями `owner_session_id`, `prepared_in_session_id`, `session_experience`. Новые планы хранятся в `.harness/plans/by-id/<scope_id>.md`; legacy `todo-plan.md` сохраняет свой путь и историю. Поиск владельца читает только эти файлы: отдельного mutable глобального указателя/дублированного реестра нет. Пустая сессия получает виртуальный navigation-plan NONE с идентичностью проекта. Список подготовленных здесь строится по `prepared_in_session_id`; после привязки файл остаётся тем же.

CLI принимает `--session <sessionId>` и при необходимости `--plan <planId>`; операции над draft проверяют его источник, операции задач — владельца. `plan:prepare`, `plan:bind`, `plan:adopt`, `plan:view` дополняют существующие команды. До появления собственных планов legacy CLI сохраняется; после миграции запись без явной сессии отклоняется, а чтение глобальной навигации не назначает чужой scope. Область команды изолирована в контексте вызова, UI не меняет её выбором строки. Git journal хранит точный путь/идентичность кандидата; hooks читают его из журнала, исторический resolver проверяет файл именно того коммита с fallback на legacy путь.

Все изменения сериализованы существующим worktree lock; новая task отклоняется, пока другая task удерживает право записи. Завершение task освобождает писателя, но оставляет все незавершённые планы доступными. Read-only просмотры не активируют чужой план. Повтор `plan:bind` возвращает ранее привязанную сессию; локальная запись новой сессии использует этот идентификатор и восстанавливается после сбоя. Проверка revision предшествует записи, а отмена выбора не вызывает bind.

Миграция session store — с резервной копией. Надёжное доказательство связи: переданный данной сессии пакет с совпадающими project_id/scope_id; при нескольких кандидатах связь остаётся неразрешённой. Не угадывать по имени/дате/последней открытой строке. Текущий scope явно передан этой сессии; его можно штатно adopt после внедрения. Legacy/архивы сохраняются и доступны для диагностики. Удаление/архив сессии не удаляет файл плана.

Канонический пакет выбранной сессии формирует сам Workflow Kit через его CLI, включая транспортный envelope; Web Pilot только вызывает и доставляет результат. Это использует локальный Node/Workflow entrypoint и не требует менять внешний Codex Local runtime. MCP/tunnel для действий агента сохраняются. Кэш адресуется workspace/session/plan и revision/файлами; несовпадение владельца/запаздывание отменяет отправку.

Manifest обновляется штатной процедурой integrity/reconcile с backup после синхронной разработки двух копий ядра; существующие ownership/hash checks не отключаются. Сборка после всех проверок — версия 0.6.28. Сверка app.asar 0.6.27 с checkout 0.6.26 показала единственное различие в `src/ui/index.html`: линии 0.5px, приглушённый tree-guide и скругление нижней ветви; точный исходник сохранён локально и переносится в T009.
