# Передача контекста

Канонический контракт стартового сценария Web Pilot. С 11.09.2026 пользователь выбрал полный контекст в первом сообщении и короткое подтверждение от агента. Экспериментальный ACK и проверка hooks больше не участвуют в этом сценарии. Поведение MCP согласовано с актуальным mac-codex-local/skills/local-computer/SKILL.md.

## Каноническая последовательность

1. Подготовить либо проверить выбранную папку по WORKSPACE_SETUP до открытия чата. Выбрать её канонический абсолютный путь и прочитать идентичность проекта из Workflow Kit. Связь папка/чат и отдельный session_id сохраняются в приложении.
2. Приложение проверяет и запускает существующий MCP/tunnel. Локальный клиент получает канонический полный пакет через установленный Workflow Kit: recover --session <sessionId> --format packet, используя существующий Node launcher. Это вызов приложения до сообщения, а не дополнительный ход агента.
3. Проверить protocol=inline-context-v1, COMPLETE, workspace, session_id, plan_id, восемь facts, точный UTF-8 размер и SHA-256 всего context. Старый probe/ACK формат, неполный ответ, чужая папка и повреждённый текст отклоняются. Пакет берётся штатным workflow recover; обязательные разделы не сокращаются.
4. Подготовить первое обычное пользовательское сообщение: назначение старта, явный проект/папка/сессия, идентификатор отправки, весь context и инструкция ответа. Агент должен прочитать уже переданный пакет, кратко подтвердить восстановление и в одном-двух предложениях описать проект и текущее состояние. Для этого ответа tools и изменение файлов не требуются.
5. Дождаться входа и свободного поля. Сохранить подготовленную попытку до ввода, а sending — до click. Существующий черновик и активный ответ задерживают автоматический старт. Непосредственно перед Send перепроверить текущую папку/план и полный текст поля.
6. Подтвердить появление своего пользовательского сообщения. Приложение показывает «Контекст передан», его проект, версию и время. Это подтверждение доставки сообщения; отдельного машинного ACK от модели нет.
7. Агент отвечает коротким подтверждением и описанием проекта. Дальнейшие поручения выполняются в выбранной папке по её плану; дополнительные файлы читаются по потребности самой задачи.

## Повторное открытие и обновление

Повторное открытие сохранённого чата не отправляет ещё один пакет. Новый чат создаёт новую сессию и новый request_id. Явное «Обновить контекст» после завершённой доставки получает новый пакет и отправляет новое сообщение. При изменении плана интерфейс показывает устаревшую доставку. Неизвестный исход Send сначала проверяется по чату; он не даёт права на автоматический дубль.

Смена проекта отменяет ещё не выполненные действия. Чужой уже открытый чат не привязывается к новой папке до собственной отправки. Временный URL Work /c/WEB:UUID ожидается до появления постоянного /c/UUID. Чаты версии 0.1 сохраняются; для прямой передачи используется явно выбранное обновление либо новый чат, прежний ACK не выдаётся за новую доставку.

Если план изменился до отправки, подготовленный пакет нужно обновить. Уже вставленный текст не удаляется автоматически: он остаётся черновиком, а UI сообщает об устаревании. После click при сетевом сбое, смене страницы или перезапуске сохраняется неизвестный исход и выполняется только наблюдение.

## Канонический формат пакета и совместимость MCP

Для адресованных сессий Web Pilot вызывает установленный Workflow Kit через существующий Node launcher: recover --session <sessionId> --format packet. Прежний workflow_context_recover с абсолютным workspace сохраняет совместимость неадресованных вызовов. Канонический builder возвращает delivery_protocol, status=ready, completeness=COMPLETE, workspace, session_id, plan_id, plan_path, facts, objective, head, signature, context, context_bytes, context_sha256, generated_at_ms, ack_required=false. Facts включают project_id, project_name, plan_revision, scope_id, execution_scope_status, delivery_status, task_id и task_title; последние два могут быть null.

Через MCP локальный клиент использует только прежний read-only recover, initialize и tools/list. Адресованный recover и bind/adopt выполняются фасадом установленного Kit через отдельный процесс Node; внешний MCP-протокол не менялся. Модельные API отсутствуют. Пакет ограничен 180000 UTF-8 байт; чрезмерный пакет даёт явную ошибку, без скрытого усечения. Полный текст и состав пакета определяет Workflow Kit, а не самостоятельно собранная подборка файлов.


## Recovery Capsule v2 — согласованный контракт 14.09.2026

Workflow Kit формирует не «полный архив проекта», а минимальный execution capsule текущего scope. Новая сессия, ручное «Обновить контекст» и будущий подтверждённый compact используют один и тот же builder; отличается только reason.

Стандартный capsule содержит компактный Workflow Core, идентичность project/workspace/HEAD/plan, цель и progress текущего todo-plan, required context текущего архитектурного модуля, прямые dependency commit diffs, изменения файлов текущей task, релевантную verification evidence и однозначный next action.

Функциональный scope сначала сопоставляется с владельцем из `docs/MODULES.md`. Для существующего модуля сначала согласуется изменение module specification; если владельца нет, сначала создаётся новая specification. Todo-plan реализует уже согласованный контракт. Required документы перечисляются самим plan/task и передаются сразу; optional документы являются reference-only и читаются агентом по необходимости.

Большой `.harness/kit/WORKFLOW.md`, полный исторический `VERIFICATION.md`, полный `PRODUCT.md`/`ARCHITECTURE.md`, старые scopes/build reports и просто «последний завершённый commit» автоматически не входят. `include_last_completed_task` в новой семантике по умолчанию false; commit diff включается только как прямая task dependency или явная context dependency.

Hard limit Workflow Kit должен совпадать с транспортным лимитом Web Pilot 180000 UTF-8 bytes. Soft budget — сигнал качества модульной границы, а не механизм silent truncation. Целевая масса normal capsule — 15–30 KiB, сложного модуля — 30–50 KiB; устойчивый рост к 80–100 KiB требует проверки module/task boundary.

## Адаптер обычного поля

Text area заполняется native value setter с input/change; contenteditable — обычным Chromium insertText. Адаптер проверяет видимость, чужой черновик, активную генерацию и доступность Send. Перед click сравнивается полный текст; нормализуется только представление абзацных переводов строки и неразрывных пробелов браузером. Для подтверждения отправки требуется request_id в сообщении роли user, а не цитата assistant. Unknown outcome не повторяет click.

## Границы

Подготовка пакета приложением и короткий ответ агента не требуют экспериментальных hook tools, challenge, readback или журнала ACK. Git hooks и правила проекта продолжают действовать при разработке. Механизм старта не объявляется внутренним событием ChatGPT. Автоматическое восстановление после compact не входит в этот сценарий и не навязывает оговорки каждому ответу.

## Реализация координатора — T015

ContextSession сохраняет protocol, полный text, request_id, факты пакета и метаданные до ввода. Для первой реплики прямо задан русский короткий ответ с назначением и текущим состоянием проекта; повторное чтение контекста не требуется. Завершённая доставка сохраняется после перезапуска. Старые попытки версии 0.1 показываются отдельно и обновляются только по явной команде. Нового вызова ACK/status/hook нет.

## Интерфейс — T016

Положительный статус называется «Контекст передан»: он появляется после наблюдения пользовательского сообщения и сохранения постоянной связи с чатом. Ответ агента пользователь читает справа. Размер пакета, версия и время передачи доступны в подробностях подключения. Статусы ожидания hook/ACK не показываются.

## Несколько сессий одного workspace — T018

Workspace содержит список сессий. Передача контекста и её результат принадлежат session_id, а не единственному «последнему чату» папки. Новый чат добавляет сессию; выбор старой открывает её сохранённый URL и попытку без новой стартовой отправки. Переключение отменяет ещё не выполненные действия прежней сессии. Сохранённые связи формата 0.1/0.2 переносятся с резервной копией настроек.

## Открытие из дерева — T019

Двойной клик и стрелка раскрывают сессии без отправки сообщений. Выбор дочерней строки открывает конкретный сохранённый чат; новый пакет автоматически нужен только новой сессии, у которой ещё нет отправки. Статус передачи, обновление контекста и возврат в чат относятся к выбранной сессии. Название и дата служат для выбора, идентичность задаётся сохранённым session_id.

## Архив workspace

Архивирование выбранного проекта останавливает его ContextSession и снимает локальный выбор. В настройках tick приостановлен. Возврат из архива сохраняет sessionId, chatUrl, attempts и selectedSessionId; ничего не отправляет автоматически. Открытие возвращённого workspace выполняет обычную проверку готовности и открывает прежний выбранный чат без повторной отправки. Удаление очищает локальные записи, а веб-разговоры остаются в аккаунте пользователя.

### Реализация core v2 — T003

Builder Workflow Kit больше не использует большой `Обязательные правила` как session payload: передаётся только `Workflow Core`. Optional context sections перечисляются как reference-only. Unrelated last-completed commit не добавляется; обязательны только прямые/явные dependencies. Transport API Web Pilot не меняется: он по-прежнему получает COMPLETE text + bytes/hash/facts, поэтому переход на v2 не требует нового MCP protocol.

## Анализ ускорения — 15.09.2026 / scope 012

Исходный локальный замер Project Web Pilot 0.6.9: ensure 295 ms, три получения одинакового полного пакета 606/567/542 ms, 40 164 UTF-8 bytes. Запрос идёт по loopback MCP; облачный tunnel в локальную передачу пакета не входит. Workflow Kit при каждом recover повторяет разрешение Git references и две проверки snapshot. После готовности composer уже используется единая вставка текста, а не посимвольный ввод; обязательная пауза 200 ms и наблюдение отправки защищают от дублей.

Варианты:
- Предварительная подготовка + кэш по содержимому входов: сохраняет полный контракт и убирает повторный builder из критического пути. Выбран для релиза.
- Уменьшение capsule: помогает размеру ввода, но меняет выбор required данных и не требуется для этой оптимизации.
- Ускорение самого Git builder: полезно для холодного старта, но затрагивает поставляемый Workflow Kit и его upgrade; пока не нужно.
- Удаление проверок/паузы перед Send: не принято, поскольку увеличивает риск чужого draft, устаревших данных и двойной отправки.

Применяется известный принцип кэша по входным данным: сохранённый результат используется после сравнения зависимостей, как в ccache (https://ccache.dev/manual/latest.html#_how_ccache_works). Дополнительная библиотека не нужна.

Новый путь: фоновое получение штатного COMPLETE → хранение проверенного результата в памяти → проверка входов при запросе → добавление session/request_id → повторная проверка перед Send → обычное наблюдение сообщения. При изменении входов выполняется штатный recover; подготовленный текст не дополняется устаревшими фрагментами. Пакет соответствует файлам/плану проекта; незаписанные решения разговора автоматически не извлекаются.

Релиз публикует длительность подготовки и доставки в подробностях контекста. Замер не включает рассуждение/ответ модели; готовность страницы и свободного composer остаётся обязательной. Масштаб полного ускорения зависит от доли подготовки в исходном ожидании.

### Проверка перед Send — T007

Попытка сохраняет ключ исходных данных, preparationMs/cacheHit и после наблюдаемой отправки deliveryMs. Начиная со scope 029 / T006 приложение получает ключ из актуальной полной WorkspaceSetup.ready с отдельным адресом workspace/sessionId/planId и проверяет его при подготовке и непосредственно перед Send. Ошибка ключа или старый пакет без ключа требуют новой подтверждённой подготовки; возраст пакета не заменяет эту проверку. Ожидание уже выполняющейся холодной сборки учитывается в preparationMs и не выдаётся за мгновенное попадание в кэш. Просмотр sent/legacy/unknown чата не запускает runtime.ensure, прогрев или новый recover; при потере актуальности вставленный черновик сохраняется без отправки.

## Видимость выполнения операций — T008

По отдельному поручению пользователя индикатор выполнения виден без раскрытия подробностей: вращающееся кольцо, название текущего этапа и прошедшее время. Этапы: проверка папки/подготовка проекта, подключение служб, открытие ChatGPT, получение/вставка/отправка контекста, наблюдение отправки; также действия с проектами, настройками и архивом. Фоновая пересборка пакета имеет отдельную подпись и не выдаётся за отправку. При завершении индикатор скрывается. Ожидание login/draft и ошибки остаются отдельными сообщениями, а не бесконечным спиннером. Процент прогресса не выдумывается; reduced-motion останавливает вращение, подпись/время сохраняются.

### Результат реализации — 0.6.10

На текущем workspace одинаковый полный пакет 69 556 bytes: median штатной подготовки 691.55 ms, из готового кэша 17.98 ms; вместе с дополнительной проверкой перед Send 36.07 ms (~19.17x). В packaged Electron macOS load+validation 40.24 ms. Подготовка в фоне сохраняет полный текст; сборка после изменения происходит штатным builder. Время страницы/ответа модели не входит в эти показатели. Пакет хранится в памяти; после restart прогрев начинается заново. Полный анализ вариантов и границы измерения приведены выше.

## Восстановление перед доставкой — Project Doctor 0.6.20

Ошибка Workspace Setup может быть исправлена явным запуском Доктора из Settings/экрана ошибки. Доктор не отправляет сообщение и не создаёт сессию. После повторной readiness пользователь выбирает действие продолжения; оно использует эту каноническую последовательность доставки. Project continuity 1.3 всегда включает OVERVIEW, MODULES и DOCUMENTATION_INDEX, в том числе при NONE; финальная DOCS не расширяет recovery всеми историческими dependency diffs.
