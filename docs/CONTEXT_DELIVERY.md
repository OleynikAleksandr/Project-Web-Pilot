# Передача контекста

Это канонический контракт Project Web Pilot для стартового сценария. Он описывает новую оболочку; текущий MCP-контракт находится в исходном `mac-codex-local/skills/local-computer/SKILL.md`. При реализации адаптера проверить согласованность обоих документов, tool descriptions и backend. Противоречие не обходить подменой события.

## Каноническая последовательность

1. **Зафиксировать цель.** Координатор получает явную абсолютную папку, её project_id и привязанный чат. Для нового чата создаёт уникальный session_id; при продолжении того же чата сохраняет его. Новый session_id не заимствуется из исторических тестов. Отдельный request_id обозначает попытку отправки, не lifecycle-событие ChatGPT.
2. **Подготовить инструменты.** Само приложение вызывает существующий `control.py status/start` и проверяет отдельно MCP initialization и готовность tunnel. Модель не получает поручение запустить сервер, через который ей ещё предстоит работать. Готовность локального endpoint не означает, что плагин доступен в этом веб-чате; это проверяется фактическим вызовом из ChatGPT.
3. **Подготовить страницу.** Открыть связанный чат во встроенном Chromium, дождаться входа и доступного поля пользователя. Существующий черновик и текущая генерация задерживают автоматическую отправку с понятным состоянием. Не стирать черновик и не прерывать ответ ради стартового текста.
4. **Отправить видимое сообщение.** Собственный локальный хук оболочки формирует текст с workspace, session_id, request_id и краткой задачей. Сообщение просит выполнить последовательность этого контракта. Оно является обычным пользовательским сообщением, не developer context и не внутренним SessionStart. Для первой проверки задача ограничена чтением состояния, без изменения файлов.
5. **Получить контекст агентом.** Агент читает действующие MCP-инструкции, устанавливает папку через `bridge_status(repository=workspace)`, вызывает `workflow_context_recover(workspace, session_id, source="agent_request")` и читает весь `context`. Этот инструмент уже вызывает канонический `scripts/workflow recover --format json` в выбранном workspace; вручную собирать сокращённый пакет не требуется.
6. **Подтвердить агентом.** Агент вызывает `workflow_context_ack(workspace, session_id, probe_id, challenge, readback)`. probe_id/challenge и полный объект facts, включая null, берутся непосредственно из полученного пакета. После успеха агент сразу сообщает возвращённое `user_message`. При ошибке признаёт её и получает новый пакет; не выдумывает успешное подтверждение.
7. **Подтвердить в оболочке.** Координатор читает `workflow_context_status(workspace, session_id)` через локальный MCP и сопоставляет latest/last_receipt с текущей привязкой и новой попыткой. Требуются новое выданное probe_id, acknowledged=true и совпадающие проект и сессия. Предыдущее подтверждение нельзя повторно засчитать новой отправке. UI показывает фактические проект, версию плана и отметку времени подтверждения.
8. **Продолжить работу.** После подтверждения агент действует только в пределах пользовательского поручения и канонического плана. Для тестового сообщения это завершение чтения; для рабочей задачи — её разрешённое продолжение.

Существующий MCP не принимает request_id отдельным аргументом: этот идентификатор хранится оболочкой и связывается с baseline журнала до отправки и последующим новым probe_id. За одну пару workspace/session_id допускается одна незавершённая стартовая попытка. Повтор при неопределённом результате отправки требует сначала проверить чат и журнал, а не нажимать Send вслепую.

## Шаблон первого проверочного сообщения

Приложение должно подставить реальные значения вместо фигурных скобок. Этот текст — будущий шаблон, не команда для агента, который читает данный документ.

```text
Восстанови контекст проекта через подключённый Codex Local Mac.
Workspace: {canonical_absolute_workspace}
Session ID для этого чата: {session_id}
Идентификатор отправки оболочки: {request_id}
Задача: прочитать актуальное состояние проекта и сообщить его. Файлы не менять.

Следуй действующим инструкциям MCP. Установи папку через bridge_status,
получи полный пакет workflow_context_recover с source=agent_request,
прочитай его и подтверди через workflow_context_ack с точными facts.
После успешного ACK сразу сообщи user_message.
Это стартовое сообщение нашей оболочки. Оно не доказывает запуск
внутреннего SessionStart или автоматического compact ChatGPT.
```

Не включать ключи, browser cookies, полный вывод приватной конфигурации или контекст другого workspace. Ошибку отсутствующего tool сообщать явно. Если подключение требует Refresh либо действий пользователя в ChatGPT, показывать конкретный шаг; не менять разрешения и не отключать плагин автоматически.

## Протокол существующего MCP

| Инструмент | Назначение и фактические параметры |
| --- | --- |
| workflow_context_recover | workspace, session_id, source: agent_request или manual_test; выдаёт полный context и новый probe |
| workflow_context_ack | workspace, session_id, probe_id, challenge, readback: точный facts; выдаёт user_message |
| workflow_context_status | workspace, session_id; выдаёт latest, last_receipt, last_compaction без challenge |
| workflow_context_hook | workspace, session_id, hook_event_name, source, trigger; приём реально настроенного lifecycle hook, не обычный старт оболочки |

Факты: project_id, project_name, plan_revision, scope_id, execution_scope_status, delivery_status, task_id, task_title. Backend проверяет signature текущего recovery и отклоняет пакет при изменении контекста. Возраст более часа, чужая сессия, заменённый probe и неверный readback также отклоняются. Повтор валидного ACK идемпотентен.

Status сообщает историческую запись и сам не пересчитывает её актуальность относительно текущего Git/плана. Поэтому UI обязан показывать версию и время подтверждения; после выявленного изменения плана или workspace не оставлять безусловное «всё актуально». Для новой проверки нужен новый пакет и ACK. Приложение не читает challenge из журнала и никогда не вызывает ACK вместо агента.

Имена инструментов в клиентском namespace могут иметь префикс. В реализации использовать актуальный tools/list, не рассчитывать на неизменность старого codex_apps-префикса. Для встроенного ChatGPT необходима фактическая доступность MCP в выбранном аккаунте и чате.

## Состояния интерфейса

| Состояние | Что подтверждено |
| --- | --- |
| Папка выбрана | Известны путь проекта и связанный чат |
| Подключение запускается | Локальные службы ещё не готовы |
| Требуется вход или подключение | Не выполнен вход либо MCP недоступен веб-чату |
| Ожидание поля ввода | Есть черновик, генерация или страница ещё загружается |
| Сообщение отправлено | В чате подтверждено появление нашего сообщения |
| Контекст ожидает подтверждения | Сообщение отправлено, подходящего ACK ещё нет |
| Контекст подтверждён | Получен соответствующий ACK с проектом, версией и временем |
| Ошибка / результат отправки неизвестен | Показана конкретная причина и безопасный следующий шаг |

Нельзя выводить «Контекст подтверждён» только по тому, что текст вставлен, получен HTTP 200, готов tunnel или существует старый ACK.

## Отношение к hooks и compact

Собственный хук оболочки — локальный обработчик её события, запускающий каноническую последовательность выше. Он не регистрирует внутренние hooks Web Work и не вызывает workflow_context_hook с выдуманным source=startup/compact.

В текущем backend `runtime_event_verified` остаётся false даже при ручном вызове receiver. Успешный readback подтверждает возврат фактов пакета, а не понимание модели, её будущую дисциплину или автоматический compact. Старый Workflow Kit hook:ack относится только к реально доставленному DELIVERY-MARKER локального Codex и не используется для отметки новой оболочки.

Если в будущем появится доступный достоверный compact event, его источник и причинная связь с новым пакетом проверяются отдельно. Восстановление перед следующим запросом — возможный другой режим, пока не входящий в этот scope.

## Адаптер поля — T008

ChatGPTComposer работает только с видимым composer в HTTPS chatgpt.com. Textarea заполняется native value setter с input/change; contenteditable — обычным Chromium insertText внутри поля. Проверяются видимость, отсутствие чужого черновика, остановки генерации и доступность Send. Повторная проверка точного текста происходит в одном renderer turn с click, чтобы пользовательские изменения не были отправлены как стартовый запрос.

Перед click координатор обязан сохранить состояние sending. Успех отправки требует появления request_id в DOM сообщения с ролью user; цитата assistant не подходит. Таймаут после click даёт unknown и не повторяет Send. Смена папки отменяет ещё не выполненное действие. При неопределённом результате следующая попытка сначала только осматривает сообщение и status. Login/черновик/генерация/изменившаяся разметка возвращают конкретную причину ожидания.

## Координатор подтверждения — T009

ContextSession сохраняет baseline probe IDs, новый request_id и точный текст до отправки; sendStartedAtMs и sending записываются до click. После перезапуска sending/unknown проверяются только чтением DOM/status. ACK засчитывается при совпадении workspace/session/probe между latest и last_receipt, source=agent_request, новой выдаче после начала попытки, acknowledged=true и совпадении всех восьми фактов с текущим планом. Сохранённый ackProbeId не подменяется чужим поздним probe.

Статус подтверждения связан также с наблюдавшимся пользовательским сообщением и привязанным chat URL. Переоткрытие чата не отправляет новый текст. Изменение плана или истечение свежести показывается как необходимость обновления, а не безусловное подтверждение. Кнопка повторной проверки после неизвестного Send только перечитывает состояние; новый запрос допускается после уже завершённого ACK либо через явно выбранный новый чат. Через 180 секунд без ACK появляется понятное сообщение, дальнейшие status-чтения могут принять поздний валидный ответ.

## Реальный composer и связь чата — T010

В Work contenteditable отображает абзацы как несколько переносов строки. Адаптер нормализует только последовательные переводы строк и их формат; слова, путь и пробелы внутри строк остаются под точным контролем. Собственный заранее сохранённый текст может быть продолжен после перезапуска; чужой изменённый черновик не отправляется.

До собственной отправки существующий чат считается посторонним. После Send координатор ждёт постоянный conversation URL и собственное пользовательское сообщение. Временный адрес Work /c/WEB:UUID не принимается за постоянную привязку; наблюдавшийся переход к /c/UUID обрабатывается без нового Send. Выбор папки, новый чат, закрытие окна и повторный запуск используют один и тот же контракт.

## Повторная проверка после устаревшего ACK — T012

Если пришёл валидный ACK, но к моменту чтения уже изменился план, интерфейс показывает устаревание. При подтверждённой отправке и привязанном чате старая попытка отмечается завершённой; явная кнопка «Обновить контекст» может сформировать новый запрос с новым baseline. Это не распространяется на неизвестный исход Send или неподтверждённый пакет. Неполные facts, отсутствующий receipt и некорректное время ACK не подтверждают контекст.
