# Доставка контекста — Web Pilot 0.6.97

## Владелец и границы
Workflow Kit 1.6.0 строит полный recovery; Web Pilot доставляет его в ChatGPT Web. MCP на macOS/Windows предоставляет только локальные инструменты, не контекст. Модельные API, чтение cookies/page internals и системный clipboard не используются. Связанный Web Pilot Sidebar переиспользует browser-адаптер: [контракт](modules/chatgpt-dom-compatibility.md).

Пакет передаётся новой сессии или по явному «Обновить контекст». Просмотр сохранённого чата, переключение между чатами и перезапуск приложения сами по себе не отправляют его повторно. Автоматическая доставка после внутреннего compact не заявляется без подтверждённого сигнала.

## Последовательность
1. Выбрать канонический workspace и current plan. Session ID принадлежит навигации разговора, не выбирает план. Сохранённый URL может открыться до фоновой readiness; доставка ждёт подтверждённой готовности.
2. Клиент вызывает установленный Kit: recover --format packet. ContextCache общий для чатов workspace, до четырёх полных пакетов в памяти; параллельные запросы объединяются. Источник ключа — WorkspaceSetup.ready().inputKey / inspectionInputs, включая новые planning/NONE-источники и повторные dirty-правки.
3. Проверить delivery_protocol=inline-context-v1, status=ready, completeness=COMPLETE, workspace, facts, точный размер/хеш context. Дополнительно проверить parts: последовательные index/total, text/bytes/sha256, предел каждой части и сцепление частей через два перевода строки, равное context. Старый пакет без частей требует обновления Kit.
4. Сохранить attempt: requestId, короткий текст и attachments из частей. Имена включают requestId, номер и общее число; содержимое каждого файла — точный part.text.
5. Дождаться входа, режима Chat/Work, свободного поля и отсутствия busy/ошибок. Перед вставкой подтвердить актуальность входов/facts. Вставить File[] через DataTransfer и ClipboardEvent(paste), затем короткую текстовую обёртку.
6. Дождаться всех отдельных карточек файлов без признаков загрузки/ошибки и доступного Send. Состояние повторно проверяется непосредственно перед кликом. При неполной загрузке сообщение не отправляется.
7. Сохранить send-start до действия. Один click завершает автоматическую доставку как sent / send-dispatched; post-click ожидания текста сообщения или машинного ACK нет. Это подтверждение вызова Send, не доказательство ответа модели или живой приёмки.
8. Постоянный URL связывается независимо от текстового представления вложений. Агент читает пакет, кратко подтверждает проект и ждёт следующего поручения.

## Первое сообщение
Содержит проект, точный workspace, навигационный Session ID, requestId, число частей и правила исполнителя. Основные процессные инструкции остаются в Workflow Core/PROTOTYPE, не копируются в обёртку.

Обязательная строка: **«Читай каждое вложение отдельно одним вызовом, не объединяй вложения в общий вывод, при признаках обрезки дочитай недостающее».**
Чтение вложений разрешено; MCP проекта в первом ответе не вызывается, файлы проекта не меняются. Ответ — короткое подтверждение восстановления и назначение/состояние проекта по-русски.

Правила исполнителя запрещают запуск других модельных агентов без поручения и управление UI мышью/клавиатурой/командами. Список окон и снимки разрешены. Существующие разговоры автоматически новыми инструкциями не дополняются.

## Части и ошибки
Kit ограничивает пакет 180000 байт и 7 частями, каждую — budget.document_bytes (28000 UTF-8 по умолчанию) с оформлением. Восьмая часть или общий избыток дают CONTEXT_TOO_LARGE; скрытого усечения и fallback к большой текстовой вставке нет. Контракт состава — [recovery](modules/workflow-kit-recovery.md).

Attachment readiness определяется по видимым карточкам вне истории сообщений: точное имя, отдельная карточка удаления, отсутствие progress/error и доступность Send. Во время загрузки допустимо ограниченное ожидание с повторной DOM-проверкой; обычная работа управляется событиями PageStateSource. Селекторы — граница совместимости с реальным ChatGPT.

Сохранённая попытка после частичной загрузки сохраняет requestId и все части. Метка на editor и состояние composer препятствуют повторному paste; изменённый набор не подменяется незаметно. ATTACHMENTS_PENDING/FAILED/CHANGED требуют проверки состояния, а не повторного Send. Исключение после возможного клика даёт unknown; автоматический дубль запрещён.

Подготовленные попытки старого формата без attachments не отправляются как новый пакет. Уже отправленные/legacy разговоры остаются доступными. Смена документа/проекта отменяет ещё не выполненное действие; чужой чат не привязывается без своей отправки. Временные Work URL ожидаются до постоянного адреса.

## Черновик и ручной ввод
Черновик и генерация задерживают автоматический старт. Только явное создание новой сессии разрешает ограниченную очистку восстановленного поля на пустой entrypoint-странице; reopen/retry чужой текст не удаляют. После собственной вставки содержимое короткого сообщения не сверяется как условие Send, но наличие и загрузка всех вложений обязательны.

Ручной Send подготовленного recovery распознаётся по своему сообщению. Обычное ручное первое сообщение сохраняет manualStart и URL, не объявляя recovery доставленным; такой чат ждёт явного обновления. Сигнал ручного Send привязан к документу, не выводится из одного количества сообщений.

После успешной доставки явное обновление создаёт новый requestId и пакет. Неопределённый исход сначала требует наблюдения/решения; повторное открытие не разрешает повторную отправку.

## Автовыполнение и наблюдение
AutoPlan независимо наблюдает текущий checkout и отправляет «Продолжай» с данными следующей задачи, не больше 4096 байт. Это не новый scope и не recovery. Перед отправкой nextTask перепроверяется; изменившаяся задача отменяет подготовленный сигнал. DONE/раунды/DOCS читаются из актуального плана, session ownership отсутствует.

PageStateSource принимает только сообщения правильного frame/origin/document/sequence. Текст беседы в IPC не передаётся; busy означает видимый Stop, не серверный статус. Diagnostics хранят переходы, причины и время без содержимого сообщений, cookies и ключей. PlanMonitor работает независимо от доставки; файловые события требуют перечитывания, не являются журналом.

## Проверка и переход
Node tests и Electron fixture проверяют состав файлов, ожидание загрузки, один Send, частичные/неопределённые сбои, восстановление attempt и совместимость pageScript. Ручная отправка семи файлов по 28000 байт подтверждена пользователем: 21 метка, сумма 8442. Synthetic File/DataTransfer в живом ChatGPT по решению 07.10.2026 проверяется после нового выпуска; fixture это не подтверждает. Нативную Windows и чистый первый запуск проверяет пользователь.

Текущий checkout остаётся на установленном Kit 1.5.6 до T006; source 1.6.0 уже содержит новый формат. Полный порядок и запасной внешний клиент — [переход](planning/workflow-kit-context-transition.md). Отсутствие живой пробы не блокирует согласованный выпуск, но не превращается в положительную приёмку.
